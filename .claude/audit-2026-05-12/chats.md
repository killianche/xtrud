# Аудит: Chats (Inbox + Thread)

## TL;DR

Чат — core-loop платформы, и в текущей реализации он закрывает только базовый minimum-viable-уровень: список + 1:1 переписка + realtime через Supabase. Главные пробелы: (1) на карточке чата и в шапке диалога **нет контекста заказа** (категория, цена, статус, дата) — а это именно то, ради чего пользователи и говорят; (2) **нет шаблонов быстрых ответов** для мастера, а это самый высокий ROI в marketplace-чате (Thumbtack, TaskRabbit); (3) **нет статусов сообщения** (отправлено / доставлено / прочитано) и **нет typing-индикатора** при том, что бэкенд уже знает время последнего прочтения; (4) пузыри сообщений **не группируются по отправителю**, **нет date-separator**, и **аватаров нет** ни в инбоксе, ни в треде — вместо них одиночная буква-инициал, что прямо нарушает 2-й принцип «классные фото — главный визуальный нерв»; (5) `bg-canvas` под пузырями не-моими делает их визуально слабыми в light-теме, а dark-тема не описана вообще. Web-вариант отсутствует как класс: оба экрана рендерятся stacked, без split sidebar+main — на десктопе так смотреть переписку неудобно.

## Экраны в скоупе

- `app/(tabs)/chats/index.tsx` — список чатов (Inbox).
- `app/(tabs)/chats/[id].tsx` — диалог 1:1 (клиент ↔ мастер).
- `app/(tabs)/chats/_layout.tsx` — Stack с `slide_from_right`, без header. OK.

Связанные хуки (только чтение для контекста, не правим):
- `src/features/chat/use-my-chats.ts` — JOIN `orders.title/status` + `users.first_name/last_name/avatar_url`. То есть **аватар партнёра и статус заказа уже в payload, но UI их не использует**.
- `src/features/chat/use-chat-messages.ts` — realtime INSERT. Полный `ChatMessage` (всё из `messages`), но UI рендерит только `text` + `created_at`.

## Находки

### 🔴 Критично

#### 1. Inbox: карточка чата не несёт контекста заказа — только `order.title` мелким шрифтом

**Файл:** `app/(tabs)/chats/index.tsx`, строки 119–137 (`ChatListRow`).

**Что не так:**
В payload `useMyChats` уже есть `order.id / order.title / order.status` и `client/master.avatar_url`. UI использует только `order.title` как строку под именем и **полностью игнорирует**: статус заказа (`new / in_progress / completed / cancelled`), аватар партнёра, last-message-preview (показывается «Заказ» или название заказа вместо последнего сообщения). Это противоречит главным четырём референсам — у Profi.ru/Thumbtack/Яндекса карточка чата = превью заказа + последнее сообщение + статус, а не только имя собеседника.

В частности: у пользователя 5 чатов с разными мастерами — он видит 5 одинаковых строк «Имя / Заказ X / дата». Понять, на каком этапе каждый, нельзя без открытия диалога.

**Что сделать (конкретные правки):**
- Строка 1 в карточке: имя партнёра (как сейчас) + **бейдж статуса заказа справа** (pill 13px, `surface-card` фон для `new/in_progress`, `success-soft` для `completed`, `muted` для `cancelled`).
- Строка 2: **последнее сообщение** (text-preview), не `order.title`. Для этого добавить в `useMyChats` JOIN на последнее сообщение (`messages` LIMIT 1 ORDER BY created_at DESC) или хранить `last_message_text` в `chats` денормализованно. Если бэкенд не готов — пометить как TODO и сейчас показывать `order.title` мелким `text-caption text-muted-soft`, а в строке 2 — превью с placeholder «Начните переписку».
- Строка 3 (тонкая, опциональная): `order.title` курсивно/`muted-soft` 12px, чтобы сохранить контекст «о каком заказе чат».
- **Аватар:** заменить «буква-инициал на сером кружке» (`bg-surface-2`) на `expo-image` с `avatar_url`, fallback — инициалы. Размер 44–48px (сейчас 48 — оставить).

**Референс:** Telegram inbox (`screenshotId: 87080`) — двухстрочный rich-row; Wix Business Inbox (`screenshotId: 21476`) — каждый thread с message-preview + timestamp + unread-badge. Profi.ru/Thumbtack — статус заказа всегда в превью.

**Сложность:** M (нужно добавить JOIN/денормализацию в use-my-chats и расширить `MyChatWithRefs`).
**Платформа:** Both.
**Принципы:** 1 (минимализм, без шума, но с информацией), 2 (фото!), 3 (быстро понять контекст), 6 (функциональность — payload используется не полностью).

#### 2. Thread: шапка не показывает контекст заказа — нет ни статуса, ни цены, ни срока

**Файл:** `app/(tabs)/chats/[id].tsx`, строки 92–124 (header).

**Что не так:**
В шапке диалога — имя партнёра (тапается → переход на профиль, ОК) и `chat?.order?.title` мелкой строкой. Никаких других данных по заказу нет. Между тем чат — это переговоры **по конкретной задаче**, и пользователю критично видеть: какой статус (договариваемся / в работе / выполнено), какой бюджет обсуждался, какой дедлайн. Без этого человек либо помнит наизусть, либо лазит между табами.

У **Thumbtack** в шапке pro↔customer чата всегда видны: название задачи + цена/бюджет + статус + кнопка «View request». У **TaskRabbit** onboarding-туториал (`screenshotId: 9003`) явно показывает, что чат — это «продолжение бронирования», в шапке — карточка задачи. У **DoorDash** (`screenshotId: 64023`) чат с курьером встроен в карточку заказа со всеми деталями.

**Что сделать:**
- Добавить **под шапкой** компактную «order-context-strip» (collapsible или fixed-h-12):
  - Слева — статус-badge (pill, цвет по статусу).
  - В центре — `order.title` одной строкой + бюджет (если есть в `orders`).
  - Справа — кнопка-link «К заказу» (chevron → push `/orders/[id]`).
- Strip живёт **между header и messages**, фон `surface-soft` (`#f8f9fa`), border-bottom hairline. Высота ~44–48px, по принципам Cal.com — generous breathing, но не толстый блок.
- На вебе — order-context может быть отдельной правой панелью (см. находку 9).

**Сложность:** S (есть готовые данные в `chat.order`, нужно расширить SELECT на budget/deadline).
**Платформа:** Both.
**Принципы:** 1, 3, 6.

#### 3. Нет шаблонов быстрых ответов (quick replies) — ноль для мастера, ноль для клиента

**Файл:** `app/(tabs)/chats/[id].tsx`, область input (165–190).

**Что не так:**
Полностью отсутствует то, что Thumbtack/Airbnb/TikTok DM считают must-have для marketplace и любого high-frequency мессенджера. У мастера 10 однотипных заказов в день — он 10 раз пишет «Здравствуйте, опишите подробнее, какой объём работ?». В Ингушетии где мастера часто на выезде и стучат по экрану одной рукой — это критическая боль скорости.

**Airbnb Messaging settings** (`screenshotId: 12772`) **прямо** содержит «Quick replies» + «Suggested replies» как отдельную фичу. **TikTok DM** (`screenshotId: 3944`) показывает AI-suggested replies над input. **Thumbtack** Pro app — шаблоны это известный must для мастера.

**Что сделать (минимум, без AI):**
- Над input — горизонтальный scroll-ряд из 3–5 chip-кнопок с шаблонами. Дефолтный набор зависит от роли:
  - **Мастер:** «Здравствуйте, опишите подробнее задачу», «Когда удобно подъехать?», «Цена под ваш объём — X ₽», «Сегодня занят, могу завтра», «Готово, всё сделано».
  - **Клиент:** «Подскажите цену», «Когда можете подъехать?», «Спасибо!».
- Chip = `badge-pill` (по DESIGN.md), но `surface-card` фон, padding 8×14, tap → вставляет текст в `<TextInput>` (не отправляет автоматически — пользователь может дописать).
- Шаблоны редактируемые: в Settings → «Мои шаблоны» (отложить как Sprint+1, сейчас захардкодить дефолты на роль).
- Не показывать chip-row, когда поле уже заполнено (`text.length > 0`) — иначе шум.

**Сложность:** M (UI компактный, но добавится state шаблонов на роль; редактирование — отдельный Sprint).
**Платформа:** Both.
**Принципы:** 3 (главное — скорость переписки), 6 (мастер реально использует, не декорация).

#### 4. Сообщения не группируются и не разделены датой — длинный тред превращается в стену

**Файл:** `app/(tabs)/chats/[id].tsx`, рендер сообщений 153–155 и `MessageBubble` 195–213.

**Что не так:**
Каждое сообщение рендерится отдельным пузырём с time-suffix снизу. Три моих подряд сообщения = три отдельных bubble + три раза по 12:34. Date-separator (`Сегодня`, `Вчера`, `12 мая`) отсутствует. Это базовая гигиена чата — её есть везде (Telegram, Messenger, любой WhatsApp).

**Telegram** (`screenshotId: 87080`) — date-separator + grouping by sender (хвостик-стрелочка только у последнего пузыря группы). **DeepSeek conversation** (`screenshotId: 19153`), **Messenger** — то же.

**Что сделать:**
- Группировать соседние сообщения одного `sender_id`, если зазор между ними < 60 сек: пузыри идут вплотную (`gap-0.5`), время показывается **только под последним** в группе.
- Уменьшить вертикальный `gap` между сообщениями одного отправителя (`gap-0.5` vs текущий `gap-2`) — между разными отправителями оставить `gap-2`.
- Перед первым сообщением каждой календарной даты — date-separator: текст `13px / 500 / muted-soft`, центрирован, обёрнут в `surface-card` pill (как Telegram). Логика: `Сегодня / Вчера / Понедельник / 12 мая 2026`.

**Сложность:** S (чистая UI-логика, payload не меняется — есть `created_at`, `sender_id`).
**Платформа:** Both.
**Принципы:** 1 (меньше визуального шума), 5 (современность), 6.

#### 5. Нет статусов сообщения (отправлено / доставлено / прочитано), хотя бэкенд это знает

**Файл:** `app/(tabs)/chats/[id].tsx`, `MessageBubble` 195–213.

**Что не так:**
В `chats` есть `client_last_read_at` / `master_last_read_at` (`useMarkChatRead`, `isChatUnread`). То есть **бэкенд уже хранит** время последнего прочтения партнёром. Но в UI треда у моих сообщений нет ни галочки, ни «прочитано» — пользователь не понимает, дошло ли сообщение, прочёл ли его собеседник, висит ли в pending.

Это нарушает принцип 6 («функциональность»): данные есть, UI их не использует. Это же — главное чувство «современности» в чате (принцип 5).

**Что сделать:**
- У моих пузырей под временем — статус-иконка размером 12–14px, цвет `muted-soft`:
  - **Отправляется** (optimistic, `sendMessage.isPending` или ещё нет `id`): часики (`Clock`).
  - **Отправлено** (есть `id`, но `partner_last_read_at < message.created_at`): одна галочка (`Check`).
  - **Прочитано** (`partner_last_read_at >= message.created_at`): две галочки или `CheckCheck` с акцентным цветом.
  - **Ошибка** (`sendMessage.error`): красный `AlertCircle` + tap → ретрай.
- Иконку рендерить inline с временем (`{time} {icon}`), не отдельной строкой.

**Сложность:** S (всё на клиенте, payload есть).
**Платформа:** Both.
**Принципы:** 5, 6.

#### 6. Аватары — нет нигде, везде «одна буква-инициал на сером кружке»

**Файлы:** `index.tsx` 114–118, `[id].tsx` header 92–124.

**Что не так:**
В payload `useMyChats` есть `client.avatar_url` и `master.avatar_url`. UI **не использует их вообще**. Везде рендерится `{partner.first_name[0]}` на `bg-surface-2`. В шапке треда аватара нет совсем — только текстом имя.

Это прямо нарушает 2-й дизайн-принцип «классные фото — главный визуальный нерв». В marketplace мастеров фото = trust-signal номер один (Thumbtack pro-detail page целиком построен на большом фото). В чате это особенно важно: ты разговариваешь с конкретным человеком, а не с инициалом.

**Что сделать:**
- В `ChatListRow` (Inbox): `expo-image` 48×48 `rounded-full` с `partner.avatar_url`, fallback на инициалы только если `avatar_url === null`. Использовать `blurhash` placeholder (есть в стеке — `expo-image`).
- В шапке `[id].tsx`: добавить 32px аватар слева от имени партнёра (после back-кнопки). Тап на аватар → тот же `partnerHref` что и тап на имя (профиль).
- Под аватаром в шапке — маленький online-индикатор: зелёный кружок 8px в углу (paused, см. находку 7 — это nice-to-have, но место под него зарезервировать).

**Сложность:** S.
**Платформа:** Both.
**Принципы:** **2** (главное), 5.

#### 9. Web-варианта нет — на десктопе stacked-layout неудобен

**Файлы:** оба экрана, кода для веба нет вообще.

**Что не так:**
Брифинг прямо требует: web должен быть полноценным, не «адаптив телефона». На десктопе marketplace-чат — это всегда **split-view sidebar+main**: слева вертикальный список чатов фиксированной ширины (~340px), справа открытый тред. При тапе на чат не происходит «навигация-переход», а просто меняется содержимое правой панели. Это паттерн Slack (`siteId: 8498`), Beeper (`siteId: 14997`), всех B2C-мессенджеров, всех marketplace (Avito, Profi.ru).

**Что сделать (план, не реализация — реализация большая):**
- Завести двух-вариантный layout через `Platform.OS === 'web'` или, лучше, через breakpoint-хук (`useWindowDimensions`):
  - Mobile (< 768px): текущий stacked flow (`/chats` → push `/chats/[id]`).
  - Desktop (≥ 768px) и Web: split — `/chats` рендерит обе панели side-by-side, route param `id` определяет, какой тред показан справа. Если `id` нет — справа empty state «Выберите чат».
- Sidebar: ширина `w-[340px]` или max-w, ScrollView c карточками; активная карточка с `bg-surface-soft`.
- Main: тот же `[id].tsx`, но без back-кнопки и без отдельного header — заголовок встроен в split-toolbar.
- Тред на десктопе должен быть **ограничен по ширине** (max-w ~720px, центрирование), иначе пузыри растягиваются на пол-экрана.
- На вебе over-keyboard logic (KeyboardAvoidingView) не нужна — там обычная клавиатура.
- На вебе Enter = send, Shift+Enter = newline (mobile — кнопка Send).

**Сложность:** L.
**Платформа:** Web (+ tablet ≥768).
**Принципы:** 3, 5, 6.

#### 10. Input UX: send-кнопка снаружи поля, нет toolbar, нет attach, нет focus-state

**Файл:** `app/(tabs)/chats/[id].tsx`, 165–190.

**Что не так:**

#### 11. ScrollView вместо FlashList — на больших чатах будет тормозить

**Файл:** оба экрана используют `ScrollView`.

**Что не так:**
- Inbox: при 50+ чатах FlashList даст более плавный рендер и lower memory.
- Thread: при 500+ сообщений ScrollView рендерит всё — это main thread block. По принципу 4 (скорость) — должен быть `FlashList` (он явно в стеке упомянут в BRIEF: «плавный feed (FlashList)»).

**Что сделать:**
- Inbox → `FlashList` с `estimatedItemSize={72}`.
- Thread → `FlashList` с `inverted` опцией (сообщения растут снизу вверх — типичный mobile messenger pattern; убирает костыль `scrollToEnd` после каждого ре-рендера). Можно через `FlashList` или временно `LegacyImplementation` — но `scrollToEnd` через `setTimeout` (строка 55) — ненадёжно.
- Pull-to-refresh в треде — для подгрузки старых сообщений (pagination). Сейчас всё грузится разово LIMIT по умолчанию — на длинных чатах будет тяжело.

**Сложность:** M (особенно inverted thread + pagination).
**Платформа:** Both (mobile в первую очередь; web ScrollView ок).
**Принципы:** 4, 6.

## Кросс-экранные паттерны

Сводка повторяющихся проблем (не дублирую находки, фиксирую системные дыры):

1. **Payload используется не до конца.** В `useMyChats` уже есть `avatar_url`, `order.status`, `order.id` — все они отрисовываются плохо или никак. Это самая частая системная проблема в этой группе: бэкенд готов, UI не подобрал. (Принцип 6: «грамотная инженерия».)
2. **Hardcoded цвета вместо токенов.** `#71717a`, `#0a0a0a`, `#ffffff` — по нескольким местам. Заводим единый source: либо `lib/tokens.ts`, либо передаём цвета через NativeWind на обёртках Lucide-иконок. Это блокер для dark.
3. **Dark theme как «область невидимого».** Ни один компонент не описан как «работает корректно в обеих темах» — `surface-2`, `accent-soft`, `placeholderTextColor` все указаны на light-варианте. Это блокер уровня DESIGN.md.
4. **Web как «mobile, растянутое до десктопа».** На обоих экранах — никаких breakpoint'ов, никаких desktop-вариантов. Это блокер уровня архитектуры layout — нужен общий `useResponsive` hook + split-pattern.
5. **Отсутствие FlashList / pagination.** Оба экрана на ScrollView; не масштабируется на длинные истории и большие инбоксы.
6. **A11y минимальный.** Везде только `accessibilityRole="button"` без label/hint. Это системная дыра, по ней нужен общий проход.
7. **Связка чат↔заказ слабая.** Только `order.title` строкой в Inbox и в header. Ни статуса, ни кнопки «к заказу», ни цены. Хотя в `PRODUCT_CONTEXT.md` чат прямо описан как «по заказу X».

## Что отлично — НЕ трогать

- **Realtime через Supabase channel + dedup по `id`** (`use-chat-messages.ts` 40–73). Грамотная имплементация: setQueryData без рефетча, дедупликация против optimistic update — это правильно.
- **Mark-as-read триггерится при появлении новых сообщений** (`[id].tsx` 44–47), не только при mount. Корректное поведение для активного thread.
- **Empty state Inbox текст** — содержательный, точный, по делу. Только CTA добавить (находка 7).
- **KeyboardAvoidingView с `padding` на iOS** (87–91) — правильное поведение для чата.
- **Optimistic UX в `onSend`** (70–84) — текст исчезает мгновенно, при ошибке возвращается обратно. Это очень хорошо, не ломать.
- **Stack screenOptions** в `_layout.tsx` — `slide_from_right` корректно для thread-навигации, `headerShown: false` потому что свой header. OK.
- **maxFontSizeMultiplier={1.3}** в input (176) — забота о Dynamic Type. Принцип 6, отлично.
- **`hitSlop={12}` на back-кнопке** — частично решает touch-target проблему, оставить (хотя стоит увеличить до 16–20).
- **`useMyChats.staleTime: 15_000` + `useChatMessages.staleTime: 0`** — корректная стратегия: список редко обновляется, тред — постоянно через realtime.
