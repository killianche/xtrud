# Подключение агентов на крупных задачах (приоритет 0)

## Зачем этот файл

Запрошено владельцем 2026-07-28: «Подключай агентов и добавь в документацию, чтобы при большой задаче ты сразу подключал агентов.»

Проблема, которую это решает: на крупной задаче один агент читает файлы последовательно, забивает контекст сырым кодом и к моменту принятия решений уже «не помнит» начало. Итог — поверхностный результат, пропущенные куски очереди, «сделал самое импактное». Агент-помощник читает свой кусок в **своём** контексте и возвращает только вывод — главный агент остаётся с чистой головой и полной картиной.

Правило простое: **большая задача → сначала веер агентов, потом работа.** Не наоборот, не «сам почитаю, если что — позову».

---

## Триггеры: когда агенты ОБЯЗАТЕЛЬНЫ

Если задача попадает хоть под один пункт — агенты подключаются **до** первой правки кода. Не спрашивая разрешения (правило №12 working-rules — не жду подтверждений).

1. **Аудит / ревизия / «изучи»** — «изучи продукт», «проверь всё», «найди все места где…», «пройдись по коду», «что у нас с безопасностью». → веер из 3–5 агентов по областям.
2. **Задача трогает 5+ файлов** или заранее непонятно сколько. Например: миграция паттерна по всем экранам, переименование сущности, смена источника данных.
3. **Новая фича дольше часа** — сначала RPI (`/rpi:research` → `/rpi:plan` → `/rpi:implement`), эти команды сами вызывают агентов.
4. **Новый экран / страница** — обязательно `xtrud-designer`, без исключений (правило design-enforcement.md).
5. **Очередь из 5+ задач** от владельца в одном сообщении или серией. Независимые задачи из очереди раздаются агентам параллельно, зависимые — по очереди.
6. **Незнакомая область кода** — прежде чем править, `Explore` возвращает карту: где живёт логика, кто её дёргает, какие есть дубли.
7. **Расследование бага «не понимаю почему»** — 2–3 агента с разными гипотезами параллельно (данные / UI / платформа), а не одна линейная догадка.
8. **Архитектурное решение** (схема базы, внешний сервис, крупный рефакторинг) — `technical-cto-advisor` до начала работы.
9. **Перед коммитом крупного изменения** — `code-reviewer`.

## Когда агенты НЕ нужны

- Правка одной строки текста, цвета, отступа.
- Известный файл + известная правка («поменяй заголовок на экране заказа»).
- Ответ на вопрос по уже прочитанному в этой сессии коду.
- Чисто разговорный ответ («что дальше делать?», «объясни как работает вход»).

Ошибка в обе стороны стоит по-разному: лишний агент на мелочи — это минута. Отсутствие агентов на аудите — это пропущенные баги и потерянное доверие. **Сомневаешься — подключай.**

## Каталог: кого звать под задачу

### Обязательный совет качества владельца

Для любой осмысленной задачи, затрагивающей поведение продукта, архитектуру,
UI, данные, безопасность или release, работа идёт волнами с разделением
полномочий:

1. `product-manager` — бизнес-директор: определяет проблему, границы продукта,
   метрики и критерии приёмки.
2. `technical-cto-advisor` — директор по разработке: проверяет архитектуру,
   безопасность, совместимость, rollout и rollback.
3. `xtrud-designer` — проектирует полный UX/UI до правок экранов.
4. `senior-software-engineer` — реализует согласованный контракт в выделенной
   зоне и прикладывает автоматические проверки.
5. `qa-engineer` — независимо тестирует требования и реальные сценарии, включая
   различия web/iOS/Android; не принимает работу со слов разработчика.
6. `code-reviewer` — последним проверяет общий diff и передаёт замечания
   бизнес-директору и техническому директору для go/no-go.

Каждая роль отделяет подтверждённые факты от решений и `UNKNOWN`. Совет не
заполняет пробелы догадками: неизвестное получает способ проверки и блокирует
только зависящее от него опасное действие. Разработчик не начинает реализацию
архитектурного решения до заключения техдиректора, а финальный go/no-go требует
независимых QA и code-review.

При ограничении на параллельность роли запускаются волнами. Директор, разработчик
и проверяющие не должны сливаться в одну роль: автор кода не может быть
единственным тестировщиком или финальным ревьюером своей работы. Для мелкой
известной правки текста/отступа полный совет не нужен; обязательные триггеры
ниже сохраняются.

### Встроенные агенты

| Агент | Когда |
|---|---|
| `Explore` | **Рабочая лошадка разведки.** Читает много файлов, возвращает карту/выводы. Для любого «найди / изучи / где лежит». Только чтение — код не портит. |
| `general-purpose` | То же, но с правом писать: параллельные независимые правки, скрипты, проверки с запуском. |

## Как делать: параллельный веер

Главный приём. Область задачи режется на **непересекающиеся** куски, на каждый — свой агент, все запускаются **в одном сообщении** (иначе они пойдут по очереди и выигрыш во времени исчезнет).

Проверенное разбиение для аудита продукта (использовано 2026-07-28, 4 агента, полная картина за один заход):

1. **Клиентская часть** — `app/**` (маршруты), `src/features/**`, `src/components/**`, `src/lib/**`, метрики, TODO/заглушки.
2. **Серверная часть** — `supabase/migrations/**` (схема), RPC-функции, edge-функции, RLS и дыры, Storage, актуальность типов.
3. **История и этап** — `STATUS.md`, `SESSION_SUMMARY_*`, `TASKS.md`, launch-доки, `git log`, аудиты. Что открыто, что устарело.
4. **Инфраструктура** — `package.json`, `app.json`, `eas.json`, `deploy/**`, `scripts/**`, `.claude/**`, тесты, состояние рабочей копии, проверка типов.

Другие типовые разбиения:

- **Расследование бага:** агент-«данные» (запросы и база) ‖ агент-«интерфейс» (экран и обработчики) ‖ агент-«платформа» (различия браузер/телефон).
- **Правка по многим экранам:** сначала один `Explore` собирает точный список файлов → потом по агенту на группу файлов (или один `general-purpose`, если правки связаны между собой).
- **Новая фича:** `product-manager` ‖ `ux-designer` (параллельно) → `technical-cto-advisor` (если трогает базу) → `xtrud-designer` (если есть экран) → `senior-software-engineer`.

**Ограничения.** Разумный максимум — 5 агентов за раз; больше — каша в отчёте. Агентам, которые **пишут** в файлы, нельзя давать пересекающиеся зоны (два агента в одном файле = потерянные правки); если пересечение неизбежно — либо один агент, либо изоляция через `isolation: "worktree"`.

## Шаблон брифа агенту

Агент не видит наш диалог. Бриф обязан стоять на своих ногах.

```
Проект /Users/ruslancherbizhev/Desktop/xtrud — маркетплейс услуг
(Expo SDK 54 + Expo Router + NativeWind + TanStack Query + Supabase),
одна кодовая база web/iOS/Android.

Задача: <одно предложение — что именно нужно выяснить или сделать>.

Не трогай: <зона соседнего агента — обязательно, если запущен веер>.

Изучи / сделай:
1. <конкретный путь или паттерн поиска>
2. ...

Верни: <точная структура ответа — разделы, что в каждом>.
Пути файлов обязательны, длинных дампов кода не надо.
Пиши по-русски.
```

Обязательные элементы: абсолютный путь проекта, границы зоны, нумерованный список пунктов, формат ответа. Без последнего пункта агенты возвращают разноформатные простыни, которые невозможно свести.

## Что делать с результатом

1. **Свести, а не пересказать.** Пользователю идёт единая картина, а не четыре отчёта подряд. Отчёты агентов ему не показываются — он видит только то, что я написал.
2. **Проверять факты, на которых строится решение.** Агент может ошибиться. Прежде чем править код по его находке — открыть указанный файл и убедиться. Особенно это касается утверждений «не используется нигде», «дыра в безопасности», «уже починено».
3. **Противоречия между агентами — не замалчивать.** Проверить самому и написать, как есть.
4. **В отчёте владельцу — простым языком** (`communication-style.md`) и с указанием, кто работал: «Подключил четырёх помощников: код приложения, база данных, история проекта, сборки».
5. **Незакрытые находки — в `STATUS.md`.** Иначе следующая сессия начнёт разведку с нуля.

## Запрещено

- ❌ Начинать крупную задачу с самостоятельного чтения файлов «по-быстрому посмотрю» — контекст забивается, качество падает.
- ❌ Запускать агентов по одному там, где они независимы (теряется весь смысл).
- ❌ Отдавать агенту бриф без границ зоны при веере — получишь четыре пересекающихся отчёта об одном и том же.
- ❌ Принимать находки агента на веру и править код, не открыв файл.
- ❌ Отчитываться «агент сказал, что всё хорошо» — ответственность за результат на мне, не на агенте.
- ❌ Создавать новый экран без `xtrud-designer` «чтобы быстрее».
