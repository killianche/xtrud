# Делегирование агентам — обязательное правило

> Статус: DECISION владельца (2026-08-29). Это правило действует всегда, без
> отдельного напоминания в каждом запросе.

## 1. Базовое правило

Любая осмысленная задача xtrud выполняется **через совет ролей**, а не одним
агентом. Автор изменения никогда не является единственным QA и единственным
финальным reviewer собственной работы.

Мощность подбирается под задачу, а не «максимум всегда»: дешёвая задача не
должна стоить как аудит, а дорогая задача не должна проходить без review.

## 2. Маршрутизация: какой класс задачи — какие агенты

| Класс задачи | Роли | Модель / усилие | Thinking |
|---|---|---|---|
| Тривиальная правка: текст, копирайт, переименование, обновление документации | основной агент, без делегирования | Haiku/Sonnet | off |
| Обычная фича: кнопка, поле, экран, простой баг | `xtrud-implementer` → `xtrud-reviewer` | Sonnet | off |
| UI/новый экран | `xtrud-designer` → `xtrud-implementer` → `xtrud-qa` → `xtrud-reviewer` | Sonnet | off |
| Сложный или повторный баг | `xtrud-technical` (диагностика) → `xtrud-implementer` → `xtrud-qa` | Opus | **on** |
| Архитектура, стратегия, выбор между решениями | `xtrud-product` + `xtrud-technical` параллельно → `xtrud-reviewer` сводит | Opus | **on** |
| Auth, безопасность, платежи, RLS/ACL | `xtrud-security` → `xtrud-implementer` → `xtrud-security` (повторная проверка) | Opus | **on** |
| Миграции БД, backend, Beget/Supabase | `xtrud-backend` → `xtrud-security` → `xtrud-reviewer` | Opus | **on** |
| Критический релиз, полный аудит | все профильные роли параллельно → `xtrud-reviewer` финально | Opus | **on** |

Thinking включается по списку из запроса владельца: полный аудит, архитектура и
стратегия, сложная невылеченная с первого раза ошибка, авторизация/безопасность/
платежи, миграции БД, критический релиз, выбор между несколькими техническими
решениями.

## 3. Как запускать

- Независимые роли запускаются **параллельно одним сообщением** с несколькими
  вызовами агента; зависимые — последовательно.
- Каждому агенту явно выдаётся: зона владения (конкретные пути), запрет трогать
  соседние файлы, обязательное чтение `AGENTS.md` и
  [`docs/AGENT_WORKFLOW.md`](../../docs/AGENT_WORKFLOW.md), и требуемый формат
  отчёта (FACT / DECISION / UNKNOWN).
- Зоны владения агентов не пересекаются. Каждый агент сохраняет чужие
  изменения; `git add .` при смешанном worktree запрещён.
- Результат субагента — не истина по умолчанию. Основной агент проверяет
  утверждения кодом или проверкой, прежде чем принимать их.

## 4. Границы

- Внешние действия (commit, push, deploy, EAS build/submit, изменения
  Supabase/VPS/DNS) агентам не делегируются. Их выполняет только основной агент
  и только по явной команде владельца.
- Делегирование не отменяет release gate из `docs/AGENT_WORKFLOW.md`:
  `npm run quality:check` выполняется после последней правки, а не до неё.
- Если роли пришли к разным выводам, конфликт не «усредняется»: он выносится
  владельцу с обеими позициями и ценой каждого варианта.

См. также [`working-rules.md`](working-rules.md).
