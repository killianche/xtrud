# Стиль общения с владельцем продукта (приоритет 0)

## Главное правило

User — **владелец продукта xtrud**, не разработчик. Объяснять как руководителю бизнеса, не техническому директору. Запрошено явно 2026-05-20: «Пиши простым языком, не техническим. Я не понимаю технический.»

## Запрещено

- ❌ **Сокращения:** P0, P1, P2, RPC, RLS, TS, SQL, MCP, UX, UI, CRUD, MVP, API, FE, BE.
- ❌ **Жаргон:** mutation, hook, query, invalidation, regression, race condition, atomic, refactor, deprecated, schema, migration, hydration, lifecycle, idempotent, debounce.
- ❌ **Англицизмы там где есть русские слова:** implement → сделать, verify → проверить, debug → найти причину, commit → сохранить, deploy → выкатить, fix → исправить, fetch → получить, push → отправить.
- ❌ **Безличный технический стиль:** «Будет применена миграция к prod БД» → «Обновим базу данных проекта».
- ❌ **Код-блоки, JSON, SQL в ответе** — только если user явно попросил.

## Обязательно

- ✅ **Глаголы действий вместо существительных:** «исправил кнопку которая не работала» вместо «применил patch для button submit handler».
- ✅ **Бизнес-смысл рядом с действием:** каждое техническое действие сопровождать «зачем» с точки зрения продукта и пользователя.
- ✅ **Короткие предложения, простая структура:** что сделано → что значит для продукта → что дальше.
- ✅ **Шкала важности словами:**
  - «Срочно, нужно исправить до запуска» (раньше P0)
  - «Важно, но не блокирует» (раньше P1)
  - «Можно сделать потом» (раньше P2)
  - «Идея на будущее» (раньше backlog)
- ✅ **Время в человеческих единицах:** «Полчаса», «День работы», «Неделя» — не «~2h focused», «6h estimated».
- ✅ **Аналогии:** «Это как…», «Похоже на…», «Представьте что…».

## Если без термина никак

Расшифровать в скобках при первом упоминании:
- «Сохранил в репозитории (хранилище кода всего проекта)»
- «Открыл сайт в браузере и проверил» — лучше чем «preview MCP smoke-test»
- «Обновил базу данных (где хранятся профили мастеров и заказы)»

## Примеры

| ❌ Технически | ✅ По-человечески |
|---|---|
| «Phase 2 — ~2.5h. Master can complete happy path via Dashboard approval. P1 regression: form не pre-fills on resume.» | «Второй этап займёт около 2,5 часов. Мастер сможет пройти регистрацию полностью. Есть мелкая шероховатость: если он закроет приложение посередине, при возврате форма будет пустая. Данные не теряются, но придётся ввести имя заново. Не критично.» |
| «TS clean, biome lint pass, 8 grep-checks pass, design-quality §G/B/D enforced.» | «Проверил код — ошибок нет, все правила оформления соблюдены.» |
| «Применил миграцию 0095_finalize_master_onboarding к prod БД через MCP apply_migration.» | «Обновил базу данных — добавил функцию для последнего шага регистрации мастера.» |
| «P0 баг в LoginWall flash + redirect bounce из-за useAuthSession status race» | «Срочный баг: при заходе на профиль на долю секунды мелькает экран “Войти” у уже залогиненных пользователей. Выглядит криво.» |
| «Закрыл RPI Research → GO verdict. Перейду к /rpi:plan?» | «Закончил изучать новую функцию верификации — можно делать. Перейти к подробному плану реализации?» |

## Когда можно технически (исключения)

- User сам задал вопрос техническим языком («какая миграция применена?», «как работает RLS?») — отвечать на его уровне.
- User явно говорит «не нужно объяснять, я понял», «пиши коротко технически», «как разработчику».
- Финальный commit-message в git, имена файлов, command-line — это не для бизнес-чтения, может быть техническим.
- Имена технологий когда без них вообще никак (React Native, Supabase, Phosphor) — называть, но не объяснять архитектурно.

## Триггер на самопроверку

Перед отправкой ответа прогнать в голове:
1. Есть ли в ответе сокращения P0/P1/RPC/TS/RLS? → расшифровать.
2. Есть ли непереведённые жаргонные слова? → заменить русским эквивалентом.
3. Сказано ли что это даёт пользователю / бизнесу, не только что сделано в коде?
4. Каждое предложение читается ли с первого раза без перечитывания?

Если хоть один пункт fails — переписать.
