# Жёсткий enforcement дизайн-правил (приоритет 0, перекрывает скорость)

## Зачем этот файл существует

История 2026-05-20: пользователь обнаружил **3 одновременных нарушения** [design-quality.md](design-quality.md) на онбординг-экранах мастера, плюс inline-hex в `role.tsx`, плюс баги «Завершить» молчит, лаг при заходе в профиль. Цитата:

> «Когда ты создаешь новые экраны, я заметил, там бывает очень много ошибок по дизайну. То есть легко относишься к дизайну, много ошибок допускаешь.»

Это **системный сбой**: правила [`design-quality.md`](design-quality.md) существовали, в них прямо были §G «никаких subtitle под H1», §B «никаких inline hex», §D «только Phosphor», но они **не enforce'ились**. Агенты их читали, но не проверяли каждый раз перед закрытием UI-задачи.

Этот файл — **жёсткий протокол** который ОБЯЗАН прогоняться **перед каждым закрытием UI-задачи**, без исключений.

## Триггер

Правило применяется к **любой** правке/созданию файла, который:

- Лежит в `app/**/*.tsx` (любой экран).
- Лежит в `src/components/**/*.tsx` (компоненты).
- Лежит в `src/features/**/*.tsx` (feature components, screens, sheets).
- Содержит JSX/RNW UI-элементы (View, Pressable, Text, AppText, формы).

**Не применяется** к hooks (`use-*.ts`), schemas (`*-schema.ts`), libs (`src/lib/`), миграциям (`supabase/migrations/`).

## 🚨 Новый экран — создаётся ТОЛЬКО через роль дизайнера (приоритет 0, обязательно)

Запрошено владельцем продукта 2026-05-23: «любая новая страница, которая создаётся, должна создаваться дизайнером».

**Правило.** Любой **новый экран / новая страница** создаётся **только** через роль `xtrud-designer` (Agent с `subagent_type=xtrud-designer`), а не напрямую правками в диалоге. Это не «по возможности» и не «желательно» — это обязательное условие. Самостоятельно (без роли дизайнера) создавать новый экран **запрещено**.

### Что считается «новым экраном»

- Новый route-файл в `app/**` (новый `*.tsx`-экран, новый сегмент навигации).
- Новый full-screen компонент (экран целиком), даже если он не отдельный route — например, новый шаг wizard'а, новый под-экран.
- Новый крупный self-contained UI-блок уровня экрана: bottom-sheet / modal с собственной формой, новый таб, новый empty / onboarding / success-экран.

### Что НЕ требует роли дизайнера

- Правки и редизайн **существующего** экрана (для них действует обычный enforcement этого файла + design-quality; роль дизайнера — по триггерам из CLAUDE.md, но не обязательна на каждую мелочь).
- Маленький переиспользуемый компонент внутри существующего экрана (кнопка, чип, строка списка), если это не самостоятельный экран.
- Чистый не-UI код (hooks, schemas, libs, миграции).
- Правка текста / цвета / отступа / иконки на существующем экране.

### Процесс

1. Получив задачу «создай экран X» / «новая страница» / «добавь экран» — **сразу** вызвать `xtrud-designer` с полным брифом (что за экран, где живёт, какие данные показывает, обе темы).
2. Роль дизайнера гарантированно делает: Lazyweb-референсы → проектирование в обе темы → 8 grep-чеков → финальные скриншоты → отчёт простым языком.
3. После возврата роли — родительский агент сверяет реальные изменения (diff, `tsc`, grep-чеки) прежде чем отчитаться «готово».

### Запрещено

- ❌ Создать новый экран напрямую правками файлов, минуя роль дизайнера, «чтобы быстрее».
- ❌ Спрашивать «делать через дизайнера или самому?» — по умолчанию **всегда** через дизайнера.
- ❌ Отчитаться «создал экран» без строки в отчёте «создано через роль дизайнера: <бриф>».

См. также CLAUDE.md §«Как вызвать роль дизайнера» и [`lazyweb-rules.md`](lazyweb-rules.md).

## Обязательный grep-чек (прямо перед закрытием задачи)

Прогоняй **все 8 grep-команд** на изменённых файлах. Любой матч — баг, исправь до закрытия.

```bash
# 1. SUBTITLE ПОД H1 (правило §G) — самая частая ошибка.
#    Patterns: AppText сразу после H1 с текстом-помощником в muted/body цвете.
git diff --cached --name-only | grep -E "\\.(tsx)$" | xargs grep -nE "text-(body|muted|caption).*mt-(1|2|3)" 2>/dev/null

# 2. INLINE HEX (правило §B). Любой #ffffff, #000000 и т.п. в JSX.
git diff --cached --name-only | grep -E "\\.(tsx)$" | xargs grep -nE 'color="#[0-9a-fA-F]{3,8}"|backgroundColor:\s*"#' 2>/dev/null

# 3. LUCIDE ИКОНКИ В НОВОМ КОДЕ (правило §D). Phosphor only.
git diff --cached --name-only | grep -E "\\.(tsx)$" | xargs grep -nE "from\s+\"lucide-react-native\"" 2>/dev/null

# 4. ШРИФТ < 12px (правило §C). caption-xs запрещён в новом коде.
git diff --cached --name-only | grep -E "\\.(tsx)$" | xargs grep -nE "text-caption-xs|fontSize:\s*(10|11)\b" 2>/dev/null

# 5. ПУСТОЙ onPress / Alert «Скоро» (правило §F).
git diff --cached --name-only | grep -E "\\.(tsx)$" | xargs grep -nE 'onPress=\{\(\)\s*=>\s*\{\}\}|Alert\.alert\("Скоро"' 2>/dev/null

# 6. bg-primary БЕЗ text-on-primary (правило §A — кнопка с невидимым текстом).
git diff --cached --name-only | grep -E "\\.(tsx)$" | xargs grep -nE "bg-primary" 2>/dev/null | grep -v "text-on-primary"

# 7. ScreenHeader с subtitle (правило §G ещё раз).
git diff --cached --name-only | grep -E "\\.(tsx)$" | xargs grep -nE "ScreenHeader[^>]+subtitle=" 2>/dev/null

# 8. BottomSheet с subtitle (правило §G ещё раз).
git diff --cached --name-only | grep -E "\\.(tsx)$" | xargs grep -nE "BottomSheet[^>]+subtitle=" 2>/dev/null
```

Если хоть один grep вернул матч — **не закрывать задачу**, исправить.

## Обязательный preview-чек (если экран рендерится в браузере)

После каждой UI-правки на экране, который реально открывается:

1. **`preview_list`** — серверid берём.
2. **`preview_eval`**: `window.location.reload()` → подождать → `document.body.innerText.slice(0,500)` — убедиться что текст из правки виден.
3. **`preview_screenshot`** — посмотреть глазами.
4. **Сравнить с design-quality.md §G** — title есть? subtitle под ним есть? Если есть subtitle — **баг, исправить**.
5. **Сравнить с пользовательским дизайн-эталоном** (Vercel/Linear/Stripe — минимализм, один primary action, тонкие hairlines, чистая типографика).

**Не закрывать задачу пока скриншот не подтверждает финальный вид.** Не «у меня TS прошёл, значит ок». TS не ловит subtitle.

## Lazyweb-чек (для новых экранов и существенных редизайнов)

Прописано в [`lazyweb-rules.md`](lazyweb-rules.md). Здесь — повторно для усиления:

- **До написания UI-кода** на новом экране: 1–3 запроса в Lazyweb с конкретным описанием.
- В отчёте: «Lazyweb-запрос: `<запрос>`, посмотрел N экранов, переиспользовал паттерны A/B, осознанно делаю иначе C».
- **Если новый экран сделан без Lazyweb** — это нарушение, исправлять.

Когда **не** требуется: тривиальная правка (1 строка, цвет токена, отступ), баг-фикс существующего экрана без redesign.

## Чёрный список фраз в отчётах

Запрещены фразы которые маскируют недосмотр:

- ❌ «Сделано, не запускал в preview» (если экран рендерится — обязан запустить).
- ❌ «По дизайну как было, не трогал» (если оригинал нарушал rules — обязан был починить).
- ❌ «Минимальный вариант, потом доработаю» (никаких MVP-стиля).
- ❌ «Subtitle я оставил, его специально просили» (subtitle запрещён без письменного user-override).

## Сверка с design-quality.md

Перед закрытием UI-задачи ОБЯЗАН прогнать `Pre-commit чек-лист (10 секунд)` из [`design-quality.md`](design-quality.md) §"Pre-commit". 7 пунктов. Все 7 = pass. Хоть один fail = баг.

## Что делать когда нарушение обнаружено

1. **Не закрывать задачу.** Исправить до отчёта.
2. **Добавить в отчёт** в раздел «🔧 Побочные изменения» строку: «design-quality §X violation в `<file>` — исправлено в этом же коммите». Это создаёт audit trail.
3. **Если нарушение системное** (то же повторяется в 3+ местах) — добавить новый grep в раздел «Обязательный grep-чек» выше.

## Цена нарушения

Каждый раз когда user находит дизайн-баг в моих правках:
- Доверие пользователя падает.
- Я заставляю user делать работу QA, который у нас нет.
- Перед демо это блокер: пользователь не покажет продукт где видны artefacts.

**Дизайн — не «потом доработаем». Это часть «сделано».**
