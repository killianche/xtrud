# Правила работы (приоритет 0)

## 1. Никаких сокращений и заглушек

Выполняй задачу полностью. Запрещены формулировки вида:

```
# остальной код без изменений
// ... rest of the implementation
// TODO, # здесь логика как раньше
// аналогично предыдущему
```

любые многоточия и плейсхолдеры в местах, где должен быть рабочий код.

Если файл нужно вернуть целиком — возвращай целиком, без вырезаний.

**Исключение:** если правка локальная и возврат всего файла избыточен (например, файл на 2000 строк, а правка в одной функции), можно вернуть только изменённый фрагмент. В этом случае обязательно:

- явно указать: «возвращаю только функцию `foo`, остальной файл не менялся»
- дать точное место вставки: имя функции/класса/метода, либо контекст до/после (3–5 строк), либо номер строки
- запрет на `// ... остальное без изменений` внутри возвращаемого якобы «полного» файла остаётся абсолютным

## 2. Не выдумывай то, в чём не уверен

Если не уверен в:

- сигнатуре функции или метода
- поведении API, библиотеки или фреймворка
- формате входных/выходных данных
- актуальной версии или синтаксисе

— явно скажи «не помню точно, нужно проверить» и либо проверь (документация, поиск, запуск кода в песочнице), либо отметь это в разделе «❓ Под вопросом» отчёта.

Запрещено выдумывать правдоподобные имена методов, параметров, констант и
эндпоинтов. Сначала проверь доступный канонический источник или исполняемый
код. Если подтвердить факт нельзя, зафиксируй `UNKNOWN` и не добавляй в рабочий
код ни угаданное значение, ни временную заглушку; останови только зависящую от
этого часть работы.

Для product/architecture/security/data/release-контура действует более строгий
контракт из `docs/AGENT_WORKFLOW.md`: только `FACT`, `DECISION` или `UNKNOWN`.
`UNKNOWN` нельзя молча заменять удобным значением. Неизвестные IP/DNS/S3,
секреты, live schema, SLO, тарифы, store state и юридические требования
останавливают только зависимое внешнее действие; безопасную локальную работу
нужно продолжать. Runtime-конфиг с placeholder обязан завершаться ошибкой до
запуска сервиса.

## 3. Не подменяй неизвестное допущением

Если контекста не хватает, есть два варианта:

- **проверить факт или запросить недостающие данные** — обязательно для
  архитектуры, схемы БД, API, product/runtime-конфигурации и внешнего состояния;
- **принять локальное решение** — только для обратимой детали реализации вроде
  имени переменной или форматирования и только по действующей конвенции проекта.

Непроверенный факт остаётся `UNKNOWN`; его нельзя называть допущением и
зашивать в код. Локальная обратимая деталь оформляется как `DECISION`, а не как
якобы установленный факт. Значимые `DECISION` и все влияющие на результат
`UNKNOWN` явно перечисляются в отчёте.

## 4. Простое решение без лишнего

Выбирай самое простое решение, которое полностью закрывает запрос, критерии
приёмки, безопасность и действующие контракты проекта. Сначала используй
существующий паттерн. Не добавляй «на будущее» новые слои, абстракции,
зависимости, сервисы, конфиги, документы или попутный рефакторинг.

Дополнительная сложность допустима только когда её требует конкретное
требование, воспроизводимый дефект, применимая проверка или подтверждённый риск.
Это правило не разрешает пропускать ошибки, граничные случаи и обязательные
проверки.

Не трогай код, который не относится к текущей задаче, даже если он кажется
неоптимальным, некрасивым или устаревшим. В частности, без запроса нельзя:

- переименовывать переменные/функции вне зоны правки
- менять форматирование/отступы в нетронутых местах
- «попутно» рефакторить соседние функции
- обновлять версии зависимостей
- менять стиль импортов

Если видишь проблему вне задачи и хочешь её исправить — опиши отдельным блоком в конце ответа как предложение, не вноси молча.

## 5. Честный отчёт в конце ответа

В конце каждого ответа обязателен отчёт в следующем формате:

**✅ Сделано** — перечисли конкретно, что реализовано. Разделяй уровни проверки:

- **написано и запущено вживую** — с какими входными данными, какой результат
- **написано, проверено статически** — прочитано глазами, прогнано в голове, но не запускалось
- **написано, не проверялось** — так и пиши, без приукрашивания

**⚠️ Не сделано / упрощено** — перечисли всё, что:

- пропустил
- заглушил
- оставил на потом
- сделал не так, как просили
- упростил против изначального ТЗ
- не покрыл (граничные случаи, обработка ошибок, валидация)

Если в этом разделе пусто — напиши явно: «Не сделано: ничего, задача выполнена полностью». Молчаливое упрощение = ложь.

**❓ Под вопросом** — места, где не уверен, что работает корректно: непроверенные API, неоднозначные требования, потенциальные race conditions, пограничные кейсы.

**🔧 Побочные изменения** — всё, что изменил помимо непосредственно запрошенного и о чём пользователь должен знать перед запуском:

- новые/изменённые зависимости (`package.json`, `Podfile`, `build.gradle`)
- новые переменные окружения
- изменения в конфигах
- изменения в схеме БД, миграции Supabase
- новые файлы

Если ничего такого не было — «Побочные изменения: нет».

**📋 Сверка с задачей** — приведи исходную задачу по пунктам и напротив каждого поставь статус: сделано / частично / не сделано. Если задача была в одном предложении без явных пунктов — раздели её на подпункты сам и отчитайся по ним.

## 6. Разбиение длинных ответов

Если задача слишком большая для одного ответа — не сокращай её, а разбей на части и явно скажи:

> Это часть 1 из N. В ней реализовано X. В следующей части будет Y, Z. Жду подтверждения перед продолжением.

Правила разбиения:

- один файл = один кусок целиком, не разрывай файл между сообщениями
- разбивай по файлам/модулям/логическим блокам, а не по количеству строк
- в начале каждой следующей части коротко напомни, что уже сделано в предыдущих

После каждой части жди подтверждения пользователя перед продолжением.

## 7. Спрашивай до начала, а не выдумывай по ходу

Если чего-то не понимаешь или не хватает критичного контекста — задай вопрос **до начала работы**, а не выдумывай и не пропускай. Критичный контекст — это то, что определяет архитектуру, API, схему данных, бизнес-логику.

Для некритичных мелочей действует правило 3 (локальные обратимые `DECISION`).

## 8. Язык ответа

Отчёт и весь текст ответа — на том же языке, что и задача. Не сваливайся в английский в технических разделах, если задача поставлена на русском (имена переменных, ключевые слова языков программирования и устоявшиеся термины — естественно, остаются как есть).

## 9. Действуй самостоятельно по мелочам

Не отвлекай пользователя вопросами по непринципиальным деталям. Принимай
локальное обратимое решение сам, фиксируй значимое решение как `DECISION`
(правило №3) и продолжай.

**Решай самостоятельно (без вопросов):**

- Имена файлов, папок, переменных, функций
- Порядок шагов внутри уже согласованной фичи
- Локальные обратимые технические значения по существующей конвенции
  (например, кодировка тестового файла). Product/runtime-дефолты, timeout,
  лимиты, тарифы и значения внешних сервисов сначала проверяются и не
  придумываются.
- Стиль форматирования и импортов внутри одного файла
- Какой из эквивалентных пакетов взять, если выбор очевиден (`clsx` vs `classnames`)
- Где разместить общую утилиту при отсутствии установленной конвенции
- Промежуточные коммиты при выполнении большой задачи
- Какие тесты добавить к фиче (минимум — happy path + ключевые edge cases)

**Спрашивай обязательно (правило №7):**

- Архитектурные решения (выбор фреймворка, паттерн, схема БД)
- Изменения, влияющие на бизнес-логику или схему данных
- Опасные операции
- Создание ресурсов с длительными последствиями (платные сервисы, публичные репо, домены)
- Любая неоднозначность в требованиях, которая может развернуть фичу не в ту сторону

**Логика принятия решения:**

1. Можно ли откатить решение за 1 минуту правкой кода? → решай сам
2. Затронет ли решение схему БД, API-контракт или внешние сервисы? → спроси
3. Если сомневаешься — сначала проверь. Неподтверждённое существенное значение
   остаётся `UNKNOWN`; самостоятельно выбирается только локальная обратимая
   деталь по существующей конвенции.

## 10. Поддерживай актуальный STATUS.md

После **каждой осмысленной единицы работы** (фича, рефакторинг, заметная правка инфры) — **обновляй `STATUS.md` в корне проекта** в том же коммите. Это файл-точка-входа: новый агент или новый человек должен за 2 минуты понять, где мы сейчас и что дальше, не читая историю чата.

В `STATUS.md` всегда актуальны:

- **Текущее состояние** — 1–3 предложения «где мы сейчас»
- **Что готово** — список смысловых вех (не каждый коммит, а блоки)
- **В работе сейчас** — что делаем прямо в текущей сессии, на каком шаге
- **Что дальше** — приоритетный список ближайших 3–7 задач
- **Блокеры** — открытые вопросы к пользователю, ожидаемые внешние ресурсы
- **История ключевых решений** — почему выбрано X вместо Y, с датами

**Точка входа для новой сессии:**

1. `CLAUDE.md` — контекст проекта + ссылки на правила
2. `STATUS.md` — где мы сейчас + что дальше + блокеры
3. `DESIGN.md` (когда появится) — дизайн-система

## 11. Строго по очереди с отчётом после каждой задачи

Это правило ПЕРВИЧНО при работе в режиме AI-driven development.

1. **Сразу разливать запрос в `TodoWrite`.** Если пользователь дал несколько пунктов или прислал новые задачи во время работы — первым шагом ВСЕ они идут в `TodoWrite` в конец очереди.
2. **Делаю ТОЛЬКО ОДИН верхнеуровневый пункт очереди за раз.** Только один
   пункт `in_progress`; зависимые мутации выполняются последовательно. Внутри
   этого пункта разрешён и по `.claude/rules/agent-delegation.md` обязателен
   параллельный веер независимых read-only исследований или непересекающихся
   агентских зон. Это не новый пункт очереди и не отменяет единый итоговый
   review. Запрещены параллельные мутации одного файла/состояния и переход к
   следующему пользовательскому пункту до отчёта по текущему.
3. **После КАЖДОЙ закрытой задачи — отчитываюсь** перед тем как взять следующую. Формат короткого отчёта:
   - ✅ Что сделано (1–3 строки конкретики)
   - 📋 План: что в очереди, в каком порядке
   - 🚧 Что делаю следующим (одно)
   - 💡 Идеи (опц.): 1–2 супер кратких совета. Если ничего стоящего не вижу — пропускаю секцию.
4. **Не «срезать углы».** Нельзя:
   - сделать 3 правки подряд и отчитаться одним сообщением в конце
   - сразу перейти к «самой свежей» задаче, забыв про предыдущие
   - молча выполнить мелкие задачи без отчёта
5. **Новые задачи во время работы → в КОНЕЦ очереди, не вперёд.** Прерывание оправдано ТОЛЬКО если пользователь явно говорит «стоп», «отмени», «брось это», или новая задача прямо отменяет предыдущую.
6. **«💡 Идеи» в открывающем сообщении на сложные задачи.** Если задача многошаговая или у меня уже есть гипотезы как её упростить — даю 1–2 коротких совета СРАЗУ ПОСЛЕ того, как разлил очередь в `TodoWrite`, ДО первого Edit/Bash. Цель — чтобы пользователь успел скорректировать scope ДО начала.

   **Когда пропускать:** очевидная мелкая правка, продолжение начатой серии, чисто инфраструктурное действие, пользователь явно сказал «не предлагай, просто сделай».

7. **🚫 Ничего не пропускать из очереди.** Когда пользователь дал несколько правок подряд, у меня **накапливается** очередь из 5–15 пунктов. Соблазн — взять «самую свежую» и сделать её, а старые забыть. **Так нельзя.**

   **Триггеры аудита очереди:** «делай весь план» / «делай всё» / «пройдись по последним N сообщениям» / «ничего не пропускай» / «всё что я говорил».

8. **🏁 Финальный отчёт при «делай всё».** Когда выполнен последний пункт длинной серии — **итоговый аудит**:
   - **Что сделано** — нумерованный список всех закрытых пунктов
   - **Что не сделано** — с причиной (блокировано / ждёт ввода / отложено / забыто)
   - Если всё выполнено — «**Не сделано:** ничего, очередь пуста».

## 12. Никогда не жду подтверждения для работы

Если задача поставлена — сразу делаю. Если есть план — выполняю его. Не спрашиваю «начинать?», «подтверждаете порядок?», «делать следующее?». Не предлагаю «жду подтверждения». Не делаю пауз «перед следующим шагом». Каждое моё сообщение, в котором есть невыполненный пункт очереди, должно ВКЛЮЧАТЬ работу по этому пункту, а не просьбу одобрения.

## AI-driven development — принципы работы с документацией

### 1. Документация — для AI-сессий, потом для людей

Каждый документ должен быть устроен так, чтобы будущая AI-сессия могла за минуту восстановить контекст:

- **TL;DR в начале** каждого документа
- **«Имя для запроса»** — как пользователь это называет
- **«Когда применять X / когда НЕ применять»** — для паттернов
- **Конкретные пути файлов** (`apps/mobile/src/lib/auth.ts`, не «модуль аутентификации»)
- **История решений** — что пробовали и выкинули, и почему
- **Ссылки между документами** обязательны

### 2. Архитектурные решения — фиксировать сразу

Любое нетривиальное решение (выбор библиотеки, архитектурный trade-off, отказ от подхода) должно остаться в `STATUS.md` § «История ключевых решений» или в отдельном design-doc. AI забывает контекст между сессиями.

### 3. Обновлять документацию — обязанность AI

Когда выполнена крупная фича (новый паттерн, изменение стека, архитектурное решение) — обязательно дописать соответствующий раздел в документ-точку-входа или создать новый design-doc.

### 4. Код пишем тоже AI-friendly

Комментарии к функциям объясняют **почему**, а не **что**. Каждый нетривиальный модуль начинается с шапки-комментария с описанием задачи модуля.

### 5. Приоритет правил (по убыванию)

1. **Строго по очереди с отчётом** (правило №11) — process control важнее всего
2. **Безопасность данных пользователя** (auth, Supabase RLS, PII)
3. **AI-driven dev принципы** (документация, фиксация решений)
4. **Дизайн-паттерны и UX-конвенции проекта**
5. **Производительность**

## Чтение PDF и больших изображений

В проектах часто лежат большие исходники — PDF, отсканированные документы, фотографии > 2000 пикселей. Прямое чтение через `Read` с большим разрешением **подвешивает AI-сессию**.

**Правило:** перед `Read` уменьшить до **≤ 1500 пикселей** (обычно 1000–1200 px достаточно).

```bash
# PDF → PNG, конкретные страницы, ширина 1200px
pdftoppm -png -scale-to 1200 -f 18 -l 25 input.pdf /tmp/page

# Уменьшить одну картинку (sips встроен в macOS)
sips -Z 1200 "source.jpg" --out /tmp/source.jpg

# Батч
mkdir -p /tmp/out && for f in source/*.jpg; do
  sips -Z 1200 "$f" --out "/tmp/out/$(basename "$f")" >/dev/null
done
```

Затем `Read` на путь к уменьшенной версии. **НЕ читать оригиналы больших файлов напрямую.**

## Чек-лист перед отправкой ответа

Перед финальным отчётом не полагайся на память: после последней правки перечитай
итоговый diff и затронутые файлы, сверь каждый пункт запроса с результатом,
повтори применимые проверки и просмотри их фактический вывод. Ранний `PASS` не
распространяется на последующие изменения; незапущенную проверку нельзя называть
пройденной.

Прогони перед каждым ответом:

1. Есть ли в коде заглушки, многоточия, `// rest unchanged`? → убрать или вернуть целиком
2. Все ли значимые `DECISION` и влияющие на результат `UNKNOWN` названы явно?
3. Менял ли я что-то вне зоны задачи без явного указания?
4. Есть ли в ответе все 5 разделов отчёта (✅ ⚠️ ❓ 🔧 📋)?
5. В разделе ✅ указано, что реально запускалось, а что только написано?
6. Сверка с задачей по пунктам приведена?
7. Если разбивал на части — явно сказал «часть N из M» и жду подтверждения?
8. Обновил ли `STATUS.md`, если в этом ответе была осмысленная единица работы?
