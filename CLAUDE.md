## Правила работы

Все базовые правила (отчётность, очередь задач, видимые допущения, запрет заглушек, чек-лист) — в [`.claude/rules/working-rules.md`](.claude/rules/working-rules.md). Этот файл подгружается автоматически в каждую сессию.

**Главное в одну строку:** делай ровно одну задачу за раз, отчитывайся после каждой по 5-секционному формату (✅ ⚠️ ❓ 🔧 📋), не выдумывай факты, не трогай то, что не просили.

### 🚨 АВАТАРЫ — ТОЛЬКО DiceBear `shapes`

Для placeholder-аватаров (demo-данные, seed-based fallback, любые сгенерированные) используем **только** `https://api.dicebear.com/9.x/shapes/png?seed=<seed>` — геометрические формы из brand-палитры. См. https://www.dicebear.com/styles/shapes/

**Запрещено:**
- `/avataaars/` — мультяшные люди («детский placeholder», ломает Vercel-эстетику).
- `/personas/`, `/micah/`, `/notionists/`, `/pixel-art/`, `/lorelei/`, `/adventurer/` — любые human-style наборы DiceBear.
- Сторонние cartoon-генераторы (Boring Avatars, RoboHash и т.п.) без явного согласования.

Допустимы: реальные user-uploaded фотографии (через image-picker → Supabase Storage). Если фото нет → инициалы (см. `<Avatar>`) → DiceBear shapes-fallback.

### 🚨 НИКАКИХ ЭМОДЖИ В UI БЕЗ ЯВНОГО РАЗРЕШЕНИЯ

Эмоджи (💧 ⚡ 🔨 🛠️ 🚪 и т.п.) — **не иконки**. Они выглядят как «детский placeholder», ломают Vercel-эстетику и читаются по-разному на разных платформах. Запрещено использовать их в UI как замену иконкам категорий, статусов, кнопок, badges.

Когда нужны цветные/современные/минималистичные иконки — реализовать через:
- **Lucide React Native** (моно, текущий дефолт) + tinted background (как в FeaturedRequests)
- **Iconify CDN** с конкретным курированным сетом (`flat-color-icons`, `fluent-color`) — согласовать сет с пользователем перед интеграцией
- **AI-generated SVG** — через external image-gen pipeline (DALL-E / SDXL), сохранять в репо, не CDN

Эмодзи допустимы только в **текстовом контенте** (тексты заданий пользователя, copy кнопок типа «Ваш номер скрыт 📵» если запрошено), но никогда как замена visual-icon.

### 🚨 КРИТИЧЕСКОЕ ПРАВИЛО: ОЧЕРЕДЬ ЗАДАЧ — НИЧЕГО НЕ ПРОПУСКАТЬ

Когда пользователь присылает 5–10 задач подряд (одно сообщение или серия) — нарушение правил:
- ❌ выполнить только последнюю задачу
- ❌ выполнить «самые важные», остальное забыть
- ❌ ответить на одну задачу и проигнорировать остальные
- ❌ «отложить» задачу без явного согласования с пользователем

**Обязательное поведение:**

1. **СРАЗУ разлить ВСЕ задачи в `TodoWrite`** — даже если их 10. Каждая отдельным пунктом, в конец очереди.
2. **Делать строго по одной** в порядке поступления. Никаких перескоков, никаких «сразу к самой свежей».
3. **После каждой закрытой — короткий отчёт** перед тем как взять следующую (формат из working-rules.md правило №11).
4. **Ничего не «забывать»** — если задача уходит в pending без выполнения, в финальном отчёте явно написать почему (заблокировано / ждёт scope / отменено пользователем).
5. **Финальный аудит** при триггерах «делай всё», «ничего не пропускай», «пройдись по последним N сообщениям» — нумерованный список выполненного + что осталось с причиной.

**Триггеры аудита очереди:** «делай весь план» / «делай всё» / «пройдись по последним N сообщениям» / «ничего не пропускай» / «всё что я говорил» / «все задачи за последние X сообщений».

Это правило ПЕРВИЧНО — нарушение = потеря доверия пользователя. Длинная честная серия отчётов всегда лучше одного «выполнил самое нужное».

### Формат краткого отчёта в конце ответа

Каждый ответ обязан заканчиваться коротким финальным блоком:

- **Что сделано** — конкретные пункты, без воды.
- **Что не сделано** — пропущенное / упрощённое / отложенное. Если пусто — пиши «нет».
- **Дальше** — следующая задача, которую беру сам, либо короткий план на ближайшие шаги. Если работа окончена и продолжать нечего — раздел не пишется.
- **Вопросы / решения от тебя** — только если они реально нужны. Если их нет — раздел не пишется вовсе (не указывай «вопросов нет», просто опусти секцию).

Этот короткий блок дополняет, а не заменяет полный 5-секционный отчёт (✅ ⚠️ ❓ 🔧 📋) из working-rules.md. Полный отчёт обязателен после осмысленной единицы работы; короткий блок — после **любого** ответа.

## Критические правила инфраструктуры

### №1: где живёт код

Исходный код живёт **ТОЛЬКО** в `~/Desktop/xtrud/` (или будущей переименованной папке проекта). Не в `/tmp`, не в `/var/tmp`, не «внутри Docker-образа».

Если setup или туториал говорит работать в `/tmp` — игнорируй, работай в папке проекта.

### №2: git с первой минуты

В этой папке обязан быть инициализирован git и настроен remote на GitHub. Проверь первым делом:

```bash
git status
git remote -v
```

Если git не инициализирован — инициализируй немедленно (`git init && git branch -M main`) и создай `.gitignore`. Если remote не настроен — спроси пользователя один раз в начале и настрой. **Не работай без remote.**

Минимум в `.gitignore`:

```
node_modules/
dist/
build/
.expo/
.next/
ios/Pods/
android/.gradle/
.env
.env.local
*.log
.DS_Store
```

### №3: коммиты и push

После каждой осмысленной единицы работы (новая фича, баг-фикс, рефакторинг):

```bash
git add <конкретные файлы>
git commit -m "осмысленное сообщение"
git push
```

Не накапливай несделанные коммиты. Больше часа работы без коммита — стоп и закоммить промежуточный результат.

**Не используй `git add .` / `git add -A`** — это риск зацепить `.env`, секреты, артефакты сборки. Добавляй конкретные файлы.

### №4: опасные операции — спрашивай

Перед `rm -rf`, `git reset --hard`, `git push --force`, удалением папок, миграциями БД с потерей данных — **спроси подтверждение у пользователя** и убедись, что текущее состояние закоммичено и запушено.

### №5: безопасность Supabase

- **Secrets** (service_role key, DB password) — только в `.env.local` и GitHub Secrets, никогда в коде, никогда в публичных переменных Expo/Next (`EXPO_PUBLIC_*`, `NEXT_PUBLIC_*`)
- **RLS включён на каждой таблице** с пользовательскими данными. Без исключений
- Миграции — через файлы в `supabase/migrations/`, не правкой схемы вручную в дашборде

## Чек-лист перед началом любой работы

1. `pwd` показывает `~/Desktop/xtrud/`?
2. `ls -la .git` — есть `.git` папка?
3. `git remote -v` — есть remote на GitHub?
4. `git status` — все изменения с прошлой сессии закоммичены?
5. Прочитан `STATUS.md` — понятно, где мы остановились?

Если хоть один пункт не выполнен — **сначала исправь это**, потом работай.

## Порядок чтения для новой AI-сессии

Не пытайся прочитать всё. Минимальный набор по типу задачи:

1. **Всегда первым** — `CLAUDE.md` (этот файл, 2 мин). Здесь контекст проекта + ссылки.
2. **Всегда вторым** — `STATUS.md` (3 мин). Где мы сейчас, что в работе, блокеры. Это самый свежий документ.
3. **Если задача функциональная** (новый экран, фича, бизнес-логика) — `PROJECT_MAP.md` (карта продукта) + `PRODUCT_CONTEXT.md` (1-страничный бриф).
4. **Если задача UI/UX** — `DESIGN.md` (токены, цвета, типографика) + `CROSS_PLATFORM_RULES.md` (правила вёрстки iOS/Android/web).
5. **Если задача про БД/таксономию** — `CATEGORIES_AND_PROFILES.md` (схема, 64 L2 категории).
6. **Если задача про конкурентный анализ** — `COMPETITOR_INSIGHTS.md` + `PRODUCT_BLINDSPOTS.md`.
7. **Если меняешь wizards/UX-flow** — `AUDIT_2026-05-12.md` (113 UX-проблем + рекомендации).

Историческое (читать только если нужен контекст ранних решений) — папка `legacy/`.

## Внешние инструменты для дизайна

**Lazyweb MCP** — библиотека из 1000+ референс-экранов реальных приложений. Установлен как плагин Claude Code (`lazyweb@lazyweb`). Перед проектированием или существенным редизайном любого UI-экрана **обязательно** сходи в Lazyweb за референсами. Правила использования — в [`.claude/rules/lazyweb-rules.md`](.claude/rules/lazyweb-rules.md).

Токен лежит в `~/.lazyweb/lazyweb_mcp_token` (вне репозитория). В git не коммитим.

Новые правила (например, `supabase-rules.md`, `mobile-rules.md`) добавляются как отдельные файлы в `.claude/rules/` с `paths:` frontmatter, чтобы подгружаться только когда работаем в соответствующих папках.
