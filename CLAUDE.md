## TL;DR

- **Проект:** **xtrud** — маркетплейс услуг (мастера ↔ клиенты) для Республики Ингушетия. Полный бриф о продукте и функциональных референсах — в [`PRODUCT_CONTEXT.md`](PRODUCT_CONTEXT.md).
- **Платформы:** web-сайт + мобильное приложение для iOS и Android (одна кодовая база)
- **Бэкенд:** Supabase (Postgres + Auth + Storage + Edge Functions)
- **Стек фронтенда:** Expo SDK 54 + Expo Router (одна кодовая база web/iOS/Android) + NativeWind 4 + TanStack Query v5 + Zustand + react-hook-form/zod. Иконки — Phosphor.
- **Хостинг кода:** GitHub (обязательно с первой минуты)
- **Темы:** light + dark с переключателем
- **Дизайн:** Vercel-based (`DESIGN.md`, активирована 2026-05-13). 3 override'а под marketplace перечислены в блоке «xtrud overrides» внутри `DESIGN.md`.
- **🎨 UI-паттерны и архетипы экранов:** [`UI_PATTERNS.md`](UI_PATTERNS.md) — единый кук-бук «как делать страницы» (header / list / chip / hero / filters / empty-state). **Перед проектированием любого нового экрана читать первым.**
- **Product scope (MVP):** в каталоге показывается **только L1 `construction`** (Строительство и ремонт). Остальные 9 L1 (Дом и быт, Авто, Бьюти, Образование и т.д.) — скрыты. Управление scope — `IN_SCOPE_L1_IDS` в [`src/lib/product-scope.ts`](src/lib/product-scope.ts). Подробно — `CATEGORIES_AND_PROFILES.md` → раздел «Product scope (MVP)».

## 🧭 Актуальная модель продукта (новым агентам читать ПЕРВЫМ)

Самый частый источник путаницы: старые доки (`PROJECT_MAP.md`, `docs/lifecycle.md`, `docs/chat-states.md`, `docs/order-states.md`) описывают функции, которых **больше нет**. Ниже — как продукт устроен **сейчас** (актуально 2026-05-29). Если док противоречит этому блоку — прав этот блок.

### Как работает (модель «доска объявлений», с 2026-05-20)

1. Клиент создаёт **заказ** (категория, описание, фото до 5, бюджет, срок, отображаемое имя).
2. Мастера видят заказ в ленте и **откликаются** (одно сообщение + цена).
3. Клиент видит отклики (имя мастера, рейтинг, цена, текст) и **сам звонит / пишет в WhatsApp**.
4. Всё. **Номер клиента всегда скрыт** от мастеров — инициатор контакта всегда клиент.

Подробнее и история перехода — [`docs/SIMPLE_FLOW.md`](docs/SIMPLE_FLOW.md).

### Чего в продукте НЕТ (удалено — не возвращать без явной просьбы владельца)

- ❌ **Чат / переписка в приложении** — удалён (UI + БД-таблица сообщений, миграция 0110). Контакт только звонок/WhatsApp.
- ❌ **Lifecycle сделки** — нет «клиент выбрал мастера», «в работе», «подтвердить выполнение». Заказ: open / cancelled / expired (+ draft). Старые RPC (`accept_response` и т.п.) в БД остались, но в UI не вызываются.
- ❌ **Оспаривание (dispute)** — удалено полностью (RPC dropped, миграция 0109).
- ❌ **Рейтинг клиента** — у клиента рейтинга нет (только у мастера). Жалобы на клиента есть, оценок нет.
- ❌ **Email** — никогда (ни auth, ни уведомления). Только телефон. См. инфра-правило №6.
- ❌ **Фамилия** — везде только **имя** (`last_name` пустое/legacy, в UI не показываем и не запрашиваем).

### Что в продукте ЕСТЬ (актуальные фичи)

- ✅ **Auth по телефону** (SMS-OTP). В будущем логин+пароль поверх. Email никогда.
- ✅ **Username** — уникальный публичный `@handle`, задаётся при регистрации, редактируется в профиле.
- ✅ **Срок заказа**: `urgent` / `this_week` / `this_month` / `flexible` + **`by_date`** (точная дата, колонка `orders.preferred_date`, календарь `OrderDateSheet`).
- ✅ **Фото заказа** (до 5) + **отображаемое имя** (дефолт из профиля, можно менять).
- ✅ **Отзывы**: клиент оценивает мастера. Мастер может **обжаловать** отзыв → модератор в `/admin/reports` скрывает (`status='hidden'`). Жалобы — таблица `reports` (target_type `user/order/review/message`).
- ✅ **Рейтинг мастеров** — внутренний балл (умная сортировка), `docs/MASTER_RANKING_PLAN.md`.
- ✅ **Верификация мастера (паспорт)** — `docs/VERIFICATION.md`.
- ✅ **Отслеживание сбоев** — Sentry (`src/lib/sentry.ts`, активен при заданном `EXPO_PUBLIC_SENTRY_DSN`).
- ✅ **Product scope (MVP)**: в каталоге только L1 `construction`.

### Деплой и площадка

- Сайт: **https://xtrud.alanbani.ru/** (VPS). Выкатка — `bash deploy/web.sh` (собирает через `scripts/build-web-local.mjs` → tar/scp на сервер). **Только по явной команде владельца «выкатывай».**

## Правила работы

Все базовые правила (отчётность, очередь задач, видимые допущения, запрет заглушек, чек-лист) — в [`.claude/rules/working-rules.md`](.claude/rules/working-rules.md). Этот файл подгружается автоматически в каждую сессию.

**Главное в одну строку:** делай ровно одну задачу за раз, отчитывайся после каждой по 5-секционному формату (✅ ⚠️ ❓ 🔧 📋), не выдумывай факты, не трогай то, что не просили.

### 🚨 АВАТАРЫ — ИНИЦИАЛЫ (а не DiceBear), решение владельца 2026-05-23

Плейсхолдер-аватар у любого аккаунта без своего фото (и у новых аккаунтов) — **кружок с инициалами имени** (цветной фон по seed + буквы), как в Google / Notion / Linear. Реализован в обоих `<Avatar>` компонентах.

**Единый источник истины — [`src/lib/avatar.ts`](src/lib/avatar.ts) `realAvatarUrl(url)`:** возвращает URL только для настоящего загруженного фото (Supabase Storage). Любая ссылка на `api.dicebear.com` (shapes / avataaars / initials / любая генерёжка) и пустое значение → `null` → UI рисует инициалы. Поэтому demo-аккаунты со старыми shapes-ссылками в БД автоматически показывают инициалы — базу править не нужно.

**Запрещено:**
- Рендерить аватар прямым `<Image>` в обход фильтра. Любой аватар идёт либо через `<Avatar>`, либо через `realAvatarUrl(...)` перед `<Image>`.
- Возвращать DiceBear как плейсхолдер (бывшее правило «только shapes» — **отменено** 2026-05-23).
- Сторонние cartoon-генераторы (Boring Avatars, RoboHash и т.п.).

Допустимы: реальные user-uploaded фотографии (image-picker → Supabase Storage). Нет фото / нет имени → нейтральный кружок с иконкой `User`.

### 🚨 НИКАКИХ ЭМОДЖИ В UI БЕЗ ЯВНОГО РАЗРЕШЕНИЯ

Эмоджи (💧 ⚡ 🔨 🛠️ 🚪 и т.п.) — **не иконки**. Они выглядят как «детский placeholder», ломают Vercel-эстетику и читаются по-разному на разных платформах. Запрещено использовать их в UI как замену иконкам категорий, статусов, кнопок, badges.

Когда нужны современные/минималистичные иконки — реализовать через:
- **Phosphor React Native** (`phosphor-react-native`) — **дефолт для моно UI-иконок** с 2026-05-15. 6 weights (`thin/light/regular/bold/fill/duotone`), активный state `bold→fill`. Полная инструкция и маппинг Lucide → Phosphor в [`docs/UI_ICONS.md`](docs/UI_ICONS.md).
- **Iconify CDN** (`twemoji`, `fluent-color`) — для **цветных** иконок L2-категорий услуг. Маппинг и API в [`docs/ICONS.md`](docs/ICONS.md). Новый сет согласовать с пользователем перед интеграцией.
- **Lucide React Native** — только legacy, в новом коде не использовать. Постепенно мигрируется на Phosphor.
- **AI-generated SVG** — через external image-gen pipeline (DALL-E / SDXL), сохранять в репо, не CDN.

Эмодзи допустимы только в **текстовом контенте** (тексты заданий пользователя, copy кнопок типа «Ваш номер скрыт 📵» если запрошено), но никогда как замена visual-icon.

### 🚨 КРИТИЧЕСКОЕ ПРАВИЛО: ОЧЕРЕДЬ ЗАДАЧ — НИЧЕГО НЕ ПРОПУСКАТЬ

Когда пользователь присылает 5–10 задач подряд (одно сообщение или серия) — нарушение правил:
- ❌ выполнить только последнюю задачу
- ❌ выполнить «самые важные», остальное забыть
- ❌ ответить на одну задачу и проигнорировать остальные
- ❌ «отложить» задачу без явного согласования с пользователем

**Обязательное поведение:**

1. **СРАЗУ разлить ВСЕ задачи в `TodoWrite`** — даже если их 10. Каждая отдельным пунктом, в конец очереди.
2. **Делать строго по одной** в порядке поступления. Никаких перескоков, никаких «сразу к самой свежей».
3. **После каждой закрытой — короткий отчёт** перед тем как взять следующую (формат из working-rules.md правило №11).
4. **Ничего не «забывать»** — если задача уходит в pending без выполнения, в финальном отчёте явно написать почему (заблокировано / ждёт scope / отменено пользователем).
5. **Финальный аудит** при триггерах «делай всё», «ничего не пропускай», «пройдись по последним N сообщениям» — нумерованный список выполненного + что осталось с причиной.

**Триггеры аудита очереди:** «делай весь план» / «делай всё» / «пройдись по последним N сообщениям» / «ничего не пропускай» / «всё что я говорил» / «все задачи за последние X сообщений».

Это правило ПЕРВИЧНО — нарушение = потеря доверия пользователя. Длинная честная серия отчётов всегда лучше одного «выполнил самое нужное».

### 🚨 КРИТИЧЕСКОЕ ПРАВИЛО: НИКАКИХ МИНИМАЛЬНЫХ ВАРИАНТОВ И СОКРАЩЕНИЙ

Любая задача выполняется **полноценно**, до production-ready состояния. «Минимальное жизнеспособное решение» / «v1» / «пока хватит» — **запрещены** без явной просьбы пользователя.

**Запрещено:**
- ❌ Самовольно делать «упрощённую версию» / «минимальный вариант» / «MVP-первый шаг», когда задача предполагает полноценную реализацию.
- ❌ Оставлять stub'ы, half-finished компоненты, hardcoded const'ы вместо БД-таблицы, прохолост-логику «доделаю потом».
- ❌ Выбирать «самое импактное» из нескольких частей задачи и игнорировать остальные («сделаю A, B/C — отложу»).
- ❌ Оправдывать минимализм формулировками «это серьёзная переработка», «слишком большая работа», «оставлю на следующую сессию», «scope-decision», «осознанно сократил».
- ❌ В отчёте писать «**Не сделано / упрощено:** не делал X, Y, Z потому что minimal scope / не критично / можно потом» — если пользователь не давал такого scope-guardа.
- ❌ Когда есть **reference-реализация** в другом проекте (Ingush-Business, Profi.ru, TaskRabbit, конкурент) — делать ниже её уровня. Если у них bottom-sheet с иерархией — у нас тоже bottom-sheet, не chip-row.
- ❌ Спрашивать «делать полную версию или минимальную?» — по умолчанию **всегда полная**.

**Обязательное поведение:**

1. **Полная реализация = всё что нужно для production-ready фичи:**
   - UI-слой (включая bottom-sheets / modals / animations если нужны — не только plain chip-row)
   - Data-слой (миграция БД, таблица, индексы, RLS — если архитектурно правильно, не hardcoded const)
   - Все потребители (все экраны, где отображается / редактируется эта сущность)
   - Edge cases (empty / loading / error / dark theme / disabled / RTL)
   - Типы (regenerate после миграции, не точечные правки)

2. **Объём работы — не повод сокращать.** Если задача требует 5 файлов + миграция + новый компонент — делать все 5 файлов + миграцию + компонент. Если это больше одной сессии — разбить на части (правило №6 working-rules.md), сообщить «часть N из M», но **каждая часть** должна быть полноценной, не stub'ом.

3. **«Минимальный» / «временный» / «только UI» путь только когда пользователь явно сказал:**
   - «сделай быстро», «временно», «только UI», «только seed», «hardcoded пока», «без миграции» — тогда можно минимально.
   - Без этих фраз = **полная версия** по умолчанию.

4. **Reference-сравнение.** Если в кодовой базе конкурента / соседнего проекта (включая Ingush-Business при ссылке на него), в Lazyweb-выдаче, в Profi.ru / TaskRabbit / Thumbtack фича реализована глубже — **делать на их уровне или выше**, не ниже.

5. **Поведение при неуверенности.** Если кажется что часть задачи «можно отложить» — задать вопрос пользователю **до начала** (правило №7), не вырезать молча. Лучше явный вопрос «делаем bottom-sheet + миграцию БД + новый компонент?» чем тихий минимализм.

**Это правило ПЕРВИЧНО** для дизайна, архитектуры, UX-задач. Триггер на самопроверку — каждый раз, когда хочется написать в отчёт «оставил вне scope», «не критично сейчас», «scope-decision»: остановиться и сделать.

### 🚨 КРИТИЧЕСКОЕ ПРАВИЛО: ENFORCEMENT ДИЗАЙН-ПРАВИЛ (приоритет 0)

История 2026-05-20: пользователь обнаружил **3 одновременных нарушения** [`design-quality.md`](.claude/rules/design-quality.md) на онбординг-экранах мастера (subtitle под H1 на 4 экранах, inline-hex в role.tsx, плюс баги submit/auth). Цитата: «легко относишься к дизайну, много ошибок допускаешь».

**Это системный сбой**, не разовая ошибка. Правила были, но не enforce'ились. Поэтому теперь — жёсткий протокол, ОБЯЗАТЕЛЬНЫЙ перед закрытием любой UI-задачи. Полная спецификация — [`.claude/rules/design-enforcement.md`](.claude/rules/design-enforcement.md).

**Краткое содержание:**

1. **8 grep-команд** на нарушения (subtitle, inline hex, Lucide, шрифт < 12px, пустой onPress, bg-primary без text-on-primary, ScreenHeader.subtitle, BottomSheet.subtitle) — прогнать перед `git add`. Любой матч = баг, исправить до закрытия.
2. **Preview-чек обязателен** для экрана, который рендерится — screenshot + сравнение с design-quality §G/A/B/C/D глазами.
3. **Lazyweb-запрос обязателен** для нового экрана / существенного редизайна (см. [`lazyweb-rules.md`](.claude/rules/lazyweb-rules.md)).
4. **Чёрный список фраз в отчётах:** «не запускал в preview», «по дизайну как было», «минимальный вариант», «subtitle оставил».
5. **Audit trail:** каждое исправленное нарушение → строка в «🔧 Побочные изменения» отчёта.

Триггер: каждый раз когда правишь `app/**/*.tsx`, `src/components/**/*.tsx`, `src/features/**/*.tsx`. Не применяется к hooks, schemas, миграциям.

Нарушение этого правила = баг, не «по дизайну». Дизайн — часть «сделано».

### 🚨 КРИТИЧЕСКОЕ ПРАВИЛО: ДОКУМЕНТАЦИЯ ПОСЛЕ КАЖДОЙ ОСМЫСЛЕННОЙ ЕДИНИЦЫ РАБОТЫ

После выполнения смысловой единицы работы (новая фича, существенный редизайн экрана, новый компонент, изменение data-схемы, новое правило системы дизайна, новый паттерн в коде) **обязательно** оставить документацию для следующих AI-сессий и людей. Один диалог в чате — это один раз; следующий агент его не увидит.

**Что обновлять:**

1. **`STATUS.md`** — короткая запись в «Что готово / История ключевых решений»: что сделано, почему, где лежит. 1–3 строки.
2. **`SESSION_SUMMARY_<дата>.md`** (новый файл в корне проекта) — расширенный отчёт о сессии: какие задачи закрыты, какие правила добавлены/изменены, какие компоненты появились, какие anti-patterns обнаружены и как их избегать. Если за день уже есть файл — дописать в конец, не плодить новые. Имя строго по дате — `SESSION_SUMMARY_2026-05-14.md`.
3. **Релевантные design-doc'и** — если правило про шрифты → `DESIGN.md`, про cross-platform → `CROSS_PLATFORM_RULES.md`, про БД → `CATEGORIES_AND_PROFILES.md`, про продукт → `PRODUCT_CONTEXT.md`. **Не дублировать** между файлами — линковать.
4. **Шапка-комментарий в коде** — для нового модуля / компонента / hook'а: 5–15 строк сверху файла, объясняющие *почему* (не *что*). Особенно важно для нетривиальной логики, workaround'ов под платформу, неочевидных decisions.
5. **Обновить релевантные `.claude/rules/*.md`** — если правило универсальное и должно подгружаться автоматически (например, новое правило про preview, design-quality, документацию).

**Структура `SESSION_SUMMARY_<дата>.md`:**

```markdown
# Session summary — YYYY-MM-DD

## TL;DR
1–3 строки: что в целом сделано за сессию.

## Закрытые задачи (нумерованный список)
1. [Кратко] — [где правка / новый файл]
2. ...

## Новые правила и решения
- [Правило] — [файл, где зафиксировано] — [Why]

## Новые компоненты / паттерны
- `<ComponentName>` (`src/...`) — [назначение] — [когда использовать / когда НЕ использовать]

## Anti-patterns обнаруженные в сессии
- [Что нельзя делать] — [почему] — [как правильно]

## Открытые вопросы / TODO
- ...
```

**Запрещено:**
- ❌ Закончить большую сессию (5+ задач) и не оставить ни одного doc-обновления — следующий агент не сможет восстановить контекст.
- ❌ Писать «потом задокументирую» — потом не приходит. Документация = часть задачи, не post-action.
- ❌ Документация **только в коммит-message** — её не видно в карте проекта, агент при чтении кода не дойдёт до git-blame.
- ❌ Дублировать одну и ту же информацию в 3 файлах — выбрать один источник истины и линковать.

**Как применять:**

- **Маленькая правка (1 файл, очевидная)** → достаточно осмысленного commit-message и записи в `STATUS.md` если меняет что-то заметное. Без отдельного doc.
- **Средняя единица (2–5 файлов, новый паттерн)** → `STATUS.md` + соответствующий design-doc.
- **Большая единица (новая фича, миграция, набор связанных правил)** → `STATUS.md` + design-doc'и + `SESSION_SUMMARY_<дата>.md`.
- **Сессия с 5+ закрытыми задачами** → обязательно `SESSION_SUMMARY_<дата>.md`.

Это правило обязательно после **последней** задачи в очереди — перед финальным аудитом «🏁 что сделано / что не сделано».

### 🚨 КРИТИЧЕСКОЕ ПРАВИЛО: УМЕНЬШАТЬ ИЗОБРАЖЕНИЯ ДО ≤1200px ПЕРЕД ПРОСМОТРОМ

Перед тем как **читать любое изображение** через `Read` (фотографии пользователя, скриншоты, иконки, exported PDF-страницы, screenshots с превью) — **обязательно** уменьшить до ширины **≤ 1200 пикселей**. Прямое чтение оригиналов > 1500px подвешивает AI-сессию из-за раздутого input в multimodal-модели.

**Команды (macOS, `sips` встроен):**

```bash
# Одна картинка
sips -Z 1200 "source.jpg" --out /tmp/source-1200.jpg

# Батч
mkdir -p /tmp/out && for f in /Users/.../Downloads/*.jpg; do
  sips -Z 1200 "$f" --out "/tmp/out/$(basename "$f")" >/dev/null
done

# PDF → PNG, ширина 1200px, страницы 1-5
pdftoppm -png -scale-to 1200 -f 1 -l 5 input.pdf /tmp/page
```

После уменьшения — `Read` на путь к уменьшенной версии. **Никогда** не читать оригиналы > 1500px напрямую.

**Применяется к:**

- Фотографиям пользователя из `~/Downloads/`, `~/Desktop/`, любых внешних путей.
- Скриншотам экранов реальных приложений (например, для дизайн-референса в дополнение к Lazyweb).
- PDF-страницам (Lazyweb-export, специнструкции, доки конкурентов).
- Image-ассетам в репо, если они > 1500px по ширине (баннеры, hero-фото).

**Не применяется к:**

- Иконкам и SVG-файлам — они уже маленькие и текстовые.
- `preview_screenshot` от Claude Preview MCP — он сам отдаёт сжатый JPEG разумного размера.
- DiceBear / Iconify-CDN URL'ам — это сервер генерирует на лету, размер контролируется через query-params в самом URL.

**Триггер на самопроверку:** перед `Read` на `*.jpg / *.jpeg / *.png / *.heic / *.pdf` остановиться и спросить «известна ли ширина оригинала ≤ 1200?». Если нет / больше — уменьшить через `sips -Z 1200` (или `pdftoppm -scale-to 1200`) и читать уменьшённую версию.

## Критические правила инфраструктуры

### №1: где живёт код

Исходный код живёт **ТОЛЬКО** в `~/Desktop/xtrud/` (или будущей переименованной папке проекта). Не в `/tmp`, не в `/var/tmp`, не «внутри Docker-образа».

Если setup или туториал говорит работать в `/tmp` — игнорируй, работай в папке проекта.

### №2: git с первой минуты

В этой папке обязан быть инициализирован git и настроен remote на GitHub. Проверь первым делом:

```bash
git status
git remote -v
```

Если git не инициализирован — инициализируй немедленно (`git init && git branch -M main`) и создай `.gitignore`. Если remote не настроен — спроси пользователя один раз в начале и настрой. **Не работай без remote.**

Минимум в `.gitignore`:

```
node_modules/
dist/
build/
.expo/
.next/
ios/Pods/
android/.gradle/
.env
.env.local
*.log
.DS_Store
```

### №3: коммиты, push и автоматический деплой

После **каждой осмысленной единицы работы** (новая фича, баг-фикс, рефакторинг) — **сразу** коммит + push + деплой. Решение владельца 2026-06-04: «когда вносишь такие правки, сразу же делай коммит и деплой» (отменяет прежнее правило «выкатывай только по явной команде»).

```bash
git add <конкретные файлы>
git commit -m "осмысленное сообщение"
git push
bash deploy/web.sh    # сразу выкатываем на xtrud.alanbani.ru / xtrud.pro
```

**Что считается «осмысленной единицей»** для триггера коммит+деплой:
- закрытая задача из очереди (TaskCreate/TaskUpdate);
- новая фича, законченный баг-фикс, законченный редизайн экрана;
- завершённое инфра-изменение (config, deploy-скрипт, миграция).

**НЕ триггер:** мелкая промежуточная правка внутри одной задачи (правка-проверка-правка), временные эксперименты, work-in-progress без TS clean.

**Не используй `git add .` / `git add -A`** — это риск зацепить `.env`, секреты, артефакты сборки. Добавляй конкретные файлы.

### №4: опасные операции — спрашивай

Перед `rm -rf`, `git reset --hard`, `git push --force`, удалением папок, миграциями БД с потерей данных — **спроси подтверждение у пользователя** и убедись, что текущее состояние закоммичено и запушено.

### №5: безопасность Supabase

- **Secrets** (service_role key, DB password) — только в `.env.local` и GitHub Secrets, никогда в коде, никогда в публичных переменных Expo/Next (`EXPO_PUBLIC_*`, `NEXT_PUBLIC_*`)
- **RLS включён на каждой таблице** с пользовательскими данными. Без исключений
- Миграции — через файлы в `supabase/migrations/`, не правкой схемы вручную в дашборде

### №6: auth-политика — никакого email

xtrud **не использует email** ни для авторизации, ни для уведомлений, ни для контакта с пользователем. Идентификация — **только номер телефона** (SMS-OTP через Supabase Auth). В будущем добавится **логин + пароль** (поверх phone), но **email не появится никогда**.

**Почему:** в Республике Ингушетия и регионах СНГ телефон — универсальный идентификатор; email используется редко, путает пользователей, и его потеря/смена создаёт точки отказа в восстановлении. WhatsApp-кнопка на мастер-профиле — отдельная история (sprint 0079), это для прямого контакта, не для аутентификации.

**Правила для AI:**

- ❌ НЕ запрашивать email в формах регистрации, онбординга, редактирования профиля, заказа.
- ❌ НЕ показывать email в UI (settings, profile, header chips). Технический `auth.users.email = <phone>@xtrud-demo.local` существует только потому, что Supabase Auth требует email-колонку — это **синтетика**, в UI её прятать.
- ❌ НЕ добавлять «Написать на email» в саппорт-секциях. Только Telegram / WhatsApp / в-приложении чат.
- ❌ НЕ слать transactional/marketing email. Notifications — только Push (Expo) + Push-aware in-app banner.
- ✅ Если в будущем добавляется email — только как **опциональный** канал «для бухгалтерии» (счета юр.лицам) и **только после явного согласования с пользователем-владельцем проекта**.

При обнаружении email-полей или email-логики в legacy-коде/новых задачах — снести и заменить на phone/Telegram, либо явно отметить в отчёте «❓ нашёл email-зависимость, надо решить».

Целевые референсы: Profi.ru, TaskRabbit, Thumbtack, YouDo + эталоны Linear/Vercel/Airbnb/Stripe. Проектирует обе темы. Триггер: «**Вызови роль дизайнера**» / любой запрос на редизайн / новый UI-экран. Полный prompt — [`.claude/agents/xtrud-designer.md`](.claude/agents/xtrud-designer.md). |

### 🎨 Как вызвать роль дизайнера

> 🚨 **ОБЯЗАТЕЛЬНО (приоритет 0):** любой **новый экран / новая страница** создаётся **только** через роль дизайнера, не напрямую. Это жёсткое условие, не «по возможности». Полное правило (что считается новым экраном, процесс, что запрещено) — [`.claude/rules/design-enforcement.md`](.claude/rules/design-enforcement.md) §«Новый экран — создаётся ТОЛЬКО через роль дизайнера». Запрошено владельцем 2026-05-23.

User может сказать «**вызови роль дизайнера**» / «нужен дизайнер» / «передай дизайнеру» — это явный триггер. Также **автоматически** использовать роль на:

- Редизайн любого экрана (даже если user сказал «переделай», а не «вызови дизайнера»)
- **Новый UI-экран (создание с нуля) — обязательно, без исключений** (см. правило выше)
- Существенное изменение компонента (сложная форма, sheet, modal, новые карточки)
- Жалобы на «выглядит плохо», «нелогично», «непонятно где жать»

**Что роль гарантированно делает:**

1. Сначала Lazyweb-запрос (минимум 2 целевых референса — 1 из конкурентов + 1 из эталонов)
2. Проектирует в обе темы (light + dark)
3. Проходит 8 grep-чеков enforcement перед закрытием
4. Финальный скриншот в обеих темах
5. Отчёт user'у простым русским (без P0/P1/RPC/TS жаргона)

**Когда НЕ нужна роль**: правка одной строки текста / цвета, чисто бэкенд-задача без UI.

### Когда работать БЕЗ RPI

Мелкие правки (<1 час, явная задача) — напрямую через диалог. RPI для крупных тасков:
- «UI верификации паспорта мастера»
- «Миграция таксономии услуг»
- «Редизайн главной мастера»
- «Интеграция Stripe payments»
