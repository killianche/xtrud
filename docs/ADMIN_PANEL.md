## 1. Зачем

Владелец должен уметь разобрать жалобу, применить санкцию и увидеть, работает
ли площадка. Сегодня ни одно из трёх не выполняется полностью — раздел 3.

## 2. Предусловие — закалка базы

**Панель нельзя публиковать, пока это не закрыто.** Проверено кодом и
подтверждено живым аудитом 2026-08-26 (`PROJECT_OPERATIONS.md` §8):

| Проблема | Где | Следствие |
|---|---|---|
| `users_update_own` ограничивает строку, но не колонки; гранты широкие | `supabase/migrations/0001_init.sql:294` | Любой авторизованный структурно может выставить себе `is_admin = true` |
| `master_profiles_update_own` — то же | там же, `:311` | Мастер может сам выставить `ranking_score`, по которому сортируется каталог |
| `users_admin_update` разрешает админу писать любую колонку любого пользователя | `0030_admin_flag_and_policies.sql` | Один админ молча создаёт других, следа не остаётся |
| Demo-аккаунт с `is_admin = true`, пароль в истории Git | `0104_admin_demo_account.sql:68` | По живому аудиту demo-админ активен |
| Журнала админских действий нет | — | На вопрос «кто это сделал» ответа не существует |

RLS в PostgreSQL не ограничивает колонки — это делается только грантами.
Поэтому закалка — это `REVOKE UPDATE (…)` плюс триггер, а не правка политики.

Черновик `supabase/migration-drafts/security_hardening_live_verified.sql`
закрывает часть этого, но не применён и по имени файла применяться не должен
(`supabase/migration-drafts/README.md`).

## 3. Что сломано в текущей модерации

- **Жалоба на задание не имеет действий.** `app/(details)/admin/reports.tsx:150-190`
  строит ветки только для `target_type` `user` и `review`. Админских политик на
  `orders` и `order_responses` нет вовсе.
- **Модератор не видит предмет жалобы** — карточка показывает голый `target_id`
  (`reports.tsx:95`), и он намеренно не FK (`0029_reports_table.sql:32`).
- **Приостановка не приостанавливает.** `users.status` не проверяется ни в одной
  политике публикации, отклика или отзыва. Реальные эффекты только два: скрытие
  телефона и исключение из push. Снятия санкции в интерфейсе нет.
- **Пользователь не узнаёт о санкции** — приложение `users.status` не читает.

## 5. Архитектура

```
Браузер владельца
  └─ https://admin.xtrud.pro        статика на web-VPS, Caddy, строгий CSP
        │  бандл + config.json: URL и publishable key, БЕЗ секретов
        └─ backend
              ├─ GoTrue: пароль → TOTP → сессия aal2
              └─ PostgREST: только RPC вида admin_*
                    └─ is_admin_session() → действие → запись в журнал
```

**Ключевая мысль: панель — тонкий клиент без единого секрета.** Вся власть
остаётся в PostgreSQL. Если бандл украдут целиком, злоумышленник получит ровно
то, что уже лежит в опубликованном iOS-приложении.

**Стек:** отдельный статический SPA, npm-workspace `admin/`. Тот же React и
TypeScript, что уже сопровождаются; `src/types/database.ts` переиспользуется как
есть; ноль новых серверных процессов; deploy копируется с `deploy/static.sh` со
всеми его защитами.

Отвергнуто: server-rendered решение (второй backend вопреки ADR-0001 §6),
готовые admin-панели поверх PostgREST (модерация — не CRUD), Directus/Retool и
подобные (второй продукт на сопровождении рядом с персональными данными),
Supabase Studio как повседневный инструмент (общий пароль без личности, полный
обход RLS, нет журнала; остаётся break-glass через SSH-туннель).

## 6. Доступ

- **`service_role` в браузер не попадает никогда.** У него `BYPASSRLS` — это не
  повышенные права, а отсутствие прав доступа как понятия.
- **Признак админа проверяется чтением БД**, а не клеймом в JWT: отзыв прав
  должен действовать мгновенно.
- **Второй фактор отменён владельцем 2026-09-03** («убери второй фактор, просто
  по логину и паролю», миграция 0150). Требование `aal2` снято с
  `is_admin_session()`. Цена решения: пароль администратора — единственная
  преграда к персональным данным всех людей и к смене пароля любому
  аккаунту. Компенсация — длинный пароль и журнал `admin_actions`.
  Вернуть второй фактор — восстановить проверку `aal2` в функции.
- **Чтение персональных данных — через отдельные RPC на каждый экран**, а не
  через широкие политики: широкая политика на `users` начала бы применяться и к
  запросам мобильного приложения.
- **Паспортные фото — без `service_role`:** политика на `storage.objects` плюс
  подписанная ссылка. Каждая выдача ссылки пишется в журнал.

## 7. Размещение

`admin.xtrud.pro` — статика на существующем web-VPS. Не на backend-VPS: там
намеренно оставлены только API-префиксы, и второй сайт рядом с базой создаёт
поверхность там, где её убрали.

Гейт на входе — решение владельца: сертификат mTLS (сильнее всего, привязка к
устройству), пароль на уровне сервера (быстро, но общий), VPN (избыточно для
одного оператора). IP-allowlist как основной гейт отвергнут: динамический адрес
сломает доступ чаще, чем остановит атакующего.

**Ограничение, которое надо назвать прямо:** ни один гейт не защищает сам
backend — он обязан оставаться открытым для приложения. Гейт делает панель
труднодостижимой; данные защищает база.

## 8. Совместимость с переездом на Beget

Панель знает о backend две вещи: URL и publishable key. Чтобы переезд не
потребовал переписывания:

1. не инлайнить их при сборке — читать `config.json`, который рендерится из
   `release/production.json` при деплое, тем же приёмом, что уже применён для
   статической страницы сброса пароля;
2. добавить блок `admin` в `release/production.json` и ветку в валидатор
   контракта;
3. использовать только то, что одинаково работает в Cloud и в закреплённом
   self-hosted снимке: PostgREST RPC, GoTrue MFA, подписанные ссылки Storage;
4. вход только пароль плюс TOTP, без magic link — тогда домен админки не нужно
   вносить в redirect allowlist;
5. **проверить сохранность TOTP-факторов при репетиции восстановления** — в
   текущем runbook такой проверки нет, и потеря второго фактора обнаружится уже
   после переключения.

## 14. Паспорта — подтверждение личности (0174)

DECISION владельца 2026-09-07: «человек отправляет фото паспорта, оно
приходит в админку, админ подтверждает, появляется значок».

- Страница `/verifications` («Паспорта»): вкладки «Ждут проверки /
  Подтверждены / Отклонены». RPC `admin_list_verifications(p_status)`.
- Фото — приватный бакет `master-verifications`, путь `{user_id}/passport-<ts>.jpg`.
  Панель получает подписанную ссылку на 10 минут через Storage API; политика
  `master_verifications_admin_select` пускает только `is_admin_session()`.
- Решение — `admin_review_verification(p_user_id, p_approve, p_reason)`:
  отклонение без причины невозможно; запись в `admin_actions`
  (`verification_approve` / `verification_reject`); человеку уходит
  уведомление (`data.type = verification_approved|rejected`).
- Триггер `sync_master_verification_level`: approved → `verification_level = 2`,
  иначе 1. Значок в приложении рисуется только при уровне ≥ 2.
- Что сверять: имя и фамилия в аккаунте совпадают с паспортом, фото читаемо.
  Паспортные данные никуда не копировать; ссылка на фото временная.

## 15. Скрыть задание по жалобе (0175)

DECISION владельца 2026-09-07 (Р5): «дай возможность скрыть задание».
В карточке жалобы с `target_type = order` — кнопка «Скрыть задание»:
`admin_hide_order(p_order_id, p_reason, p_report_id)` переводит задание в
`cancelled` с `cancel_reason = 'moderation: <причина>'`, закрывает жалобу как
решённую, пишет `hide_order` в журнал и отправляет автору уведомление с
причиной. Уже закрытое задание скрыть нельзя (ошибка `order_already_closed`).

## 16. Админ внутри приложения (2026-09-08)

DECISION владельца: «чтобы я мог дать аккаунту админский статус, и он мог
удалять, блокировать — прямо внутри приложения».

- Страница задания, меню «⋯»: «Скрыть задание (админ)» — `admin_hide_order`,
  автор получает уведомление с причиной.
- Причины запрашиваются системным `Alert.prompt` (`src/lib/prompt.ts`);
  все действия попадают в журнал `admin_actions`.

## 17. Панель на своём сервере (2026-09-08)

Панель больше не использует `@supabase/supabase-js`. Вход —
`POST /v2/auth/login` почтой и паролем администратора, сессия в
`localStorage` с обновлением токена; вызовы — `POST /v2/rpc/<функция>`;
фото паспортов — `POST /v2/files/sign` (ссылка на 10 минут).
Адрес API берётся из `/admin/config.json` (`supabaseUrl` — историческое имя
поля).
