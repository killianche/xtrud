# План переписывания сервера без Supabase

> DECISION владельца (2026-09-08): «полностью уйти от Supabase, переписать
> всё, чтобы работало на сервере Beget, с возможностью откатиться; если нужно
> — купим S3». Этот документ — план, архитектура и журнал этапов.

## 1. Что остаётся, что уходит

| Сейчас | Решение | Почему |
|---|---|---|
| PostgreSQL 17 (образ `supabase/postgres`) со 176 миграциями, RLS, функциями, pg_cron | **Остаётся как данные и правила.** На последнем этапе — переезд на официальный образ `postgres:17` + расширения `pg_cron`, `pg_net` | База и правила доступа не «Supabase», это PostgreSQL. Переписывать их — риск без выигрыша |
| GoTrue (auth) | **Заменяется** нашим сервисом входа в `xtrud-api` | Своя регистрация по телефону и паролю, свои токены |
| PostgREST + supabase-js | **Заменяется** нашим API (`server/`, Node 22 + Fastify + pg) и своим клиентом в приложении | Убирает клиентскую библиотеку Supabase и протокол PostgREST |
| storage-api | **Заменяется** модулем файлов в `xtrud-api`: сначала диск VDS, затем Beget S3 + CDN | Тот же путь `bucket/path`, подписанные ссылки для закрытых бакетов |
| imgproxy | Остаётся (открытый код, не Supabase) | Превью фото, уже используется |
| realtime | **Заменяется** SSE-потоком `/v2/events` (уведомления) | Единственная подписка в приложении — личные уведомления |
| Edge Functions (Deno): notify, register-user, send-sms, send-reset-email | **Заменяются** модулями API | notify → APNs напрямую (нужен ключ), send-sms → SMS.ru, reset-email — не нужен (восстановление через админку) |
| envoy/kong, studio, meta, logflare, pooler | Выключаются после переезда | Не нужны без Supabase |

## 2. Совместимость и откат

- Токены доступа — JWT HS256 с тем же `JWT_SECRET` и теми же claims
  (`sub`, `role=authenticated`, `aud`), что выпускал GoTrue. Значит: старая
  сборка приложения с PostgREST и новая с `xtrud-api` работают против одной
  базы одновременно; `auth.uid()` в RLS работает без изменений.
- Пароли: те же bcrypt-хеши в `auth.users.encrypted_password`; наш сервис
  проверяет и создаёт их совместимо. Ни один аккаунт не теряется.
- API выполняет запросы в транзакции с `SET LOCAL ROLE authenticated|anon`
  и `set_config('request.jwt.claims', …)` — все политики RLS и функции
  `SECURITY DEFINER` работают как прежде.
- Откат: переключатель `EXPO_PUBLIC_BACKEND=supabase|xtrud` в приложении;
  контейнеры Supabase остаются запущенными до конца контрольного периода
  (минимум 2 недели после полного переезда). Старые сборки продолжают
  работать всё это время.

## 3. Этапы

| Этап | Содержание | Проверка готовности |
|---|---|---|
| 0 | Каркас `server/`: Fastify, pg, миграции не нужны; Docker; деплой на Beget в сеть `supabase_default`; nginx `api.xtrud.pro/v2/` | `GET /v2/health` = 200 с сервера |
| 1 | Вход: регистрация (имя, фамилия, телефон, пароль), вход, обновление токена, выход, смена пароля; мост RPC `/v2/rpc/:name` для 24 функций | curl: регистрация → вход → `/v2/rpc/get_response_limit_today` |
| 2 | Данные: типовые эндпоинты вместо `supabase.from(...)` (63 места, 17 таблиц): задания, отклики, специалисты, профиль, портфолио, отзывы, уведомления, жалобы, блокировки | приложение с `EXPO_PUBLIC_BACKEND=xtrud` проходит чек-лист владельца |
| 3 | Файлы: загрузка/удаление/подписанные ссылки; бэкенд диск → Beget S3 (после ключей владельца); превью через imgproxy | фото профиля, работ, заданий, паспорта |
| 4 | Уведомления: SSE `/v2/events`; push в APNs напрямую (после ключа); `notify_user` в базе → `xtrud-api` | бейджи обновляются без перезапуска |
| 5 | Админка на `xtrud-api` | все страницы админки |
| 6 | Переезд базы на `postgres:17` + расширения; выключение контейнеров Supabase; удаление supabase-js из приложения и админки | `npm ls` без `@supabase/*` |

Каждый этап заканчивается сборкой в TestFlight и записью в `TASKS.md`.
