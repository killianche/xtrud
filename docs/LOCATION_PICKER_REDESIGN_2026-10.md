## 1. Разбор — что плохо на скриншоте и почему (FACT, по коду/данным)

Экран — `app/(details)/orders/new/where.tsx`. Сейчас это два `ChoiceGroup`
(`InsetGroup`/`InsetRow`, `src/components/ui/InsetList.tsx`) с **одним общим
радио-выбором**: тап по городу делает `patch({ cityId: c.id, district: "" })`,
тап по району — `patch({ cityId: "", district: d.name })`. Город и район
взаимно исключают друг друга в form-state.

1. **Орджоникидзевская / Серноводская / Нестеровская в секции «ГОРОД»** —
   это записи `MAJOR_CITIES` (`location-config.ts:47-49`), добавленные
   миграцией `0050_cities_add_large_villages.sql` как «крупные сёла с
   населением > 15К». Они стоят в списке как равноправные городу Малгобек
   или Сунжа пункты, хотя `CITY_IDS_BY_DISTRICT_ID.sunzhensky` уже перечисляет
   `sunzha`, `ordzhonikidzevskaya`, `sernovodskaya`, `nesterovskaya` как **один
   куст Сунженского района** (`location-config.ts:233-238`). Семеро равных
   строк под заголовком «ГОРОД» вместо «4 настоящих города + 1 район» —
   визуальный шум и ломает мысленную модель пользователя (владелец: «это
   небольшие сёла, они входят в район»).
2. **Район не включает город, а вычёркивает его.** `onPress` района делает
   `cityId: ""` — любой ранее выбранный город гаснет. Семантически это
   неверно ровно наоболрот тому, что уже умеет backend: таблица
   `district_cities` (миграция `0192`, упомянута в комментарии
   `location-config.ts:226-231`) и хелпер `CITY_IDS_BY_DISTRICT_ID` **уже
   трактуют** выбор района как включающий его города — `nazranovsky` →
   `["nazran-magas", "nazran", "magas"]`. UI же радио-кнопкой визуально
   утверждает обратное: «либо город, либо район» — две конкурирующие опции,
   будто они не пересекаются. Разрыв между тем, что фактически произойдёт
   (специалисты из Назрани увидят задание), и тем, что видит пользователь
   (строка «Назрань» потушена) — это именно нечестность интерфейса
   (`design-quality.md` §5), только в обратную сторону: интерфейс утверждает
   *меньше*, чем на самом деле сделает.
3. **У района нет собственного уровня «село».** Строка района сейчас —
   не навигация, а прямой выбор (`ChoiceRow`, не `navigates`), subtitle —
   статичный превью трёх сёл без возможности тапнуть по конкретному. Чтобы
   выбрать конкретное село, пользователь должен закрыть экран «Где», открыть
   где-то ещё… на самом деле — **нигде**: в текущем коде шага «Где» выбор
   конкретного села недоступен вовсе (`district` ставится только равным
   полному имени района). Это прямое несоответствие тому, что обещано
   остальной системе: `location-config.ts` содержит `findDistrictByVillage` /
   `isVillageName` — функции, рассчитанные на то, что где-то `district` может
   быть именем села, — но шаг «Где» никогда не производит такое значение.
4. **Кнопка «Далее» перекрывает последнюю строку.** `ComposerScreen.tsx`
   уже резервирует `contentContainerStyle={{ paddingBottom: actionsHeight +
   bottomSpace + 24 }}` под плавающую `GlassButton` (56 pt,
   `GLASS_BUTTON_HEIGHT`) — по расчёту места должно хватать. На
   accessibility-размере шрифта (где заголовок, подписи сёл и сама кнопка
   растягиваются) этот расчёт не включает рост высоты самой кнопки / текста
   ошибки сверх базовых 56/44 pt, и `last` в `ChoiceGroup` не добавляет
   дополнительного зазора под последней группой. На обычном шрифте с 7
   строками городов + 4 строками районов это, по всей видимости, тот самый
   случай «видно впритык», который на снимке владельца читается как
   «перекрывает» — не доказано кодом, что padding физически меньше высоты
   кнопки (UNKNOWN, способ проверки — §13), но решение ниже (§6.6) закрывает
   и количественно, и запасом.

## 3. Референсы

**iOS 26 / HIG (общее знание платформы — не снято на устройстве в этой
сессии, см. §13):**

- **Settings → General → Language & Region → Region**: строка с текущим
  значением и `>`, тап пушит полноэкранный список с поиском; выбор —
  немедленный pop back. Ровно наш случай «тап по району → список сёл».
- **Contacts → карточка → Add Field → Country/Region**: тот же push + search
  паттерн для одноуровневого, но длинного списка.
- **Health → Browse**: категории — плоский список, тап по категории пушит её
  детальный список; «показать всё» не существует отдельной строкой — родитель
  сам закрывает тему. У нас по смыслу ближе «Весь район» как первая строка
  детального списка, а не отдельная операция.
- **Списки выбора (Wi-Fi, Bluetooth, тон звонка)**: ровно одна галочка у
  текущего значения, никаких вторичных пометок у несвязанных строк — это
  довод **против** идеи «подсвечивать город галочкой, когда выбран его
  район» (см. §5, отвергнутый вариант).

**Продуктовые аналоги — UNKNOWN конкретной вёрстки.** WebSearch по
Авито/Профи/YouDo/Thumbtack в рамках этой задачи не запускался (30-минутный
лимит, задача решается в первую очередь из принципов iOS и уже принятой в
коде модели данных `district_cities`). По общему знанию: у всех крупных
российских сервисов география покрывает сотни городов, поэтому их паттерн —
**поиск-первый** (строка поиска сверху, иерархия используется только как
фильтр после ввода текста). У xtrud ровно обратная ситуация: **фиксированные
~30 известных точек в одной республике** — поиск был бы избыточным UI для
списка, который весь виден на одном экране без скролла (ранее по этой же
причине убрали `search` из `CitySelector`, см. комментарий в файле,
2026-05-15). Поэтому решение ниже ближе к iOS Settings, чем к Авито —
это FACT про наш объём данных, а не скопированный с Авито паттерн.

## 4. Шаг назад — какую задачу решает экран

Одна задача: **сузить место выполнения работы до того, что пользователь
реально имеет в виду** — либо всю республику, либо конкретный населённый
пункт (город/район/село), причём **выбор района не должен прятать то, что он
включает**: если человек выбрал Назрановский район, специалисты Назрани·Магаса
должны увидеть задание — это уже умеет backend (`district_cities`), и
интерфейс не должен визуально утверждать противоположное.

Что убрать (design-quality §1.1): три псевдо-города-села (Орджоникидзевская,
Серноводская, Нестеровская) как отдельные строки верхнего уровня — без них
ничего не теряется, они доступны там же, где и остальные 9 сёл их района.

## 5. Варианты

### Вариант A — Push-пикер района (выбран)

Уровень 1 без изменений по структуре (две группы «ГОРОД» и «РАЙОН», как сейчас
нравится владельцу по другим экранам, см. `SKILL.md`: «Фильтры — подписанные
капсулы… выбранная — border-accent»), но:
- «ГОРОД»: только 4 реальных города (Назрань·Магас, Карабулак, Малгобек,
  Сунжа) + «Вся Ингушетия» — 3 села убраны.
- «РАЙОН»: 4 района, каждая строка — `navigates` (шеврон, как `InsetRow`
  уже умеет), тап **всегда** пушит экран «‹Название района›» со списком:
  первая строка «Весь район» (жирным, плитка-иконка на акцентной подложке —
  тот же приём, что `PickerSheetPage` уже использует для «Весь раздел» /
  «Все услуги»), затем все сёла района (включая три бывших псевдо-города —
  добавлены в `villages` Сунженского района), с поиском при ≥ 8 строк (тот
  же порог, что уже в `PickerSheetPage`/`l3-select.tsx`). Выбор — немедленный
  pop back, как в `category/l3-select.tsx`.
- Город и район остаются взаимоисключающим **выбором одного значения** (одна
  работа — один адрес), но «вычёркивание» снимается иначе: см. §6.1 —
  честность решается текстом, не двойным чекмарком (см. отвергнутый вариант
  ниже).

**Цена:** 1 новый роут (экран сёл района) + правка `where.tsx`,
`location-config.ts` (данные — зона backend), `location-select.tsx`,
`category/city-select.tsx`. Переиспользует существующие компоненты
(`InsetGroup`/`InsetRow`, `PickerSheetPage`+`PickerSections`) — ни одного
нового визуального компонента. Низкий риск, 1 новый экран на платформу
(formSheet-вариант и push-вариант — два разных способа встраивания одного и
того же списка, не два разных UI).

### Вариант B — Поиск по всем населённым пунктам + иерархия как фильтр

Строка поиска сверху (как `headerSearchBarOptions`, `docs/IOS_FOUNDATION.md`
§2.6) по всем ~35 названиям (города+районы+сёла), иерархия — только когда
поиск пуст.

**Цена:** выше — нужен полноценный индекс поиска по трём типам сущностей,
маппинг «нашли село → подставить его район», два режима отображения одного
экрана. Для 30 известных точек это решает проблему, которой у нас нет (у
Авито таких точек тысячи) — добавленная сложность без выигрыша, нарушает
§1.1 «лишняя функция — дефект». Отвергнут.

### Отвергнутый приём внутри варианта A — «двойной чекмарк»

Рассматривалась идея: при выбранном районе ставить второй, более тусклый
чекмарк у его города в секции «ГОРОД», чтобы визуально показать включение.
Отвергнуто — противоречит самому частому iOS-паттерну списков выбора (ровно
одна галочка текущего значения, см. §3) и добавляет пользователю вопрос «а
почему их два». Выбрано текстовое объяснение вместо второй галочки — см.
§6.1, пункт про subtitle городов.

## 6. Решение — по экрану

### 6.1 Шаг «Где» конструктора (`where.tsx`)

**Группа «ГОРОД»:** «Вся Ингушетия», «Назрань · Магас», «Карабулак»,
«Малгобек», «Сунжа» — `ChoiceRow`, выбор как сейчас (одно значение).
Городам, у которых есть «свой» район (Назрань·Магас → Назрановский, Сунжа →
Сунженский — через `CITY_IDS_BY_DISTRICT_ID`), подпись `subtitle` города не
добавляем: честность уже обеспечена на уровне района (см. ниже), а дублировать
«Назрановский район» под каждым городом — лишний текст на самом частом пункте
списка (большинство тапает город, не читая мелкий текст).

**Группа «РАЙОН»:** 4 строки, `ChoiceRow` → используем проп `navigates: true`
+ `value` = текущее уточнение («Весь район» не показываем как value, пусто;
конкретное село — показываем его имя, напр. `value="Экажево"`), `subtitle`
остаётся превью сёл для нетронутой строки. Тап **всегда** открывает push-экран
независимо от того, выбран район уже или нет (соответствует «При нажатии на
район — открывается список сёл», владелец).
Под заголовком группы — одна строка подсказки (Footnote, `text-mute`):
«Весь район — значит заявку увидят специалисты всех его городов и сёл» —
это и есть честный текст вместо скрытого вычёркивания города, без второй
галочки.

**Push-экран «‹Район›»** — новый роут
`app/(details)/orders/new/where-district/[districtId].tsx` (push, не sheet —
продолжение текущего flow конструктора, `docs/IOS_FOUNDATION.md` §2.4: «выбор
параметра» — это formSheet, но здесь это **шаг внутри уже начатого
flow конструктора**, равноценный самому экрану «Где»; формат должен совпадать
с остальными шагами, то есть обычный push с `ComposerScreen`-шапкой выбивается
из паттерна — вместо этого **плоский native push без conposer-хрома**, как
другие detail/picker экраны, с нативным back и заголовком района):
- `InsetGroup` без заголовка (это сам контент, не подгруппа).
- Строка 0: «Весь ‹район›» — жирным, плитка-иконка на `bg-accent` (как
  «Весь раздел» в `PickerSheetPage`), subtitle «Все сёла и Назрань · Магас»
  (подстановка связанного города, если есть; для Джейрахского — без города,
  subtitle не нужен).
- Остальные строки — сёла района, алфавитный порядок (как `FILTER_VILLAGES`
  везде в проекте), галочка у текущего выбранного.
- Поиск (`SearchField`, тот же порог «≥ 8 строк» что в
  `l3-select.tsx`/`PickerSheetPage`) — у Назрановского (10 сёл) и
  Малгобекского (8) появляется, у Сунженского (6+3=9 после переноса сёл-
  городов) появляется, у Джейрахского (8) появляется.
- Тап по строке → `patch` в `composer-store` (`cityId: "", district: <район
  или село>`) → `router.back()`. Тот же handshake, что уже использует
  `category/l3-select.tsx` через собственный store — здесь проще: `where.tsx`
  и под-экран оба читают/пишут один и тот же `useComposer()`, отдельный
  result-store не нужен.

**Отображение выбранного на самом шаге «Где»** (строка района, `value`): пусто
для «весь район», имя села — для села.

### 6.2 Фильтр ленты заданий — `location-select.tsx`

Сейчас это один плоский `PickerSheetPage` список (Вся Ингушетия → города →
районы, с `subtitle: "Город"/"Район"` и поиском). Меняем на `sections`
(проп `PickerSheetPage` уже поддерживает, см. `PickerSheetPage.tsx:52`):
секция без заголовка — «Вся Ингушетия»; секция «Город» — 4 города; секция
«Район» — 4 района, но теперь районные строки **не финальны**: тап по строке
района в этой шторке сразу открывает **второй уровень той же шторки**
(`PickerSheetPage` поддерживает только один уровень, поэтому технически это
второй push-роут того же формата, что и `category/l3-select.tsx` — отдельный
`app/(details)/find/location-select-district.tsx` с теми же `sheetOptions`,
получающий `districtId` параметром). Выбор села или «Весь район» коммитит
в `useOrdersSearchFiltersStore.setLocation` и закрывает **обе** шторки
(`router.dismiss(2)` либо `router.back()` дважды — решает implementer по
фактическому API `expo-router`, помечено как деталь реализации, не дизайн).

Это даёт тот же UX, что в конструкторе, другим транспортом (sheet вместо
push), что ожидаемо: один паттерн данных, два стандартных способа его
показать (push — flow, formSheet — быстрый фильтр), как и сейчас устроено
в проекте (`city-select.tsx` и `l3-select.tsx` — тот же sheet-поверх-sheet
приём уже существует для категорий).

### 6.3 Фильтр «Специалисты» → место (`category/city-select.tsx` + стор)

Сейчас фильтр специалистов знает только `cityId` (`specialists-filters-store.ts`)
— района нет вовсе, хотя задача явно просит «специалист [в выдаче] видит
район целиком, включающий его города и сёла». Решение:
- `specialists-filters-store.ts`: добавить `district: string | null` рядом с
  `cityId`, взаимоисключающе (как в `where.tsx`), `countSpecialistsFilters`
  учитывает оба.
- `city-select.tsx` переименовать по смыслу в единый «место»-пикер (роут можно
  оставить тот же URL ради совместимости ссылок, UI-заголовок — «Место»): те
  же секции «Город»/«Район», тот же push-в-район как в §6.1/6.2.
- Фильтрация списка специалистов по выбранному району — зона backend/data
  (специалист должен попасть в выдачу, если его `ServiceAreasSection`
  пересекается с запрошенным районом или любым его городом/селом) — это
  серверная/клиентская логика фильтрации, не дизайн; помечаю как
  зависимость от `docs/LOCATION_MODEL_2026-10.md`.

### 6.4 `CitySelector` (город пользователя, главная) — не меняется

Этот пикер — «город пользователя» для рекомендаций, не локация конкретного
задания; комментарий в файле прямо говорит «сёла — не показываются… это шаг
"Где" конструктора». Один уровень (8 позиций без поиска) соответствует своей
узкой задаче — добавлять туда районы/сёла означало бы раздувать то, что
решает один клик на главной. Не трогаем; только синхронизируем список городов
(убрать 3 bugged-записи, если их уберут из `PICKER_CITIES` — зона backend/
data-слоя).

### 6.5 «Где работаете» (мастер) — `ServiceAreasSection.tsx`

Multi-select чипов. Меняется минимально:
- Чипы городов — 4 вместо 7 (три села-города исчезают, как везде).
- Район — остаётся **атомарной** единицей (чип района = весь район, без
  раскрытия до сёл). Причина: специалист размечает зону работы широкими
  мазками — точность до одного села не нужна его сценарию (он не теряет
  заявки из своего района, если не отметил именно своё село — отмечает район
  целиком). Добавлять здесь третий уровень («какие именно сёла района вы
  обслуживаете») — лишняя функция без доказанного запроса (design-quality
  §1.1); если архив `MASTER_ACCOUNT_PLAN.md` когда-то предполагал радиус —
  он уже сознательно убран тем же документом («без сёл и без radius»).
- Текст подсказки под «Вся Ингушетия» не меняется.

### 6.6 Редактирование задания (`orders/edit/[id].tsx`)

Переиспользует тот же `where.tsx`/`order-schema` (`cityId`, `district`) —
автоматически получает весь редизайн §6.1 без отдельной правки экрана.
Единственная специфика редактирования — **pre-fill**: старое задание может
иметь `district = "Экажево"` (село) — шаг «Где» должен показать это в строке
района как `value="Экажево"`, что уже предусмотрено в §6.1 (строка района
читает текущее значение как «весь район» или «конкретное село» без
дополнительного кода конвертации — `findDistrictByVillage` в
`location-config.ts` уже даёт обратный lookup).

  в рамках 30 минут, см. UNKNOWN §13.

## 8. Состояния

- **Загрузка** — список городов во `find/location-select.tsx` и
  `category/city-select.tsx` зависит от `useCities()`/сети: skeleton-строки
  (`PickerSheetPage` уже умеет `loading`), районы — локальная константа,
  не требуют сети, показываются мгновенно. В `where.tsx` список целиком
  локальный — состояние загрузки не нужно.
- **Пусто** — не применимо (списки городов/районов фиксированные и не бывают
  пустыми); единственный «пустой» случай — поиск по сёлам без совпадений на
  push-экране района → текст «Ничего не найдено» (готовый паттерн
  `PickerSheetPage`/`SearchField`, переиспользуется, не изобретается).
- **Ошибка** — сеть недоступна при загрузке городов (`find/location-select`,
  `category/city-select`): уже обрабатывается (`errorMessage` + `onRetry` в
  `PickerSheetPage`); районы не зависят от сети — не ломаются при оффлайне.
- **Оффлайн** — то же: города имеют bundled-fallback
  (`bundled-cities.ts`, уже реализовано), районы — всегда локальные данные.
- **Нет прав / не авторизован** — не применимо, выбор места доступен без
  входа (гостю) на всех перечисленных экранах, кроме «Где работаете» (мастер,
  требует профиль — уже вне зоны этой правки).
- **Длинный контент** — subtitle с перечислением сёл обрезан `…` уже сейчас;
  на push-экране района список может быть длиннее экрана — обычный скролл,
  не требует отдельного состояния.
- **Самый крупный шрифт** — см. §9.

## 9. Accessibility, Dynamic Type, тёмная тема

- **VoiceOver.** `ChoiceRow`/`InsetRow` уже строит `accessibilityLabel` из
  `title` + `subtitle`/`value` (`InsetList.tsx:92-96`) — для района с
  `navigates: true` нужно убедиться, что лейбл включает текущее уточнение
  («Назрановский район, Экажево» вместо просто «Назрановский район»), иначе
  пользователь VoiceOver не услышит, что значение уже сужено до села.
  `accessibilityRole="button"` у `navigates`-строк — дополнительно нужен
  намёк «переход», стандартно это делает сам chevron + `accessibilityHint`
  («Открывает список сёл») — добавить явно, раз строка одновременно выглядит
  как выбор (как обычный `ChoiceRow`) и как навигация (chevron) — без подсказки
  это неоднозначно для незрячего пользователя сильнее, чем для зрячего.
- **Dynamic Type / accessibility-размер.** Ни один текст в решении не имеет
  капа множителя (`InsetRow`/`PickerSheetPage` уже без капа). На push-экране
  района при крупном шрифте строка «Весь ‹район›» с длинным subtitle
  («Все сёла и Назрань · Магас») может занять 3 строки — допускается, список
  скроллится. Поисковое поле и строки — `min-h-*`, не фиксированная `h-*`
  (существующий паттерн, не меняется).
- **Тёмная тема.** Все цвета — через токены (`bg-accent-soft`, `text-mute`,
  `border-hairline` и т.п.), ни одного нового хекса не вводится — решение
  целиком использует существующие классы `InsetGroup`/`InsetRow`/
  `PickerSheetPage`. Обе темы требуют реального снимка на этапе реализации
  (`xtrud-screenshots`) — в рамках дизайн-спеки код не менялся, снимков нет
  (см. §13/14).

## 10. Закреплённая кнопка «Далее» не перекрывает список

Используем уже существующий расчёт `ComposerScreen.tsx`
(`actionsHeight + bottomSpace + 24`), но добавляем явный пол: implementer
проверяет на реальном accessibility-размере, что последняя строка группы
«РАЙОН» видна целиком при докрутке до конца (не «почти видна») — ручная
проверка на симуляторе/устройстве с AX3, а не только по формуле (формула
верна в арифметике, но не учитывает, что `GlassButton`/заголовок ошибки могут
расти по высоте на крупном шрифте сильнее, чем зарезервированные
+48/+44 — см. диагноз §1.4). Если на устройстве всё же тесно — увеличить
статичный запас `+24` в `ComposerScreen.tsx`, не трогая расчёт по месту
использования (это общий компонент для всех шагов конструктора, правка в
одном месте закрывает проблему везде, а не только на шаге «Где»).

  не вводим непрошенную точность.
- `CitySelector` (город пользователя) не трогаем — другая задача экрана.

**UNKNOWN**

- Точная вёрстка выбора района/города у Авито, Профи, YouDo, Thumbtack —

- Точное API `expo-router` для закрытия двух вложенных formSheet одним

## 14. Что не проверено на устройстве (честно)

Это дизайн-спецификация, код не менялся и не собирался. Ничего из разделов
6–10 не снято на реальном iPhone: ни обе темы, ни Dynamic Type/AX, ни
VoiceOver, ни фактическая высота отступа под кнопкой «Далее» с новым
содержимым. Всё это — задача `xtrud-implementer` (реализация) и `xtrud-qa`
(проверка сценариями и состояниями) по маршруту
`.claude/rules/agent-delegation.md` для класса «UI/новый экран».
