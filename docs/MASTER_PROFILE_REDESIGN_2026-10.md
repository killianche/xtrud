## 1. Разбор того, что есть (FACT, прочитано в коде)

1. **Контакты гостю уже показываются** — `bottomBar = !isOwn && hasContacts`
   (строка ~141) не проверяет `currentUserId`. Это прямо противоречит новому
   запросу: гость сейчас видит «Позвонить» / «WhatsApp» точно как вошедший.
   Старое `DECISION владельца 2026-05-20 («classifieds»)`, записанное прямо в
   шапке файла («Гость видит контакты… отзыв оставляет после входа»), сегодняшним
   запросом **отменяется для контактов специалиста** (см. §5 ниже — это не
   только UI, это и бэкенд).
2. **Склонение числительного захардкожено.** `` `· ${ratingCount} отзывов` ``
   (строка ~262) — для 1, 2, 3, 4, 21… отзывов грамматически неверно («2
   отзывов» вместо «2 отзыва»). В проекте уже есть готовая функция
   `pluralizeReviews()` в `src/lib/pluralize.ts`, но в этом экране она не
   используется — очевидный пропуск, не новая работа.
3. **Четыре разных стиля заголовка секции на одном экране** — ровно то, что
   выглядит «не нашим стилем» на скриншоте:
   - `InsetGroup title="Чем занимается"` / `"Услуги и цены"` / `"Ссылка"` —
     заголовок рисует сам компонент (единый iOS-стиль, uppercase caption).
   - «О себе» — ручной `<AppText className="uppercase text-ios-footnote">`
     + своя карточка `rounded-2xl bg-canvas px-4 py-3.5` (строки ~318–333).
   - «Фото работ · N» — ручной заголовок с иконкой `ImageIcon` перед текстом
     (строки ~344–350) — третий вариант оформления подписи.
   - «Отзывы» — `text-title-lg`, **не** uppercase, `font-semibold`, без
     иконки (`ReviewsSection.tsx` строка ~36) — четвёртый вариант.
   Итог: один экран, четыре типографические системы для одной и той же роли
   «подпись секции». Это и есть источник ощущения «не свой стиль», а не
   собственно цвет или иконки.
4. **«О себе» показывает по факту только опыт.** Если `bio` не заполнено (на
   скриншоте — именно так: «Опыт 3–7 лет» без текста о себе), заголовок «О
   себе» обманывает: под ним нет рассказа, только метка стажа. Это смежно с
   §5 `design-quality.md` (честность интерфейса) — заголовок обещает то, чего
   нет.
5. **Рейтинг и число отзывов продублированы без общего визуального якоря.**
   Шапка показывает «★ 5.0 · 2 отзыва[ов]», а секция «Отзывы» ниже просто
   повторяет число в скобках `(2)` — иначе оформленным текстом. Это не плохо
   само по себе (App Store делает так же, см. §2), но раз стили разные —
   выглядит как две независимые надписи, а не одна история.
6. **Безопасность, а не только дизайн: контакты специалиста публичны на
   уровне данных, а не только на уровне кнопки.** Проверено в
   `supabase/migrations/0098_get_master_phone_contact_first.sql`:
   `GRANT EXECUTE ON FUNCTION get_master_phone(uuid) TO anon, authenticated` —
   функция не проверяет `auth.uid()`, отдаёт телефон анониму так же, как
   вошедшему. `whatsapp_phone` — обычная колонка `master_profiles`, читаемая
   `SELECT *`/публичным полем в `useMasterPublicProfile` (комментарий в файле:
   «master_profiles (read all)»), без какого-либо RPC-слоя. **Спрятать кнопку
   в UI не закрывает доступ**: как гость, так и сейчас, так и после моего
   редизайна интерфейса без изменения бэкенда, можно получить номер прямым
   вызовом RPC/прямым select, минуя экран. Это не входит в зону дизайнера —
   фиксирую как блокер для `xtrud-security`/`xtrud-backend` в §5 и в разделе
   приёмки, иначе «призыв зарегистрироваться» — витрина без замка.

## 3. Шаг назад: какую задачу решает экран

Одна задача: **гость должен быстро понять, подходит ли специалист, и ровно в
точке, где он хочет действие «связаться» — получить одно понятное предложение
войти**, а не наткнуться на то, что контакт уже открыт без всякого аккаунта
(нынешнее поведение) и не наткнуться на четыре по-разному оформленные таблички
«вот секция».

### Вариант A — точечная правка этого экрана (рекомендован)

- Один общий стиль заголовка секции на весь экран: формат `InsetGroup`
  (uppercase caption, тот же интервал) — применяется и к «О себе», и к «Фото
  работ», и к «Отзывы» (их текущий ручной заголовок убирается, используется
  тот же паттерн, что уже дают `InsetGroup`-секции).
- Карточка «О себе» рисуется только когда есть `bio`; строка опыта — отдельная,
  тихая подпись под именем в шапке (как `place`/`availability_status` сейчас),
  а не часть секции с заголовком, который она не оправдывает (чинит находку
  §1.4).
- `· {ratingCount} отзывов` → `pluralizeReviews(ratingCount)` — готовая функция,
  просто подключить.
- Секция «Отзывы»: сверху — сводка (крупное число среднего рейтинга + 5 звёзд
  + склонённый total), ниже — список карточек без изменений по сути. Без
  гистограммы по звёздам (нет данных, см. §2).
- Нижний блок контактов: ветвится по `currentUserId`, а не только по
  `hasContacts`:
  - **вошедший, `hasContacts`** — как сейчас, плавающие стеклянные
    «Позвонить»/«WhatsApp» (ничего не меняется, это уже хороший, проверенный
    узор).
  - **гость, `hasContacts`** — карточка-призыв **в потоке контента**, сразу
    под шапкой (имя/рейтинг/категория), **не floating-glass**: стекло в
    `SKILL.md` зарезервировано за навигационным слоем, а не за содержимым —
    карточка с заголовком, подписью и кнопкой — это содержимое. Опаковая
    карточка `rounded-2xl`, фон `canvas-soft` (тот же токен, что уже даёт
    «О себе»), иконка замка (Phosphor, mono-UI — см. `docs/UI_ICONS.md`;
    точное имя символа — `LockSimple`, проверить при реализации, что оно есть
    в установленной версии `phosphor-react-native` — не угадано как факт).
    Текст: «Войдите, чтобы увидеть контакты» + одна строка «Позвонить или
    написать можно после входа в аккаунт» + кнопка `pill` «Войти» (стиль как
    «Войти по телефону» в `app/(tabs)/cases/index.tsx` / `profile/index.tsx` —
    узнаваемый паттерн гостевого CTA в проекте). Кнопка сохраняет return-intent
    и ведёт на `/(auth)/phone`.
  - **никто, `!hasContacts`** — ничего не показываем (как сейчас) — не
    обещаем контакт, которого у специалиста нет (§5 `design-quality.md`).
  - Размещение **сразу под шапкой**, а не в самом низу под отзывами: это и
    есть главное действие гостя на этом экране (приоритет 1.1
    `design-quality.md` — «одно главное действие», и оно должно быть видно
    без скролла, как «Показать телефон» у Авито, не найдено только после
    долгого чтения профиля).
- Return-flow для гостя: по образцу `RespondAuthSheet.tsx` —
  `parseAuthReturnTo` + `useAuthReturnUrlStore`. Сейчас allowlist в
  `src/features/auth/auth-return.ts` разбирает только `/orders/new` и
  `/orders/<uuid>` — нужно расширение регулярки на `/master/<uuid>` (по тому же
  шаблону, что уже есть для заказов). Это код, не входит в зону этого
  документа, но без него «возврат на профиль» не сработает — фиксирую как
  обязательный пункт для `xtrud-implementer`.
- **Цена:** малая. Один экран, один новый мелкий компонент (карточка-призыв,
  переиспользует токены и паттерн кнопки «Войти» из уже существующих
  экранов), один util уже есть, одна строка regex в `auth-return.ts`. Риск
  регресса — только этот файл и этот RPC/вызов.

### Вариант B — унификация заголовков секций по всему приложению + гистограмма рейтинга

- То же самое, но заголовок секции выносится в общий компонент и переиспользуется
  везде, где сегодня есть похожие ad hoc заголовки (`client/[id].tsx` и другие
  detail-экраны), плюс добавляется агрегат распределения оценок по звёздам
  (новый `GROUP BY rating` запрос — не N+1, разовый, но новая серверная
  работа) для App Store-подобной гистограммы.
- **Цена:** выше — трогает экраны, не названные в этой задаче (нарушает «одна
  причина изменения», `working-rules.md` §2), требует отдельного QA-прогона
  по каждому затронутому экрану и отдельного решения по новому агрегату.

### Решение

**Вариант A.** Он закрывает буквально то, что просил владелец (надпись-призыв
для гостя, более стильный и единый вид), не трогая экраны, которых не касалась
просьба. Унификация заголовка секций по всему приложению и гистограмма
рейтинга — ценные, но отдельные задачи; предлагаю занести их в `TASKS.md` как
backlog, а не делать прямо сейчас заодно.

### Токены и отступы

- Горизонтальный отступ карточки-призыва — `px-4`, как весь остальной экран
  (решение владельца: отступ от края 16 pt везде).
- Фон карточки — `bg-canvas-soft` (тот же, что уже используют соседние
  карточки на этом экране), текст — `text-ink`/`text-mute`, кнопка — `bg-accent`
  / `text-on-accent`, иконка замка — `tc.mute` (вторична, не самая яркая деталь
  карточки — это текст и кнопка).
- Обе темы — токены берутся из `src/lib/colors.ts`, отдельного прохода не
  требуется: карточка использует только уже проверенные в этом файле токены.

## 5. Блокер для безопасности (не дизайн-решение — фиксирую как находку)

Карточка-призыв решает **интерфейс**. Она не решает то, что `get_master_phone`
и колонка `whatsapp_phone` сегодня отдаются анониму без проверки — см. §1.6.
Если это не будет закрыто на бэкенде, результат — «витрина»: гость видит
красивый призыв войти, но тот же номер доступен тем же RPC/запросом в обход
экрана. Нужно явное решение владельца/`xtrud-security`:

- RPC `get_master_phone` должен проверять `auth.uid() IS NOT NULL` (или новый
  вариант сигнатуры), прежде чем отдавать номер — это меняет поведение,
  зафиксированное `DECISION 2026-05-20 («classifieds»)`, и значит требует
  нового явного DECISION, а не тихой правки функции.
- `whatsapp_phone` в `master_profiles` нужно либо убрать из публичного
  `select`, либо завести отдельный RPC с той же проверкой входа, аналогично
  `get_master_phone`.
- Если владелец решит оставить контакты полностью публичными на уровне
  данных (например, умышленно — номер легко найти и так), тогда карточка-призыв
  вводит пользователя в заблуждение заявлением «нужен вход», и тогда сам
  запрос этой задачи нужно обсудить повторно, а не достраивать красивый UI на
  факте, который бэкенд не подтверждает.

Это прямо попадает в приоритет №1 `design-quality.md` («Требования App Store и
безопасность пользователя») — выше любого визуального решения в этом
документе.

## 6. Приёмочный чек-лист (docs/IOS_FOUNDATION.md §10, под эту правку)

1. Light/dark на реальном iPhone — `UNKNOWN`, устройства не было в рамках этой
   задачи (только спецификация).
2. Dynamic Type Large и AX3 — карточка-призыв и правленые заголовки секций не
   обрезаются, кнопка «Войти» растёт по высоте, а не по ширине текста.
3. VoiceOver — карточка-призыва должна озвучиваться одним логическим блоком
   («Войдите, чтобы увидеть контакты. Позвонить или написать можно после
   входа. Кнопка Войти»), не тремя разрозненными элементами.
4. Тач-цель кнопки «Войти» ≥ 44×44 pt (pill `min-h-14` — заведомо больше).
5. Нет хардкода цвета — все цвета карточки из `src/lib/colors.ts`.
6. Reduce Motion — переход на `/(auth)/phone` не вводит собственной анимации
   сверх системной навигационной.
7. Склонение «N отзыв(ов)» проверено для 1, 2, 5, 11, 21, 22 — через
   `pluralizeReviews`, не вручную.
8. Пустое «О себе» не рисует секцию без текста.
9. Гость с контактами видит карточку-призыв и НЕ видит номер/WhatsApp ни в
   UI, ни (после бэкенд-правки из §5) в сетевом ответе на этот экран.
10. `npm run quality:check` — после реализации (не выполнялось в рамках этой
    спецификации, т.к. код не менялся).

### Что проверить на iPhone (отдельно от симулятора)

- Реальный тап «Войти» из карточки-призыва → вход по телефону → возврат
  именно на этот профиль специалиста, не на главный экран.
- VoiceOver на реальном устройстве (симулятор VoiceOver отличается от
  устройства по таймингам).
- Самый крупный размер шрифта через Settings → Accessibility → Larger Text →
  максимум, не через проп в коде.
