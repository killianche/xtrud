# Мобильная доска заданий xtrud

Канонический UX-контракт текущего мобильного MVP. YouDo, Profi.ru и другие
сервисы используются только как функциональные референсы; визуальный язык,
компоненты и тексты остаются оригинальными для xtrud.

## FACT — что уже поддерживает текущая модель

- один аккаунт может быть клиентом и исполнителем;
- клиент публикует задание с категорией, описанием, фотографиями, местом,
  сроком и бюджетом;
- исполнитель видит открытые задания и отправляет один отклик: сообщение,
  цену и необязательный срок;
- клиент сравнивает отклики и сам инициирует звонок или WhatsApp;
- номер клиента исполнителю не раскрывается;
- backend-сущности пока называются `orders` и `order_responses`. Это внутренние
  технические имена, а не обязательный пользовательский текст.
- desktop-скриншоты YouDo подтверждают информационную архитектуру категорий и
  разделение контекстов, но не меняют mobile-first решение и не являются
  макетом для визуального копирования.

## DECISION — вертикальный сценарий MVP

1. Клиент нажимает заметный CTA «Создать задание» на главной и начинает с
   собственных слов: «Что нужно сделать?». Детерминированный category search
   показывает вариант названия вместе с категорией только для уникального
   точного `synonym + score=1`. Любой prefix/FTS/trigram, несколько точных L2
   или более слабый term переводят flow в явное уточнение: до трёх уникальных
   категорий и «Все категории». Числовые «проценты уверенности» не выдумываются.
   Категория фиксируется только после явного тапа; скрытого автоприсвоения нет.
2. Создание — шесть настоящих native Stack route (DECISION владельца
   2026-09-06, «с нуля, как у TaskRabbit и iOS»): `/orders/new` (что нужно
   сделать) → `/orders/new/details` (подробности и фото) → `/orders/new/where`
   → `/orders/new/when` → `/orders/new/budget` → `/orders/new/review`
   (сводка, имя и контакты, публикация). Один вопрос на экран; Back и iOS
   edge-swipe выполняют один POP и сохраняют черновик. «Далее» включается,
   только когда шаг заполнен. Для проверенных категорий подсказка описания
   адаптируется; если конфигурации нет, остаётся универсальное поле.
3. Публикация задания бесплатна. В текущем локальном MVP действует временный
   UX-лимит 3 открытых задания на аккаунт. Клиент проверяет лимит перед
   отправкой, но это не защита от гонки двух устройств: авторитетный лимит
   появится только forward-only backend-миграцией после snapshot/backup.
4. Исполнитель открывает ленту «Задания». Вся строка задания является одной
   зоной перехода; дублирующей кнопки «Откликнуться» в каждой строке нет.
5. Карточка задания показывает в порядке важности: статус и категорию,
   название, бюджет, место/срок, фотографии и описание.
6. Отклик отправляется только из карточки задания. Для фиксированной цены,
   «от» и «до» положительная сумма обязательна; «по договорённости» не требует
   суммы.
7. Клиент видит плоский сравнимый список исполнителей: имя, рейтинг, цена,
   срок и сообщение. Контакты загружаются только после явного действия клиента,
   чтобы список откликов не создавал N+1 запросов; профиль доступен сразу.
8. Если обычный клиент хочет откликнуться, он проходит один последовательный
   onboarding исполнителя: профиль → категории → фотография. Отклик не
   отправляется автоматически после onboarding.
9. Один аккаунт сохраняет обе возможности. «Заказчик» и «исполнитель» — это
   контексты работы и разделы «Мои задания / Мои отклики», а не два аккаунта.
10. Лента использует стабильный серверный порядок `created_at DESC, id DESC` и
   составной cursor. Сортировку «срочные сверху» нельзя имитировать внутри уже
   загруженных страниц: она появится только с серверным ranking/query contract.
11. Категории показываются в два уровня: понятная крупная категория и конкретная
   услуга. Новый универсальный каталог не включается до отдельного проверенного
   backend rollout; списки конкурентов не копируются как продуктовый scope.

## Визуальный контракт

- mobile-first, системный шрифт, Phosphor и токены xtrud;
- светлая и тёмная темы обязательны;
- плоские full-bleed строки с hairline-разделителями вместо набора карточек с
  тенями;
- один главный CTA на экран, важные действия находятся в thumb-zone;
- фотографии — содержательная часть задания и профиля, а не декор;
- loading, empty, error, disabled и already-responded состояния обязательны;
- для длинной ленты используется виртуализация, а не `ScrollView.map`.

## Язык интерфейса

- пользовательская сущность: «задание»;
- человек, который выполняет работу: «исполнитель»;
- «мастер» допустим в существующем профильном и строительном контексте, пока
  внутренние модели и весь текущий scope не переведены безопасно;
- персональная подборка называется «По вашим категориям» только когда это
  действительно доказано фильтром категорий. Нельзя писать «Для вас» или
  «Рекомендуем», если ранжирование этого не подтверждает.

## Не входит в текущий MVP

- in-app чат;
- выбор победителя и состояние «исполнитель назначен»;
- lifecycle сделки, спор и подтверждение выполнения;
- escrow, комиссия и платформенные платежи;
- платная публикация или платные отклики в текущем MVP;
- генеративная классификация/переписывание пользовательского текста: intent
  suggestions строятся детерминированно по видимому каталогу;
- автоматическое назначение категории по слабому score: если точного
  однозначного словарного совпадения нет, решение всегда подтверждает человек;
- универсальные 10 L1, `work_mode`, unknown-category и новое matching API до
  отдельного backend rollout;
- сортировка по срочности/релевантности до серверного контракта и тестов
  стабильной пагинации;
- изменение production Supabase без live read-only проверки, backup и
  forward-only migration.

## Offline-контракт создания задания

- Backend-каталог всегда запрашивается первым. Успешный пустой ответ считается
  авторитетным и не заменяется локальными данными.
- При подтверждённом transport/DNS/timeout-сбое разрешён только generated
  release snapshot публичных active/visible L2/L3/terms текущего scope. Он не
  редактируется вручную и проходит SHA/reference/duplicate gate. Ошибки Auth,
  RLS и API-контракта snapshot не скрывает.
- Offline-источник явно обозначается пользователю. Он помогает подобрать и
  подтвердить категорию для локального черновика, но не создаёт локальный
  заказ и не показывает success.
- Перед любой загрузкой фото и insert категория и реальный город свежим
  read-only запросом проверяются на authoritative backend; «Вся Ингушетия»,
  районы и сёла проверяются по каноническому location-контракту. При
  недоступности backend публикация fail-closed, а owner-bound поля черновика не
  очищаются.
- Полный cold start гостя не показывает сохранённый PII-draft: guest snapshot
  карантинируется до защищённого auth-return. Для авторизованного владельца
  действует существующий TTL 14 дней.

## Проверка каждого изменения

- iOS preview/device — основной контур;
- Android отложен явным решением владельца от 2026-08-26 и не входит в текущий
  iOS-срез; перед Android-релизом для него будет отдельный полный gate;
- обе темы и узкий мобильный viewport;
- schema/unit tests, TypeScript, Biome и production-mode JS export;
- независимые design, QA и code-review решения GO/NO-GO.
