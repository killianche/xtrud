# Новый агент в xtrud — что знать в первый час

> Читается один раз перед первой правкой. Не заменяет `AGENTS.md`
> (порядок чтения) и `.claude/rules/` (правила работы), а собирает то, на чём
> здесь чаще всего ошибаются.

## 1. Где всё живёт

- Работа идёт **на VDS**, каталог `/root/projects/xtrud`. Машина владельца не
  используется никогда: ни файлы, ни браузер, ни сборка.
- Ветки: `master` — рабочая, `main` — с неё запускается сборка iOS. Пушить в
  обе: `git push origin master && git push origin master:main`.
- Сервер продукта — Beget `217.114.8.196`, доступ `ssh xtrud-beget`.
- Продукт: маркетплейс услуг для Ингушетии. Клиент публикует задание,
  специалист откликается, дальше созваниваются. Чата внутри нет.

## 2. Архитектура за одну минуту

| Слой | Что это | Где код |
|---|---|---|
| Приложение | Expo SDK 57, iOS главная платформа | `app/`, `src/` |
| Клиент данных | свой, не supabase-js | `src/lib/xtrud-client`, вход через `@/lib/supabase` |
| API | Node 22 + Fastify на Beget, `api.xtrud.pro/v2` | `server/` |
| База | PostgreSQL 17: схема, RLS, функции `admin_*`, триггеры | `supabase/migrations/`, черновики в `migration-drafts/` |
| Файлы | диск сервера `/opt/xtrud/files`, превью — свой imgproxy | `server/src/files`, nginx |
| Панель | веб-админка на том же API | `admin/` |

Правила доступа живут **в базе** (RLS и `SECURITY DEFINER`), а не в
приложении. Кнопка в интерфейсе — только подсказка; право проверяет сервер.

## 3. Пять ошибок, которые здесь уже совершали

1. **Гадать имя колонки, статуса или функции.** Проверяй в базе или в
   `src/types/database.ts`. Было: `blocked` вместо `banned`, `open` вместо
   `pending` — уронило админку.
2. **Считать документ свежее кода.** При расхождении прав код и живая база;
   документ правится следом.
3. **Забыть `git add app.json`** при сборке — номер не попадёт в коммит, и
   сборка упадёт на гейте версий (`docs/RELEASE_RUNBOOK.md`).
4. **Запускать вторую сборку, когда одна ждёт в очереди** — GitHub отменит
   ожидающую. Сначала посмотреть список прогонов.
5. **Ставить `npm run quality:check` до последней правки.** Проверка
   действительна только после неё.

## 4. Дизайн: чему следовать

- Эталон — iOS 26 и системные приложения Apple. Таблица соответствий:
  `docs/IOS_FOUNDATION.md` §0. Сначала ищем системный аналог, потом рисуем.
- Цвета, отступы, радиусы — только токены (`src/lib/colors.ts` →
  `global.css`). Хардкод цвета в компоненте — дефект.
- Экран не готов без состояний: загрузка, пусто, ошибка с действием,
  нет входа, длинный текст, крупный шрифт.
- Простота важнее полноты: лишняя функция — дефект. Убрать лучше, чем
  добавить (`.claude/rules/design-quality.md`).
- Интерфейс не утверждает непроверенного: нет данных — нет значка,
  рейтинга и «популярного».

## 5. Как заканчивается задача

1. `npm run quality:check` в корне (плюс `npm run check` в `server/`, если
   трогал сервер).
2. Коммит по-русски: что и почему, со ссылкой на решение владельца.
3. Сборка и выкладка в TestFlight — без вопросов
   (`docs/RELEASE_RUNBOOK.md`), номер сборки +1.
4. Запись в `TASKS.md`: очередь запросов владельца в начале файла и пункт
   этапа; крупное — в `CHECKLIST.md` человеческим языком.
5. Отчёт владельцу: что сделано, что проверено с реальным результатом, что
   осталось `UNKNOWN`. Без обещаний вместо фактов.

## 6. Что нельзя без слова владельца

Удалять данные, подавать версию в App Store или отзывать заявку, менять DNS
и модель продукта, публиковать в чужие группы TestFlight, запускать агентов
дольше 30 минут (`.claude/rules/agent-delegation.md` §3.1).
