# Жизненный цикл заказа клиента — план (экран «Мои заказы»)

**TL;DR.** xtrud сейчас работает как доска объявлений (как Avito Услуги): клиент выкладывает заказ → мастера откликаются → клиент звонит/пишет в WhatsApp напрямую. Внутри приложения мастера не «принимают», сделки не ведут. Для такой модели заказу нужно всего **3 состояния** — «Открыт», «Закрыт», «Истёк» — и **3 действия** клиента: «Редактировать», «Закрыть» (нашёл мастера / больше не нужно), «Удалить». Этот документ описывает текущее состояние, что в нём сломано/недоделано, и финальную модель для дизайнера и инженера.

**Имя для запроса:** «жизненный цикл заказа клиента», «мои заказы», «закрыть/удалить/завершить заказ».

**Кому читать:** продакт (утвердить модель), дизайнер (бриф в §8), инженер (план в §7).

**Связанные файлы:** `app/(tabs)/orders/index.tsx`, `app/(tabs)/orders/[id].tsx`, `src/features/orders/use-cancel-order.ts`, `src/components/OrderStatusBadge.tsx`, `docs/SIMPLE_FLOW.md`, `docs/lifecycle.md` (legacy).

## 1. Текущее состояние (что реально есть в коде)

### Экран «Мои заказы» (`app/(tabs)/orders/index.tsx`)
- Два таба: **«Открытые»** (только статус `open`) и **«Архив»** (всё остальное: `cancelled`, `expired` + legacy `completed/in_progress/awaiting_confirmation/disputed/closed`).
- Кнопка «Создать» в шапке. У каждого таба есть счётчик.
- Состояния: загрузка (крутилка), ошибка (текст + «Повторить»), пусто (заголовок + текст + кнопка «Разместить заказ» на активном табе).
- Таб «Черновики» убран 2026-05-20.

### Карточка заказа (`app/(tabs)/orders/[id].tsx`)
- Шапка: статус-плашка + категория + крупный заголовок + срочность + город + бюджет + описание.
- Меню действий (иконка «три точки») для владельца:
  - **«Редактировать заказ»** — только если `open`.
  - **«Закрыть заказ»** — только если `open`. Под капотом это `useCancelOrder` (переводит заказ в `cancelled`).
- Баннер **«Уже нашли мастера?»** (`CloseOrderHint`) — показывается если заказ открыт ≥ 24 часов и есть хотя бы 1 отклик. Кнопка ведёт в тот же «Закрыть заказ» (→ `cancelled`).
- Список откликов мастеров: имя, рейтинг, цена, текст, кнопки **«Позвонить» / «WhatsApp» / «Профиль»**, плюс «Не подходит» (скрыть отклик) и сворачиваемый блок «Скрытые отклики».

### Что реально делает «Закрыть заказ»
`useCancelOrder` (`src/features/orders/use-cancel-order.ts`) делает прямое обновление: `status → 'cancelled'`. Срабатывает триггер в базе, который отзывает все активные отклики мастеров и шлёт им уведомление «заказ закрыт». **Никакой пометки причины** (нашёл мастера / передумал) — всё валится в одну корзину `cancelled`.

### Что есть в базе данных (проверено на живой базе)
- Поле статуса (`order_status`) имеет **8 значений**: `draft, open, in_progress, awaiting_confirmation, completed, disputed, cancelled, expired`.
- Реальное распределение заказов сейчас: `open` — 11, `completed` — 11, `in_progress` — 2, `expired` — 2. То есть `completed/in_progress` — это **демо-данные старой модели**, новый интерфейс их больше не создаёт.
- Новый заказ автоматически получает срок жизни: `expires_at = создан + 14 дней`.
- **Ночные авто-задачи в базе включены и работают:**
  - `nightly_expire_orders` (03:00) — открытый заказ старше 14 дней → `expired`. **Это работает в текущей модели.**
  - `nightly_cancel_stale` (05:00) и `nightly_auto_confirm` (04:00) — относятся к статусам `in_progress/awaiting_confirmation`, которых новый интерфейс не создаёт. Работают только над legacy-данными, новых заказов не касаются. Безвредны, но это «висящий» механизм.

## 2. Сверка `lifecycle.md` (legacy) против реальной модели

`docs/lifecycle.md` описывает **сложную сделку-платформу** из 8 статусов, 15 переходов, споров, эскроу-подобного подтверждения, кармы и т.д. **Это устаревший документ.** Решение 2026-05-20 (`SIMPLE_FLOW.md`) откатило продукт к доске объявлений. Ниже — что из `lifecycle.md` мёртво в текущей модели.

| Из `lifecycle.md` | Статус в classified-ads модели |
|---|---|
| `draft` | **Не используется.** Таб черновиков убран, клиент публикует сразу. |
| `open` | **Живой.** Главный рабочий статус. |
| `in_progress` | **Мёртвый в новом интерфейсе.** Создавался при «выбрать мастера» (accept_response) — этого действия больше нет. Остался только на демо-данных. |
| `awaiting_confirmation` | **Мёртвый.** Нет шага «мастер отметил выполнено». |
| `completed` | **Мёртвый в новом интерфейсе.** Нет шага подтверждения. Остался на демо-данных. |
| `disputed` | **Мёртвый.** Споров нет. |
| `cancelled` | **Живой.** Сейчас это единственный исход «закрытия» заказа клиентом. |
| `expired` | **Живой.** Авто-истечение через 14 дней работает. |

| Механизм из `lifecycle.md` | Реальность |
|---|---|
| Выбор мастера (accept_response) | Удалён из интерфейса (база сохранила RPC). |
| Подтверждение выполнения, споры, авто-подтверждение | Удалены из интерфейса. |
| Окно отзывов 14 дней, double-blind | **В базе есть таблица `reviews` и хук `useSubmitReview`, но в интерфейсе клиента он нигде не вызывается.** Отзывы фактически недоступны клиенту. |
| Возобновление заказа (reopen) | Хук `use-reopen-order.ts` есть, но в интерфейсе не подключён. |
| Карма / penalty | Не реализовано. |

**Вывод:** `lifecycle.md` нужно пометить как «legacy / на случай возврата к сделке-платформе» и не использовать как руководство для текущего интерфейса. Источник истины сейчас — `SIMPLE_FLOW.md` + этот документ.

## 3. Спроектированный жизненный цикл заказа клиента (финал)

Для доски объявлений достаточно **трёх состояний**. Имена в базе оставляем как есть (не трогаем структуру), меняем только смысл и подписи в интерфейсе.

| Состояние (в базе) | Что показываем клиенту | Смысл | Как наступает |
|---|---|---|---|
| `open` | **«Открыт»** | Заказ опубликован, мастера видят его и откликаются. | Создание заказа. |
| `cancelled` | **«Закрыт»** | Клиент закрыл заказ сам (нашёл мастера ИЛИ передумал). Это норма, не «провал». | Клиент нажал «Закрыть заказ». |
| `expired` | **«Истёк»** | Прошло 14 дней без закрытия — заказ убран из ленты автоматически. | Авто-задача в базе. |

**Удаление** — это не статус, а отдельное действие (заказ исчезает из «Моих заказов» совсем). Подробно — §4.

### Граф переходов (простой)

```
                 создать заказ
                      │
                      ▼
                 ┌─────────┐
   редактировать │  Открыт │
   (пока открыт) │  (open) │
                 └──┬───┬──┘
       «Закрыть»    │   │   14 дней без действий (авто)
                    ▼   ▼
            ┌──────────┐  ┌──────────┐
            │  Закрыт  │  │  Истёк   │
            │(cancelled)│ │(expired) │
            └────┬─────┘  └────┬─────┘
                 │             │
            «Удалить»     «Удалить» / «Открыть заново»*
                 ▼             ▼
            (заказ исчезает из списка)

* «Открыть заново» — опционально, см. §6 и §7.
```

### Таблица «состояние → доступные действия клиенту»

| Действие | Открыт (`open`) | Закрыт (`cancelled`) | Истёк (`expired`) |
|---|---|---|---|
| Смотреть отклики, звонить/писать мастерам | **Да** | Да (только просмотр, отклики уже не приходят) | Да (только просмотр) |
| Скрыть отклик («Не подходит») | **Да** | Нет | Нет |
| **Редактировать** | **Да** | Нет | Нет |
| **Закрыть заказ** | **Да** | — (уже закрыт) | — (уже истёк) |
| **Удалить** | Нет¹ | **Да** | **Да** |
| **Открыть заново** (опц., см. §6) | — | Да² | Да² |
| Пожаловаться | (только чужой заказ) | — | — |

¹ Открытый заказ нельзя удалить напрямую — сначала «Закрыть», потом «Удалить». Это защищает от случайного удаления активной заявки с откликами. Так делают Avito и Profi (открытое объявление сначала снимаешь с публикации, потом удаляешь). Альтернатива — разрешить удаление сразу с двойным подтверждением; решение за продактом (§11).
² «Открыть заново» доступно ограниченное время (предлагаем 7 дней), потом только новый заказ.

## 4. Действия клиента — чёткие определения

Сейчас в интерфейсе всё свалено в одно: «Закрыть заказ» = `cancelled`, а «Удалить» и «Завершить» отсутствуют, хотя владелец продукта их ожидает. Разводим понятия.

### «Закрыть заказ» (бывшее «Завершить» + «Отменить» в одном)
- **Когда доступно:** заказ `open`.
- **Что делает:** переводит заказ в `cancelled`, отзывает активные отклики, мастера получают уведомление «заказ закрыт» и больше не пишут. Заказ уезжает из «Открытых» в «Историю».
- **Подтверждение:** да, диалог с пояснением.
- **Что с откликами мастеров:** все активные отклики гасятся (мастера уведомлены). Контакты, которые клиент уже получил (телефон/WhatsApp), у него остаются — он может позвонить даже после закрытия.

  **Важное продуктовое уточнение — две причины закрытия в одном экране.** При нажатии «Закрыть» показываем выбор причины (это и есть замена «Завершить» vs «Отменить»):
  - **«Нашёл мастера»** — позитивный исход. (Здесь же — опциональный шаг «оставить отзыв», см. §5.)
  - **«Больше не нужно / передумал»** — нейтральный исход.

  Технически оба ведут в `cancelled`, но причину сохраняем в поле `cancel_reason` (оно уже есть в базе). Это даёт честную статистику «сколько заказов реально закрылись успехом» и в будущем — отзывы только по «нашёл мастера».

### «Удалить заказ»
- **Когда доступно:** заказ уже `cancelled` или `expired` (т.е. в «Истории»). Открытый заказ удалить нельзя — сначала «Закрыть».
- **Что делает:** заказ исчезает из «Моих заказов» навсегда. Рекомендуем **мягкое удаление** (скрытие через флаг `deleted_at`/`hidden`), а не физическое стирание строки — чтобы не терять историю и статистику платформы. Для клиента визуально — «удалён».
- **Подтверждение:** да, явное («Удалить навсегда?»).
- **Что с откликами:** они и так уже погашены (заказ был закрыт/истёк). Ничего дополнительно не происходит.

### «Открыть заново» (опционально, рекомендуем включить — см. §6)
- **Когда доступно:** заказ `cancelled` или `expired`, и с момента закрытия прошло не больше 7 дней.
- **Что делает:** возвращает заказ в `open`, продлевает срок жизни ещё на 14 дней, заказ снова в ленте мастеров.
- **Подтверждение:** не обязательно (действие безопасное и обратимое).

### Почему так у лидеров рынка
- **Avito Услуги / Profi.ru:** объявление сначала «снимается с публикации» (аналог «Закрыть»), и только потом «удаляется». Открытое активное объявление нельзя стереть одним тапом — защита от потери заявки с откликами.
- **TaskRabbit / Thumbtack:** разделяют «task completed» (успех) и «cancel task» (отмена) — это и есть наш выбор причины при закрытии.

## 5. Решение по «Завершить» + отзыв

**Проблема.** В доске объявлений нет шага «клиент выбрал мастера X». Значит при «Завершить»/«нашёл мастера» приложение не знает, **какого** мастера оценивать.

**Рекомендация (двухшаговый, но необязательный отзыв):**

1. Клиент жмёт «Закрыть» → выбирает причину **«Нашёл мастера»**.
2. Сразу после этого показываем экран/шит **«Кого вы выбрали?»** со списком мастеров, которые **откликнулись** на этот заказ (мы их знаем — это `order_responses`). Клиент тапает по одному. Можно пропустить («Пропустить»).
3. Если мастер выбран → предлагаем оставить отзвыв (звёзды + короткий текст). Тоже можно пропустить.
4. Если мастер не из списка откликнувшихся (клиент нашёл его не через приложение) → вариант «Мастера не было в списке / нашёл сам» — тогда отзыв не предлагаем.

**Почему так:**
- Мы можем достоверно привязать отзыв к мастеру **только если он откликался** (есть запись отклика). Это честно и без выдумывания.
- Отзыв **необязателен** — в малом регионе люди неохотно оставляют публичные оценки сразу; принуждение убьёт конверсию закрытия заказа.
- **У лидеров:** Avito и Profi.ru просят отзыв именно постфактум и из списка тех, с кем был контакт; пропуск всегда разрешён. TaskRabbit/Thumbtack привязывают отзыв к конкретному tasker'у, с которым была сделка.

**Что нужно в базе:** таблица `reviews` и хук `useSubmitReview` уже есть — их надо просто **подключить** к этому флоу (сейчас они в интерфейсе клиента не используются — это «готовый бэк, не подключён в UI», классическая дыра по `connect-the-dots`). Привязка отзыва к мастеру — через выбранного из списка откликов.

**Минимальный вариант (если продакт хочет проще для теста):** при «Нашёл мастера» отзыв не собираем вообще, просто закрываем заказ. Тогда отзывы — отдельная задача на потом. Но рекомендуем сразу подключить, т.к. отзывы — главный двигатель доверия на маркетплейсе и весь бэкенд готов.

## 6. Решение по «Архив»

**Проблема владельца:** «Архив — не до конца понимаю зачем».

**Рекомендация:** оставить два таба, но **переименовать** для ясности:

- **«Активные»** (вместо «Открытые») — заказы `open`, по которым ещё идут отклики.
- **«История»** (вместо «Архив») — `cancelled` + `expired`. Внутри визуально отделять: закрытые клиентом и истёкшие (разные подписи на плашке: «Закрыт» / «Истёк»).

Почему «История», а не «Архив»: «архив» звучит как «спрятанное навсегда / служебное», а здесь — обычная лента прошлых заказов, по которым ещё можно посмотреть отклики, удалить или открыть заново. «История» точнее передаёт смысл.

**Что попадает в «Историю»:**
- Закрытые клиентом (`cancelled`) — с под-подписью причины, если выбрана («Нашёл мастера» / «Закрыт»).
- Истёкшие (`expired`).
- Legacy demo-заказы (`completed/in_progress`) — показываем нейтрально «Закрыт» (как сейчас в `OrderStatusBadge`), не падаем.

**Почему два таба, а не один список с фильтром:** в Lazyweb-выдаче (Poshmark, eBay, Rebag, Bins, Craigslist) у всех досок объявлений именно **сегментированный контрол по статусу** (Active / Sold / Inactive). Это устоявшийся паттерн, пользователю понятен. Один общий список с перемешанными активными и закрытыми — хуже для сканирования.

**Lazyweb:** искал «my listings classified ads marketplace seller manage active and archived posts», посмотрел 6 экранов (Poshmark, eBay, Rebag, Bins, Craigslist). Везде сегментированный статус-контрол (Active / Sold / Inactive / Unlisted). Переиспользуем: два сегмента «Активные / История». Делаем иначе: не добавляем третий сегмент (нет «черновиков» и «проданного» как отдельных сущностей).

3. ✅ **Шит «Закрыть заказ»** с выбором причины (две кнопки: «Я нашёл мастера» / «Больше не нужно»). СДЕЛАНО 2026-05-21 — `CloseReasonSheet` в `[id].tsx`.
4. ⚠️ **Флоу «Кого выбрали → отзыв»** (после «Нашёл мастера»): список откликнувшихся мастеров → звёзды + текст → «Готово»/«Пропустить». **ОТЛОЖЕНО** решением владельца (отдельная задача) — дизайнеру.
5. ✅ **Состояния пустого экрана** обновлены под новые названия («В истории пока пусто», «Активных заказов нет»). СДЕЛАНО 2026-05-21.
6. 💡 **Плашки в «Истории»** различать «Закрыт» (нашёл мастера) / «Закрыт» (передумал) / «Истёк» — мелкая, но полезная ясность.

### Приоритеты (словами для владельца)
- **Срочно, до показа:** причина закрытия (п.A4), действие «Удалить» (п.A5), переименование табов (п.B1), перестройка меню (п.B2-B3). Это закрывает прямой запрос «отменить / удалить / завершить».
- **Важно, сразу за этим:** отзыв при «Нашёл мастера» (п.A6, B4) — главный двигатель доверия, бэкенд готов.
- **Можно потом:** «Открыть заново» (п.A7), различение плашек (п.B6), чистка мёртвого механизма и кода (п.A8-A9).

## 8. Бриф для дизайнера

Отрисовать в обеих темах (светлая + тёмная), уровень Vercel/Linear, без подзаголовков под H1:

1. **Экран «Мои заказы»** — два сегмента «Активные» / «История» (счётчики). Карточка заказа в списке: заголовок, категория, город, срочность, бюджет, число откликов, плашка статуса. Состояния: пусто / загрузка / ошибка для обоих сегментов.
2. **Карточка заказа (детали) — меню действий** (нижний шит «три точки»):
   - для открытого: «Редактировать заказ», «Закрыть заказ» (красным);
   - для закрытого/истёкшего: «Открыть заново» (опц.), «Удалить» (красным).
3. **Шит «Закрыть заказ»** — заголовок-вопрос + две крупные кнопки выбора причины: «Я нашёл мастера» и «Больше не нужно». Без подзаголовков.
4. **Флоу отзыва** (после «Я нашёл мастера»): шаг 1 — список откликнувшихся мастеров (аватар, имя, рейтинг, цена из отклика) с одиночным выбором + «Я нашёл мастера не здесь / пропустить»; шаг 2 — звёзды (1–5) + поле короткого отзыва + кнопки «Отправить» / «Пропустить».
5. **Плашки статуса в «Истории»** — визуально отличить «Закрыт» / «Истёк» (нейтральные серые тона, без тревожного красного — это нормальные исходы).

Референсы для дизайнера: классифайды (Avito Услуги — «Мои объявления» с табами «Активные/Завершённые», снятие и удаление); Profi.ru / YouDo — «Мои заказы» + постфактум-отзыв из списка откликнувшихся; TaskRabbit/Thumbtack — разделение «completed» vs «cancel» и привязка отзыва к конкретному исполнителю.

## 9. Референсы (как у лидеров рынка)

| Решение | Кто и как делает |
|---|---|
| **Два таба «Активные / История»** | Avito «Мои объявления» (Активные / Завершённые / Архив). Lazyweb: Poshmark, eBay, Rebag, Bins, Craigslist — у всех сегментированный статус-контрол. |
| **«Закрыть» сначала, «Удалить» потом** | Avito, Profi.ru — открытое объявление снимается с публикации, и лишь затем удаляется. Защита от потери активной заявки. |
| **Причина закрытия: «нашёл» vs «передумал»** | TaskRabbit / Thumbtack — «task completed» против «cancel task». Профи.ру спрашивает «нашли исполнителя?» при закрытии. |
| **Отзыв постфактум, необязательный, из списка контактов** | Profi.ru / YouDo / Яндекс Услуги — после закрытия предлагают оценить исполнителя из тех, с кем был контакт; пропуск всегда доступен. |
| **Авто-истечение объявления** | Avito Услуги — объявление само уходит в архив по сроку. У нас 14 дней (бенчмарк Profi.ru/YouDo). |

## 10. Что НЕ делаем (вне модели доски объявлений)

Чтобы не вернуть случайно сложную сделку-платформу: статусы «в работе», «ожидает подтверждения», «спор»; выбор мастера внутри приложения; внутренний чат; авто-подтверждение выполнения; карма/штрафы. Всё это — в `lifecycle.md` как «на будущее». Если рынок попросит — возвращается через `SIMPLE_FLOW.md` способ восстановления, база менять не нужно.

## 11. Открытые вопросы продакту

1. **Удаление открытого заказа:** запрещаем (сначала «Закрыть») или разрешаем с двойным подтверждением? *Рекомендация: запрещаем, как Avito.*
2. **«Открыть заново»:** включаем сейчас (бэкенд готов) или откладываем? *Рекомендация: включить, дёшево и полезно.*
3. **Отзыв при закрытии:** делаем сразу (рекомендуется) или сначала только причину закрытия, отзыв — отдельной задачей?
4. **Мягкое vs физическое удаление:** рекомендуем мягкое (флаг скрытия) ради сохранения статистики. Подтвердить.
5. **Авто-задачи `nightly_cancel_stale`/`nightly_auto_confirm`:** оставить висеть (безвредны, на случай возврата сделки) или выключить ради чистоты?
