## 1. Инвентаризация as-is

### 1.1. Значения в данных (FACT — `src/types/database.ts`)

| Enum | Значения | Строка |
|---|---|---|
| `order_status` | `draft, open, in_progress, awaiting_confirmation, completed, disputed, cancelled, expired` | database.ts:1877 |
| `response_status` | `sent, viewed, accepted, rejected, withdrawn` | database.ts:1903 |
| `review_status` | `visible, hidden, pending` | database.ts:1905 |
| `review_direction` | `client_to_master, master_to_client` | database.ts:1904 |
| `notification_type` (относится к заданиям) | `new_response, order_accepted, order_cancelled, order_expired` | database.ts:1866-1869 |

**Что из этого реально достижимо из приложения (FACT, прослежено по коду):**

- `draft` — задание до публикации. Не показывается в списках (черновик существует только в форме).
- `open → in_progress` — `pick_order_master` RPC, только клиент, только из `open` (0196:39-79).
- `in_progress → open` — `unpick_order_master` RPC («Отказаться от исполнителя», 0196:85-127).
- `in_progress → completed` — `complete_order` RPC, только клиент (0196:133-165). Без промежуточного подтверждения мастером — клиент отмечает сам, сразу.
- `open/in_progress → cancelled` — «Закрыть задание» (`app/(details)/orders/close-reason.tsx`).
- `→ expired` — cron по сроку публикации.
- `cancelled/expired → open` — `reopen_order` RPC, окно 7 дней (0197:66-101).
- `awaiting_confirmation`, `disputed` — **значения есть в enum и в старых RPC (`supabase/migrations/0074_lifecycle_rpcs.sql`), но недостижимы из текущего приложения.** `open_dispute` удалён (`0109_drop_open_dispute_rpc.sql`). Функции `confirm_completion`, `auto_confirm_completions`, `mark_work_done`-эквивалент нигде не вызываются из `app/`, `src/features/**` (проверено `grep -rl` — ни одного вызова). `0197` явно блокирует прямую установку этих двух статусов из приложения (guard, 0197:27-32). **Вывод: это legacy-хвост, а не часть текущего продукта.** Если на проде остались заказы в этих статусах с 2026-05 — они зависли; способ проверки — `UNKNOWN`, нужен `SELECT count(*) FROM orders WHERE status IN ('awaiting_confirmation','disputed')` на живой базе.
- `response_status`: `sent → viewed` (клиент открыл), `sent/viewed → accepted` (выбор исполнителя), `accepted → rejected` (клиент отказался от исполнителя, 0196:120-121), `sent/viewed → withdrawn` (мастер отозвал сам, или авто при `complete_order`/`reopen_order`/закрытии), `sent/viewed → rejected` (клиент скрыл конкретный отклик).

### 1.2. Где и как это показано сейчас — расхождения (FACT)

Три независимых места рисуют один и тот же факт («задание завершено», «меня выбрали») тремя разными способами:

| Место | Файл | Что видно при `completed` + «я выбранный мастер» |
|---|---|---|
| Карточка в «Мои задания» → «Как мастер» | `order-card-tone.ts:62-69`, обводка `TONE_BORDER_CLASS.chosenMe = border-accent` (`order-card-tone.ts:87`) | Пилюля «Вы выполнили» на `bg-accent-soft/text-accent` (розово-красный, `#e11d48`), обводка карточки 2px того же розово-красного |
| Шапка экрана задания | `OrderStatusBadge` (`OrderStatusBadge.tsx:80-85`), вызов `[id].tsx:791` | Пилюля «Завершено» на `bg-success-soft/text-success` (зелёный, `#10b981`), точка зелёная. Без обводки — это отдельный badge, не карточка |
| Блок «Ваш отклик» на этом же экране | `responseStatusView` (`[id].tsx:1661-1667`) | Пилюля «Вы выполнили» на `bg-success-soft/text-success` (зелёный) |
| Карточка того же задания в «Мои задания» → «Как клиент» (у другого пользователя — заказчика) | `clientOrderTone` (`order-card-tone.ts:45-46`) | Пилюля «Завершено» `bg-success-soft/text-success` (зелёный), обводка `border-success` (зелёная, 2px) |

Итого один и тот же факт «работа выполнена» = **розово-красный + обводка** (карточка мастера) / **зелёный без обводки** (шапка) / **зелёный** (блок отклика) / **зелёный + обводка** (карточка клиента). Ровно то, на что указал владелец: «цвета не наследуются». Причина технически: три отдельные функции (`clientOrderTone`, `masterOrderTone`, `responseStatusView`) и отдельный `STYLES` в `OrderStatusBadge` кодируют один и тот же смысл заново, каждая с своим выбором цвета.

Второе расхождение — сила обводки. `TONE_BORDER_CLASS` пришёл 2026-09-13 и добавил `borderWidth: 2` цветную обводку (`OrderRow.tsx:228`). Это прямо противоречит зафиксированному в том же файле решению от 2026-09-08: *«чёрная обводка — не в дизайне, сделай как в iOS»* (`OrderRow.tsx:151-152`, комментарий про `CARD_SHADOW`). Яркая цветная обводка — тот же анти-паттерн, что и чёрная, только в цвете. Обводка `border-warning`/`border-success` на карточках отклика клиента (`[id].tsx:1368-1370`, `ClientMasterResponseCard`) — третье независимое место с тем же приёмом.

### 1.3. Третье расхождение — «завершено» = зелёный = «успех», а владелец хочет архив

Уточнение владельца (получено в процессе этой работы): готовое задание должно выглядеть **нейтрально-архивным**, а не празднично-зелёным — оно не требует внимания, это прошлое. Одновременно оно не должно читаться как отмена/ошибка. Ниже (раздел 3) — решение.

## 2. Модель статусов по ролям

Правило источника: **на экране виден не `order.status` напрямую, а производный «взгляд» — что это значит для конкретного человека сейчас**. Для заказчика и специалиста один и тот же `order.status` может значить разное (пример: `in_progress` — для заказчика «я жду выполнения», для проигравшего мастера — «моё дело закрыто»).

### 2.1. Заказчик (владелец задания)

| Состояние (`order.status`) | Название | Значение | Главное действие | Где |
|---|---|---|---|---|
| `open`, откликов нет | «Открыто» | Задание в ленте, ждёт первого отклика | нет (пассивно ждать) либо «Закрыть» вторым планом | список, шапка |
| `open`, есть отклики | «Открыто» + счётчик откликов | Есть из кого выбрать | «Посмотреть отклики» → выбрать исполнителя | список (счётчик в подвале карточки, уже есть — `OrderRow.tsx:372-389`), `OrderManageBlock` |
| `in_progress` | «Исполнитель выбран» | Договорились, ждём выполнения | «Работа выполнена» (главное), «Отказаться от исполнителя» (второе), «Отменить» (тихое) | список, шапка, `OrderManageBlock` (уже так, `OrderManageBlock.tsx:195-209`) |
| `completed`, отзыв не оставлен | «Завершено» | Работа сделана | «Оставить отзыв» | список (архив-секция), шапка, `OrderManageBlock` |
| `completed`, отзыв оставлен | «Завершено» | Готово, отзыв есть | нет действия — можно посмотреть свой отзыв | список (архив), шапка |
| `cancelled` | «Закрыто» | Клиент сам закрыл без исполнителя | «Открыть заново» (7 дней) либо ничего | список (архив), шапка |
| `expired` | «Истекло» | Срок публикации вышел | «Открыть заново» (7 дней) либо ничего | список (архив), шапка |
| `draft` | не показывается в списках | — | — | только форма создания |

### 2.2. Специалист (откликнувшийся)

Взгляд специалиста зависит от **два факта одновременно**: статус задания и статус его собственного отклика (кого выбрали).

| Ситуация | Название | Значение | Действие | Где |
|---|---|---|---|---|
| `order.open`, мой отклик `sent`/`viewed` | «Отклик отправлен» / «Клиент прочитал» | Жду решения клиента | «Отозвать отклик» (тихое) | список, «Ваш отклик» |
| `order.open`, мой отклик `rejected` | «Отклонён» | Клиент скрыл мой отклик, задание ещё открыто | «Посмотреть похожие задания» | архив-раздел |
| `order.open`, мой отклик `withdrawn` | «Отозван» | Я сам отозвал | можно откликнуться снова | архив-раздел |
| `order.in_progress`, выбрали МЕНЯ (`accepted`) | «Вас выбрали» | Договорились, я исполнитель | нет действия в приложении (контакт вне приложения) | список, «Ваш отклик» — **это единственный «живой», требующий внимания статус специалиста**, достоин акцентного выделения |
| `order.in_progress`, выбрали другого | «Выбран другой» | Моё дело здесь закрыто | «Посмотреть похожие задания» | архив-раздел |
| `order.completed`, выбрали МЕНЯ | «Вы выполнили» | Клиент подтвердил работу | нет действия (клиент может оставить отзыв — не моё действие) | список (архив), «Ваш отклик» |
| `order.completed`, выбрали другого | «Выбран другой» | — | — | архив-раздел |
| `order.cancelled`/`expired`, был выбран я | «Отменено» | Договорённость не состоялась не по моей вине | — | архив-раздел |
| `order.cancelled`/`expired`, не был выбран | «Задание закрыто»/«Истекло» | — | — | архив-раздел |

Рекомендую добавить (не реализовано нигде): **уведомление специалисту о `completed`** — сейчас есть push `order_completed` (0196:161-163) и `order_accepted`, но нет отдельного `notification_type` для «клиент оставил отзыв» именно по этому заданию (есть только общий `review_received`, без ссылки на задание в типизированной колонке — только jsonb metadata). Цена: 1 строка в существующий enum + прокидывание order_id в metadata (уже есть паттерн) — дёшево, но не в этом релизе, если не просили.

## 3. Семантика цвета — единый визуальный язык

### 3.1. DECISION: 4 смысловых тона (было по факту 3 независимых системы + перепутанные цвета)

| Тон | Смысл | Когда | Токен (фон/текст/точка) | Обводка |
|---|---|---|---|---|
| **live** («в игре») | Задание открыто и ждёт исхода — не важно, чья это карточка | `open`, отклик `sent`/`viewed` при открытом заказе | `bg-link-bg-soft` / `text-link` / `bg-link` (уже есть, `OrderStatusBadge.tsx:72-77`) | нет |
| **matched** («договорились») | Кого-то выбрали, идёт работа. **Один цвет для заказчика и специалиста** — сейчас это два разных цвета (оранжевый у клиента, розовый у выбранного мастера) | `in_progress` (обе роли), отклик `accepted` при `in_progress` | `bg-accent-soft` / `text-accent` / `bg-accent` (бренд-акцент — самый заметный, потому что это единственное состояние, которое реально требует, чтобы человек его заметил и знал: пора действовать/ждать звонка) | нет |
| **archive** («в прошлом») | Всё, что закрыто, независимо от исхода: `completed`, `cancelled`, `expired`, `rejected`, `withdrawn`, «выбран другой», `draft`. **Один нейтральный серый тон**, а не «зелёный успех / серая отмена» | всё терминальное | `bg-surface-2` / `text-mute` / `bg-muted-soft` (уже есть как `CLOSED_LEGACY` в `OrderStatusBadge.tsx:48-53`) | нет |
| **problem** (зарезервировано, не включать сейчас) | Спор / скрыто модератором | `disputed` — сейчас недостижим из приложения (см. §1.1) | `bg-error-soft` / `text-error` | нет |

Это ровно **4 работающих тона + 1 зарезервированный** — совпадает с пределом «4–5 смысловых тонов» из задания. `warning` (оранжевый) как отдельный тон для «исполнитель выбран» **убираю**: он не нёс отдельного смысла, только раздваивал одно и то же состояние между ролями.

**Внутри `archive` смысл различают текст и иконка, не цвет** — то, что просил владелец («не должно читаться как ошибка/отмена»):

| Статус | Иконка (Phosphor, `weight="fill"` в архиве — приглушённый вид) | Текст |
|---|---|---|
| `completed` | `CheckCircle` | «Завершено» (заказчик) / «Вы выполнили» (выбранный мастер) |
| `cancelled` | `XCircle` | «Закрыто» |
| `expired` | `ClockCountdown` | «Истекло» |
| отклик `rejected` | `XCircle` | «Отклонён» |
| отклик `withdrawn` | `ArrowUUpLeft` | «Отозван» |
| выбран другой | `UsersThree` | «Выбран другой» |
| `draft` | `PencilSimple` | «Черновик» |

Иконка *внутри пилюли*, 12-14px, тем же `text-mute`, слева от текста (там же, где сейчас точка в `OrderStatusBadge`). Дешёвая правка: заменить 6px точку на 14px иконку только для тона `archive`; для `live`/`matched` точка остаётся (там смысл один на тон, иконка не нужна).

### 3.2. Обводка — DECISION: убрать совсем

Возвращаюсь к решению 2026-09-08, которое `order-card-tone.ts` (2026-09-13) нарушил. **Ни один тон не получает цветную обводку карточки.** Разграничение — пилюлькой (уже несёт весь смысл через текст+цвет+иконку) и приглушением (`opacity: 0.65` для `archive`, уже есть `OrderRow.tsx:229`) и положением в списке (раздел 4). Это одновременно чинит «слишком яркая обводка» и «наследование» — потому что убирает третий канал кодирования цвета, оставляя один (пилюля), который и наследуется единым компонентом (см. 3.4).

Если позже понадобится подчеркнуть именно `matched` (самое «важное» состояние) — не обводка, а тонкая левая полоса 3px `bg-accent` внутри карточки (паттерн Reminders/Calendar iOS, не «рамка», а «акцент-маркер»); не делаю сейчас — не просили, это уже украшение сверх минимума (§1.1 design-quality).

### 3.4. Один компонент статуса

DECISION: завести единый источник `src/features/orders/order-status-view.ts`, заменяющий четыре независимых места (`clientOrderTone`, `masterOrderTone`, `responseStatusView` в `[id].tsx`, `STYLES` в `OrderStatusBadge.tsx`, `historyResponseStatusLabel` в `use-my-responses.ts`):

```ts
type StatusTone = "live" | "matched" | "archive"; // + "problem" зарезервирован

interface OrderStatusView {
  tone: StatusTone;
  label: string;      // текст пилюли — то, что видит человек
  icon?: IconComponent; // только для archive
  dimmed: boolean;     // приглушение карточки (opacity), не обводка
}

function orderStatusView(input: {
  role: "client" | "master";
  order: { status: OrderStatus; picked_master_id: string | null };
  myResponseStatus?: ResponseStatus; // только для role: "master"
}): OrderStatusView
```

Один и тот же результат этой функции рисует: пилюлю в `OrderRow` (список), `OrderStatusBadge` в шапке (`[id].tsx:791`), пилюлю в блоке «Ваш отклик» (`[id].tsx:1614`), чип в `ClientMasterResponseCard` (вместо `highlight`-обводки — `[id].tsx:1368-1370` заменить на маленькую пилюлю рядом с ценой отклика: «Выбран» тон `matched`). Компонент рендера — один `<StatusPill tone label icon size />`, `OrderStatusBadge.tsx` переименовать/переиспользовать под это имя (props уже почти совпадают: `bgClass`/`textClass`/`dotClass` → заменить на `tone`).

**Честность интерфейса (design-quality §5):** пилюля не утверждает больше, чем есть в данных — «Вы выполнили» показывается только когда `response.status === 'accepted' AND order.status === 'completed'`, оба факта проверены на бэкенде (`complete_order` меняет их атомарно в одной транзакции, 0196:150-158), гадать не о чем.

| Продукт | Паттерн | Берём? |

### 4.2. Решение: секции, не вкладки

Внутри каждой из двух ролей («Как клиент» / «Как мастер», переключатель остаётся как есть — `SegmentedControl`, `orders/index.tsx:186-199`, не трогаем) список делится на **две секции без явных заголовков-разделителей, а порядком**:

1. **Активные** — тон `live` и `matched`. Сортировка: `matched` выше `live` (у человека уже есть исход, ему важнее), внутри группы — по `last_activity_at`/`created_at` убыв.
2. **Архив** — тон `archive`. Ниже активных, визуально тише (`opacity: 0.65`, уже есть), сортировка — по дате закрытия убыв.

Это уже частично реализовано (`ACTIVE_STATUSES` в `orders/index.tsx:81`, `allOrders` в `orders/index.tsx:200-205` кладёт open/in_progress выше). **Чего не хватает: явного визуального шва между секциями** — сейчас это просто конкатенация двух массивов, человек не понимает, что ниже — уже другая категория, пока не увидит первую закрытую карточку. DECISION: добавить лёгкий заголовок-разделитель секции (не карточка, не жирная линия) — `text-caption text-mute uppercase` «Архив» с `mt-6` перед первой архивной карточкой, паттерн iOS `UITableView` section header (Настройки, Файлы). Дёшево: один `ListHeaderComponent`-подобный item в данных `FlashList` с другим `renderItem`.

**Счётчики** в `SegmentedControl` (`orders/index.tsx:192-199`) — сейчас считают **все** задания/отклики, включая архив (`myOrders?.length`). DECISION: не менять — счётчик роли отвечает на вопрос «сколько у меня вообще дел», а не «сколько активных»; если считать только активные, счётчик будет обнуляться после завершения последнего задания и создаст ложное впечатление пустого таба, когда на деле там архив. Если владелец захочет «только активные» в счётчике — цена: 1 `useMemo` фильтр, но тогда нужно решить, что показывать, когда всё в архиве (0 в капсуле при непустом списке — сбивает с толку). Оставляю как есть, помечаю вопросом в разделе 7.

**Пустые состояния** (уже есть, `EmptyState` в `orders/index.tsx:164+`) не меняются — они про «нет заданий вообще», не про архив. Пустой архив описан в разделе 5.4.

**Загрузка/ошибка** — уже покрыты (`OrderRowsSkeleton`, `ErrorState` с `onRetry`, `orders/index.tsx` в `OrdersList`/`ResponsesList`) — не трогаем, соответствуют `design-quality.md` §1.2 (конечное ожидание, скелетон не «вечная» полоска).

**Оффлайн / нет прав** — гостевой экран уже есть (`orders/index.tsx:130-146`, «Войдите, чтобы видеть свои задания» — честно про причину пустоты, не про «заданий нет»). Оффлайн отдельно не обрабатывается в этом экране — **UNKNOWN**, способ проверки: включить авиарежим и открыть вкладку, посмотреть, что показывает `ErrorState`/`describeQueryError` (скорее всего сработает общий адаптер сетевой ошибки — не проверено вживую в этой сессии).

## 5. Архив

### 5.1. Что архивируется и из каких состояний

| Роль | Что можно убрать в архив | Условие |
|---|---|---|
| Заказчик | своё задание | `status IN (completed, cancelled, expired)` — то есть ровно тон `archive` из §3.1. Активное (`open`/`in_progress`) архивировать нельзя — это скрыло бы дело, требующее действия, что и есть цена ошибки при «архиве вместо статуса» |
| Специалист | свой отклик на чужое задание | `isHistoryResponse(r)` уже верно считает это условие (`use-my-responses.ts:33-51`) — переиспользовать предикат, не дублировать |

**Симметрия ролей — рекомендую добавить мастеру то же самое**, ценой одной колонки и одного экрана (переиспользует всю механику архива клиента). У специалиста список откликов растёт быстрее, чем у клиента список заданий (один клиент — 1-3 задания, один активный мастер — десятки откликов за месяцы), значит архив ему даже нужнее. Делаю это частью спецификации ниже, а не отдельным «рекомендую подумать».

### 5.2. Личный характер архива

Архив — пометка **у себя**, не меняет состояние для другой стороны и не трогает `orders.status`/`order_responses.status`. Заказчик отправил своё завершённое задание в архив — специалист по-прежнему видит его как обычно в своём «Как мастер», отзыв, история, счётчик `closed_deals` не меняются. Прецедент этого паттерна в базе уже есть: `master_profiles.hidden_by_owner` (`supabase/migration-drafts/0176_hidden_by_owner.sql:8-11`) — булева колонка, которую трогает только сам человек, не пересчитывается автоматикой, не влияет на чужие данные. Архив заданий — тот же приём, применённый к `orders`/`order_responses`.

### 5.3. Как архивировать — DECISION

- **Свайп по карточке в списке** (iOS-нативный leading/trailing swipe action, `react-native-gesture-handler` / уже используемый в проекте механизм списков) — **основной способ**, потому что это ровно родной паттерн iOS для «убрать из списка, не удаляя» (Почта — Archive свайпом, Напоминания — смахнуть выполненное). Действие доступно только на карточках тона `archive` (свайп на активной карточке не предлагает архивацию — там нечего архивировать).
  - Один swipe action, не деструктивный цвет (серый/`ink`, не красный) — визуально отличим от «Удалить» (которое красное и находится в другом месте, см. раздел 6).
  - Подпись: «В архив», иконка `Archive` (Phosphor).
- **Пункт в «⋯» на экране задания** — второй вход, для симметрии с тем, что там же расположено «Удалить» (`app/(details)/orders/[id].tsx:507-541`, `ActionSheetIOS`). Пункт **не деструктивный** (`destructive: false`), стоит выше деструктивных пунктов в списке экшенов (уже так устроено в текущем `items` — деструктивные добавляются позже).
- **Android** (Material, приложение поддерживает — `CROSS_PLATFORM_RULES.md`): свайпа как системного паттерна нет same-way; там пункт архива — только через тот же «⋯»/overflow menu (уже используемый паттерн на Android, если он там есть — **UNKNOWN**, способ проверки: найти Android-эквивалент `ActionSheetIOS` в кодовой базе, не искал в этой сессии из-за лимита времени — вероятно `src/lib/action-sheet.ts` или аналог с кросс-платформенным адаптером).
- **Возврат из архива — да, без ограничения по времени.** Дешёвая, обратимая операция (просто снять метку), запрещать возврат было бы придуманным ограничением без причины (§1.1 «настройки/ограничения ради ограничений»).

### 5.4. Экран архива

- **Вход** — иконка справа вверху на «Задания» (сейчас в шапке этого экрана `LargeTitleBar` с `hideTitle`/`alwaysCompact`, без `rightAction` слота — нужно добавить). Иконка Phosphor `Archive`, `accessibilityLabel="Открыть архив заданий"` (или «…откликов» — зависит от активной роли/таба, чтобы VoiceOver не врал о содержимом). Тач-цель ≥44×44pt как у любой иконки в хедере (см. паттерн `NavCircleButton`/`iconAction` в `ScreenHeader`, `docs/IOS_FOUNDATION.md` §0).
- **Вид списка** — тот же `OrderRow`, тот же `orderStatusView` (архив тон уже приглушённый по умолчанию — здесь `opacity` можно вернуть к 1.0, раз весь список и так архив, приглушение внутри архива уже не несёт смысла «отличается от активных»). Секция единая, без деления, сортировка по дате закрытия убыв.
- **Пустой архив** — не пустой список вообще, а именно «архив пуст»: иконка `Archive`, текст «Здесь появятся завершённые и закрытые задания, которые вы уберёте из списка» — честно объясняет механику, не «у вас пока нет заданий» (это неправда, раз есть активные).
- **Загрузка** — `OrderRowsSkeleton`, тот же компонент.
- **Ошибка** — `ErrorState` с `onRetry`, тот же паттерн.
- Экран отдельного route (`/orders/archive` или `/orders/[role]/archive`), не модалка — список может быть длинным, модалка неудобна для скролла + возврата отдельных карточек.

### 5.5. Автоматический уход в архив по времени — не рекомендую сейчас

Цена: cron-задача + продуктовый риск «пропало задание без моего действия» → жалобы в поддержку «где мой заказ», что прямо противоречит §5 design-quality (честность) и §1.1 (не добавлять, пока не доказана нужда). Ручной архив (свайп/меню) уже решает исходную жалобу владельца («висит и с ним ничего нельзя сделать»). Возвращаться к автоархиву стоит только если после релиза ручного архива данные покажут, что люди им не пользуются и жалуются на захламлённость — тогда цена станет оправданной.

### 5.6. Минимальная модель данных (черновик для xtrud-backend, без SQL)

- `orders.archived_by_client_at timestamptz NULL` — ставит/снимает только `client_id = auth.uid()`, только когда `status IN ('completed','cancelled','expired')`. Не читается нигде, кроме собственного списка клиента (не выставлять в публичные RPC вроде `search_masters`, не показывать специалисту).
- `order_responses.archived_by_master_at timestamptz NULL` — ставит/снимает только `master_id = auth.uid()`, только когда `isHistoryResponse` (терминальный отклик).
- RLS: точечный `GRANT UPDATE (archived_by_client_at) ON public.orders TO authenticated` + policy `USING (client_id = auth.uid())`, аналогично для второй колонки на `order_responses` — по образцу `0176_hidden_by_owner.sql:11` (`GRANT UPDATE (hidden_by_owner) ON public.master_profiles TO authenticated`). Гейт состояния (только терминальные статусы) — либо `CHECK`, ссылающийся на другую колонку той же строки нельзя обычным `CHECK` в Postgres для мультиколоночной логики через RPC/триггер, надёжнее — обёрточная RPC `archive_order(order_id)`/`archive_response(response_id)` с проверкой статуса внутри, по образцу `pick_order_master`/`complete_order` (SECURITY DEFINER, 0196). Простой прямой `UPDATE` с колоночным грантом было бы проще, но тогда статус-гейт живёт только в клиенте — небезопасно (как раз то, от чего защищает `0197_order_lifecycle_guard.sql`). Рекомендую RPC, не прямой grant.
- **Это черновик, не готовая миграция.** Нужны: новая forward-only migration, ревью `xtrud-security` (RLS на персональные данные), проверка на живой схеме перед применением (`docs/AGENT_WORKFLOW.md` §4 backend).

## 6. Удаление

### 6.1. Текущее состояние (FACT)

Удаление уже реализовано, но **только для `cancelled`/`expired`**:
- RLS: policy `orders_owner_delete_history` — `USING (client_id = auth.uid() AND status IN ('cancelled','expired'))` (`supabase/migrations/0099_orders_owner_delete_history.sql:26-29`).
- UI: пункт «Удалить задание» в «⋯», деструктивный, только когда `isOwner && isClosedHistory` (`[id].tsx:475-477`, `isClosedHistory = status IN (cancelled, expired)`, `[id].tsx:197`). Подтверждение — `confirmAsync` с текстом *«Задание исчезнет из «Моих заданий» навсегда вместе с откликами. Это нельзя отменить»* (`[id].tsx:346-351`).
- **`completed` сейчас удалить нельзя вообще** — ни RLS, ни UI это не допускают. Новое требование владельца («в том числе завершённое») требует правки RLS (backend) и условия в UI.

### 6.3. Варианты — цена и рекомендация

**(а) Физическое удаление** (текущий код, расширить на `completed`)
- Плюс: просто, уже наполовину реализовано (RLS-паттерн, UI-паттерн, `confirmAsync` — всё есть, нужно только снять ограничение статуса и обновить текст).
- Минус: все последствия §6.2 бьют полной силой — потеря отзыва специалиста и молчаливый пересчёт рейтинга, потеря аудит-лога, дыра в лимите публикации (когда включат), осиротевшие жалобы, отсутствующий «не найдено» экран.
- Цена, чтобы сделать безопасно: чинить `reviews.order_id` FK (см. ниже), чинить `order_status_log` FK (привести код в соответствие с уже написанным комментарием — там просто забыли поменять `ON DELETE CASCADE` на `SET NULL` в 0073, это по сути баг), добавить экран «задание не найдено», учесть лимит при внедрении 0131. Это backend-задача на несколько миграций плюс review `xtrud-security`.

**(б) «Удалено для меня»** (мягкое, как архив, но необратимо со стороны клиента)
- Плюс: ничего из §6.2 не происходит — отзыв, рейтинг, лог, жалобы целы, у специалиста ничего не меняется.
- Минус: с точки зрения хранения данных это **не удаление**, а ещё один личный флаг (`deleted_by_client_at`), очень похожий на архив (§5) — по сути дублирует его смысл («не показывать мне»), только без возможности вернуть. Пользователь, попросивший «удалить», ожидает, что данных не останется (особенно фото — если там что-то личное про его дом), а не что они просто спрятались с его стороны.

**(в) Удаление с ограничениями по состоянию**
- Например: нельзя физически удалить, если есть `picked_master_id` (была реальная договорённость) или есть отзыв — в этих случаях доступен только архив (б/§5), а не удаление.
- Плюс: закрывает главный риск (пропажа чужого отзыва/рейтинга без ведома специалиста) минимальной ценой — не нужно трогать FK вообще.
- Минус: прямо противоречит явному новому решению владельца «клиент должен уметь удалить своё задание, в том числе завершённое» — если в завершённом уже есть отзыв, вариант (в) как раз это и запрещает.

**Рекомендация: (а), но с обязательным исправлением двух конкретных багов до включения на `completed`:**

1. `reviews.order_id` — сменить `ON DELETE CASCADE` на `ON DELETE SET NULL` (потребует reviews.order_id стать nullable + сохранить где-то заголовок задания для контекста отзыва, например снапшот `order_title text` в момент создания отзыва, раз сам `orders` может исчезнуть). Тогда отзыв и рейтинг переживают удаление задания — это единственный правильный способ дать владельцу то, что он просит («удалить, в том числе завершённое»), не ломая специалисту репутацию без его ведома.
2. `order_status_log.order_id` — привести факт в соответствие с уже написанным в 0099 намерением: `ON DELETE SET NULL`, лог остаётся для support/аналитики.
3. Добавить экран «задание не найдено» на `/orders/[id]` (нужен независимо от исхода этого решения — это существующий гол, не появившийся из-за архива/удаления, но удаление завершённых расширяет число живых ссылок на такие задания через push/inbox).

Если владелец готов на это (миграция + review `xtrud-security` перед применением к живой базе, по правилам `AGENT_WORKFLOW.md` §4 «Backend»), физическое удаление становится безопасным без урезания того, что он просит. Если владелец хочет обойтись без миграции прямо сейчас — тогда временно это вариант (в) для `completed` с отзывом (запрет), с явным объяснением в интерфейсе «нельзя удалить — есть отзыв специалисту, но можно убрать в архив», и физическое удаление доступно для `completed` **без** отзыва (`myReviewRating == null`) — в этом случае каскад безопасен (отзыва ещё нет, рейтинг не изменится), только теряется история отклика у специалиста и аудит-лог — то же, что уже происходит сегодня для `cancelled`/`expired`, то есть не хуже принятого статус-кво.

### 6.4. Интерфейс

- Кнопка — тот же пункт «⋯» на экране задания (`[id].tsx:475-477`), деструктивный стиль (уже есть, `destructive: true`), условие расширяется с `isClosedHistory` на `isClosedHistory || status === 'completed'`.
- Подтверждение — `confirmAsync`, текст **зависит от того, есть ли отзыв** (честность интерфейса — человек должен знать цену действия до, а не после):
  - Нет отзыва: текущий текст подходит без изменений — *«Задание исчезнет из «Моих заданий» навсегда вместе с откликами. Это нельзя отменить»*.
  - Есть отзыв **и** реализован вариант (а) с `SET NULL` на reviews: отзыв уточнять не нужно — он переживёт удаление, менять текст не для чего.
  - Есть отзыв, а `SET NULL` **не** реализован (временный вариант): такой пункт вообще не показывать (см. §6.3 конец) — не давать ложный простой «Удалить», ведущий к скрытой потере чужих данных.
- Отличие от архива на экране: архив — обычный (не красный) пункт в «⋯», текст «В архив», плюс отдельный вход через свайп в списке (§5.3). Удаление — только в «⋯», всегда красным, всегда с подтверждением, никогда свайпом (свайп без предупреждения — не то место для необратимого действия с чужими последствиями).
- Что видит специалист: при варианте (а)+`SET NULL` — ничего не меняется в его профиле/рейтинге/отзыве; в его «Мои отклики» запись этого отклика пропадает (как и сегодня для cancelled/expired — статус-кво, не новая проблема), при переходе по старому уведомлению — экран «Задание не найдено» вместо краша (см. §6.2, обязательный fix).

## 7. Accessibility

- **VoiceOver-метки статуса** — пилюля не должна озвучиваться отдельно от карточки бессвязным «Завершено» без контекста. Сейчас `OrderRow` уже строит единый `accessibilityLabel` на всю карточку, включающий `dimmedLabel` (`OrderRow.tsx:205-216`) — этот паттерн сохраняется, `orderStatusView().label` подставляется в то же место, ничего дополнительно строить не нужно.
- Для отдельно стоящего `StatusPill` (шапка задания, блок «Ваш отклик») — сам по себе не интерактивен, значит не нужна `accessibilityRole="button"`; но нужно, чтобы он не терялся как декоративный `View` — задать `accessibilityElementsHidden={false}` (по умолчанию) и включить его текст в общий `accessibilityLabel` заголовка блока, если он сейчас читается отдельно (проверить вживую — UNKNOWN, см. §9).
- **Не только цвет** — уже решено текстом (лейбл всегда другой для каждого статуса) и добавлением иконки для тона `archive` (§3.1) — двух независимых каналов достаточно по WCAG 1.4.1.
- **Dynamic Type** — пилюли используют `text-caption`/`text-body-sm` (токены с заданной шкалой роста, не `fontSize` напрямую) — при accessibility-размерах текст «Исполнитель выбран»/«Клиент отметил работу выполненной. Спасибо!» может не поместиться в одну строку внутри пилюли фиксированной высоты (`h-6`/`h-7`, `OrderStatusBadge.tsx:98`). **UNKNOWN, нужно проверить на AX3/AX5**: скорее всего пилюля с `numberOfLines` не задан явно — рискует обрезать текст или сломать высоту строки. Способ проверки — реальный симулятор/устройство с accessibility-размером шрифта, раздел 9.
- **Свайп-архивация (§5.3)** — обязательно дублировать действием в «⋯»/VoiceOver rotor «Actions», потому что свайп-жест недоступен многим VoiceOver-пользователям без явного действия в rotor (iOS сам предоставляет rotor-actions для `swipeActions` в SwiftUI/UIKit; для RN-реализации (`react-native-gesture-handler` свайпы) нужно явно прокинуть `accessibilityActions`/`onAccessibilityAction`, иначе жест недоступен VoiceOver вообще). Это не опция, а обязательное условие приёмки для нового swipe-action.
