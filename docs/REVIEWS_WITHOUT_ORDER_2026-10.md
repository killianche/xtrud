- DECISION владельца 2026-10-22: в админке — страница «Подозрительные»:

## 1. Живое состояние (FACT, 2026-10-22, read-only)

- `submit_master_review(p_target_id, p_rating, p_text, p_order_id)` —
  требует завершённое задание (0196). Старые сборки зовут её — не ломать.
- `reviews`: `order_id` NULL допустим; уникальность `(order_id, author_id)`
  (NULL не ограничивает); `status` enum `visible|hidden|pending`.
- Рейтинг — триггер `recalc_master_rating` по всем `visible` отзывам.
- Уведомление специалисту — триггеры на INSERT visible и pending→visible.
- `admin_set_review_status(id, 'visible'|'hidden', reason)` — есть, пишет журнал.
- Политика `reviews_insert_participant` + `GRANT INSERT` для authenticated —
  прямая запись в таблицу в обход RPC. Проверить (security): нельзя, чтобы
  отзыв без задания обходил правила ниже.
- Политика чтения: автор и **адресат** видят свои отзывы в любом статусе.
  Поэтому признаки накрутки не кладутся колонкой в `reviews` — отдельная
  таблица только для персонала.
- Сигналы, которые есть в базе: `users.created_at`, `users.status`,
  `orders.client_id` (активность), `notification_tokens.device_token`
  (общее устройство). IP-адреса xtrud-api не хранит (`auth.sessions`
  устарела с 2026-09-08) — UNKNOWN/не используется.

## 2. Правила отзыва без задания (сервер)

Новая RPC `submit_direct_review(p_target_id uuid, p_rating int, p_text text)
returns jsonb {id, status}` (старую не трогаем — её зовут сборки ≤168).

Жёсткие запреты (ошибка с понятным текстом, `DETAIL` — код):

1. Нужен вход; аккаунт `active` (уже даёт триггер).
2. Адресат — специалист (`is_master`), не сам автор, не `is_demo`.
3. Один отзыв без задания от человека одному специалисту — навсегда
   (частичный уникальный индекс `(author_id, target_id) WHERE order_id IS NULL`).
4. Не чаще одного отзыва без задания в 3 дня от одного человека
   (прежнее правило владельца 2026-09-12, 0191).
5. Текст обязателен, от 20 символов — «★5 без слов» дешевле всего накрутить.

Признаки накрутки → отзыв сохраняется со `status = pending`, признаки
пишутся в `review_flags` (только для персонала):

| Код | Условие |
|---|---|
| `new_account` | аккаунту автора меньше 7 дней |
| `shared_device` | у автора и специалиста есть общий `device_token` |
| `burst` | специалисту за 7 дней уже ≥ 3 отзывов без задания |
| `mutual` | специалист оставлял отзыв автору (любой direction) |

Отзыв без признаков — сразу `visible`.

## 3. Рейтинг

`recalc_master_rating` считает только отзывы с `order_id IS NOT NULL`
(для `client_to_master`). Пересчитать всех специалистов в миграции.
UNKNOWN до проверки: 4 уже существующих отзыва без задания (из периода
0175–0196) выпадут из рейтинга — это следствие решения владельца; назвать
в отчёте, сколько специалистов затронуто.

## 4. Админка — «Подозрительные»

RPC (только персонал, `is_staff_session()`):

- `admin_list_flagged_reviews()` — отзывы на проверке и с признаками:
  автор (имя, возраст аккаунта, число заданий), специалист, оценка, текст,
  признаки. Действия — существующая `admin_set_review_status`.
- `admin_list_suspicious_specialists(p_days int default 30)` — специалисты
  с отзывами за период, отсортированы по баллу подозрительности: всего
  отзывов, без задания, от аккаунтов младше 7 дней, от аккаунтов без
  единого задания, с общим устройством, взаимные, доля пятёрок. Показывать
  только тех, у кого балл > 0.

Страница админки `Подозрительные`: две вкладки/секции — «На проверке»
(одобрить / скрыть с причиной) и «Специалисты» (таблица сигналов, переход
в карточку человека).

## 5. Приложение

- Профиль специалиста: «Оставить отзыв» видит вошедший человек (не сам
  специалист), если у него есть завершённое задание без отзыва (как сейчас,
  отзыв по заданию) **или** он ещё не оставлял отзыв без задания.
  Гость — кнопка ведёт ко входу (решает designer по существующему паттерну).
- Экран отзыва без задания: подпись, что отзыв без задания не влияет на
  рейтинг; текст обязателен (20+ символов, счётчик). После отправки:
  `visible` — «Отзыв опубликован»; `pending` — «Отзыв появится после
  проверки». Ошибки сервера — как есть.
- Список отзывов на профиле: честно различать отзыв по заданию и без —
  форма решается designer (тихая подпись), без «проверено» без источника.
- Android идёт вместе с iOS.

## 6. Не делается в этой задаче

- **Google Maps / Яндекс Карты** — FACT по памяти пользовательского опыта

- Поскольку ни один референс не подтверждён живым просмотром, решение ниже

### 7.1 Профиль специалиста — когда показывать «Оставить отзыв»

Файл: `app/(details)/master/[id].tsx`. Сейчас `showReviewCta` зависит только
от `reviewable.data` (завершённое задание без отзыва, `useReviewableOrderForMaster`
в `src/features/reviews/use-reviews.ts`). Нужно расширить на отзыв без
задания, не сломав текущую кнопку.

**Варианты**

| Вариант | Что это | Цена |
|---|---|---|
| A. Один умный CTA (выбран) | Кнопка «Оставить отзыв» всегда одна; внутри — приоритет: если есть незакрытое завершённое задание → ведёт в отзыв «по заданию» (как сейчас, с `orderId`); иначе, если человек ещё не оставлял этому специалисту отзыв без задания → ведёт в отзыв «без задания» (без `orderId`); иначе кнопки нет. | Нужен 1 новый хук чтения (`useHasDirectReview`, ниже) и ветвление в `handleReview`. Экран отзыва должен уметь работать в двух режимах по наличию `orderId`. |
| B. Два отдельных CTA | «Оставить отзыв по заданию» (если есть) и «Оставить отзыв без задания» (если ещё не оставлял) — одновременно, если выполнено оба условия. | Нарушает «одно главное действие на экран» (`design-quality.md` §1.1): под отзывами возникают две кнопки с почти одинаковым текстом, человек должен понять разницу, которой не видно с первого взгляда. Больше кода, больше текста на экране, больше тестовых состояний (4 комбинации вместо 3). |

**DECISION (designer):** вариант A — single CTA с приоритетом «по заданию»
первым. Это не придумано заново: формулировка владельца в §5 уже описывает
одну кнопку с условием через «или» («видит… если у него есть завершённое
задание без отзыва **или** он ещё не оставлял отзыв без задания») — вариант
B владелец не просил и явно шёл бы против «одно действие на экран».
Приоритет «по заданию» — потому что отзыв по заданию участвует в рейтинге
(раздел 3), это более ценное действие для продукта и для специалиста.

**Состояния кнопки на `master/[id].tsx` (после `isOwn` исключён):**

1. **Есть завершённое задание без отзыва** (`reviewable.data` истинно) —
   кнопка видна, ведёт в `/master/review` с `orderId` (как сейчас, без
   изменений).
2. **Нет такого задания, но ещё не было отзыва без задания этому
   специалисту** — кнопка видна, ведёт в `/master/review` **без** `orderId`.
3. **Нет задания и отзыв без задания уже оставлен** — кнопки нет совсем.
   Текст вроде «Вы уже оставили отзыв» не нужен — это бы отвечало на вопрос,
   который человек не задавал (ничего нет = ничего нет, как с «Отзывов пока
   нет» в самой секции).
4. **Гость** (`isGuest`) — кнопка **видна** (отличие от текущего кода, где
   `showReviewCta` требует `currentUserId` и у гостя скрыта). Один тап сразу
   ведёт на вход: переиспользовать точный путь `GuestContactGate.continueTo`
   (`src/features/auth/GuestContactGate.tsx:34-37` — `parseAuthReturnTo` +
   `useAuthReturnUrlStore.setReturnUrl` + `router.push("/(auth)/phone", { returnTo })`),
   `returnPath` = `/master/${masterId}`. Не вставлять второй блок
   `GuestContactGate` под кнопку — это was бы дублирование уже показанного
   выше блока для контактов и вторая просьба войти на одном экране. Кнопка
   остаётся одна, обычная, тап = прямой переход к номеру телефона (не к
   выбору «Войти / Регистрация» — упрощение по аналогии: кнопка обещает
   отзыв, а не решение входить или регистрироваться).
5. **Нет прав** (специалист `is_demo`, собственный профиль `isOwn`,
   `target === author`) — кнопки нет, без изменений в текущей логике.

**Новый хук** (место: `src/features/reviews/use-reviews.ts`, рядом с
`useReviewableOrderForMaster`): `useHasDirectReview(targetId, authorId)` —
`select id from reviews where author_id = :me and target_id = :target and
order_id is null limit 1` (RLS уже разрешает автору видеть свой отзыв в
любом статусе, раздел 1). `showReviewCta = !isOwn && (hasReviewableOrder ||
(currentUserId && !hasDirectReview) || isGuest)`; `orderId` в `handleReview`
передаётся только когда `reviewable.data` есть.

### 7.2 Список отзывов — честно отличить «по заданию» от «без задания»

Файл: `src/features/master-view/ReviewsSection.tsx`. Сводка сверху
(`formatRating` + `pluralizeReviews`) уже и дальше считает только отзывы с
`order_id IS NOT NULL` (раздел 3) — её текст не трогаем, она и так говорит
только про оценку. Проблема — ниже в списке могут быть строки без заданий,
которые в эту цифру не входили, и без пометки это выглядит как нестыковка
(«★ 4,8 · 4 оценки», а строк — 6).

**Решение:** тихая вторичная пометка только у строк без задания — тем же
приёмом, что уже есть в `ReviewRow` для категории (`· {review.l2?.name_ru}`,
`ReviewsSection.tsx:177-181`, `text-ios-footnote text-mute`). У отзыва «по
заданию» `l2` обычно есть (категория задания) — вторичная строка показывает
категорию. У отзыва **без задания** показываем вместо категории (`l2_id`
там `NULL`, см. раздел 1/2) пометку **«Без задания»** тем же стилем:

```
{review.order_id ? (
  review.l2?.name_ru ? <AppText className="text-ios-footnote text-mute">· {review.l2.name_ru}</AppText> : null
) : (
  <AppText className="text-ios-footnote text-mute">· Без задания</AppText>
)}
```

Ничего ярче не нужно: это не предупреждение и не минус специалисту (отзыв
живой, просто другого типа), а просто честная атрибуция — раздел 5
`design-quality.md` требует не завышать уверенность, а не выделять такие
отзывы как подозрительные (подозрительность — отдельный, персонал-онли
слой, раздел 4). Бейдж/иконка/другой цвет были бы избыточны (лишняя деталь,
§1.1) для факта, который не меняет доверие к конкретному отзыву — он уже
прошёл модерацию, если что-то было не так, его не было бы видно.

Сводку в шапке секции дополняем одной строкой **только если** среди
показанных отзывов есть хотя бы один без задания (иначе — не показываем,
чтобы не объяснять то, чего не произошло):

```
{hasAnyDirectReview ? (
  <AppText className="px-4 pb-3 text-ios-footnote text-mute">
    Оценка — по завершённым заданиям
  </AppText>
) : null}
```

Место — под строкой сводки (`ratingAvg`/`pluralizeReviews`), перед списком
строк, внутри той же карточки `bg-surface-card`. `hasAnyDirectReview`
считается на уже загруженных `rows` (`rows.some(r => !r.order_id)`) —
дополнительного запроса не нужно, тип `ReviewWithAuthor` уже включает
`order_id` (`Tables<"reviews">`).

### 7.3 Экран отзыва без задания

Файл: `app/(details)/master/review.tsx`. Режим определяется наличием
`orderId` в параметрах (есть — текущее поведение, без изменений; нет — новый
режим). Переиспользуется весь существующий каркас (звёзды, `FormKeyboardAvoidingView`,
модалка) — меняются только тексты, обязательность поля и обработка ответа
новой RPC `submit_direct_review` (раздел 2).

**Подпись под именем специалиста.** Текущая строка остаётся («Ваша оценка
специалиста **{masterName}**.»). Для режима без задания — вторая строка
сразу под ней, приглушённая:

> Без задания — отзыв не влияет на рейтинг специалиста.

(`text-ios-footnote text-mute`, как остальные вторичные подписи экрана).

**Текст — обязателен, от 20 символов.** Сейчас label «Комментарий
(необязательно)», максимум 500, без минимума — верно для отзыва по заданию
(0198, текст необязателен), но не для отзыва без задания (раздел 2, правило
5: от 20 символов). Только в режиме без `orderId`:

- Label меняется на **«Комментарий»** (без «необязательно»).
- Placeholder: «Расскажите, как специалист помог» (конкретнее текущего
  «Расскажите, как прошла работа» — то не подходит, когда задания не было).
- Счётчик меняется с `{length} / 500` на **`{length} / 20` пока меньше 20**,
  затем **`{length} / 500`** — короткий способ показать прогресс к минимуму,
  не вводя отдельную строку подсказки. Пока `length < 20`, счётчик —
  приглушённого (`text-mute`), а не предупреждающего цвета: это ещё не
  ошибка, а не выполненное условие по пути; `text-error` держим только для
  уже случившейся ошибки сервера, не для незаполненной формы.
- `canSubmit` в режиме без задания требует `text.trim().length >= 20`
  (вместо того что сейчас текст не участвует в `canSubmit` вовсе). В режиме
  по заданию `canSubmit` не меняется (текст по-прежнему необязателен).
- Нижняя поясняющая строка под кнопкой — заменяется на:

  > Один отзыв без задания одному специалисту. Будьте честны — отзывы
  > видны всем.

  (вместо «Один отзыв на задание…», которая для этого режима неверна).

**Кнопка.** Текст не меняется между режимами («Отправить отзыв» /
«Отправляем…») — правило «кнопка называется одинаково на всём пути»
(`xtrud-design/SKILL.md`, «Тексты в интерфейсе»): оба экрана делают одно и
то же действие с точки зрения человека — оставляют отзыв специалисту.

**Успех.** `submit_direct_review` возвращает `{id, status}`
(`'visible' | 'pending'`, раздел 2). Режим без `orderId`:

- `status === "visible"` → `showAlert("Отзыв опубликован", "Он уже виден на странице специалиста.")`
- `status === "pending"` → `showAlert("Отзыв появится после проверки", "Мы проверим его в течение дня и опубликуем, если всё в порядке.")`

  (конкретный срок «в течение дня» — **UNKNOWN**, не проверено, что
  персонал укладывается в это время; если реальный SLA проверки не
  подтверждён, оставить без срока: «Мы проверим его и опубликуем, если всё
  в порядке» — раздел 5 `design-quality.md` запрещает утверждать
  непроверенное).

  Используем безопасную формулировку без срока:
  **«Мы проверим его и опубликуем, если всё в порядке.»**

Режим по заданию (`orderId` есть) — без изменений: `showAlert("Отзыв отправлен", "Спасибо за оценку.")`.

**Ошибки.** `serverError` — та же UI-полоса (`border-error/40 bg-error-soft`,
существующий блок), но конкретные тексты, которые должна возвращать RPC
(раздел 2, жёсткие запреты 3–4), чтобы их можно было показать «как есть»
(комментарий в коде уже обещает это):

| Запрет | Текст ошибки (RPC → экран без изменений) |
|---|---|
| Уже оставлял без задания этому специалисту (п. 3) | «Вы уже оставили этому специалисту отзыв без задания.» |
| Чаще раза в 3 дня (п. 4) | «Можно оставить отзыв без задания раз в 3 дня. Попробуйте позже.» |
| Адресат не специалист / это вы сами / демо (п. 2) | «Этому аккаунту нельзя оставить отзыв.» |
| Нет сети / таймаут | общий `describeServerError` (`src/lib/describe-server-error.ts`) — переиспользовать, не изобретать свой текст. |

Текст < 20 символов проверяется на клиенте до отправки (кнопка просто
неактивна) — отдельной ошибки сервера для этого быть не должно в обычном
потоке; если RPC всё же её вернёт (гонка/обход клиента), показываем как
есть через тот же `serverError`.

**Названия признаков (русские, для чипов и для фильтра, если понадобится):**

| Код | Название на экране | Короткая подсказка (если нужен `title=`) |
|---|---|---|
| `new_account` | Новый аккаунт | Автору отзыва меньше 7 дней |
| `shared_device` | Общее устройство | Автор и специалист заходили с одного устройства |
| `burst` | Всплеск отзывов | Специалисту пришло ≥3 отзыва без задания за 7 дней |
| `mutual` | Взаимный отзыв | Специалист тоже оставлял отзыв автору |

Чип — нейтральный тихий стиль (не `btn-danger`/красный: это сигнал для
персонала, не приговор; текст отзыва рядом уже показывает контекст, по
которому решают люди, а не автоматика).

Колонки (прямое отражение полей RPC из раздела 4; порядок — от «кто» к
«почему», убывающий по баллу подозрительности, сортировка уже на сервере):

| Колонка | Источник |
|---|---|
| Специалист | имя, переход в карточку |

| Доля 5★ | процент, `100%` только если ≥ 3 отзывов (меньше — показывать «—», процент от 1-2 отзывов вводит в заблуждение, раздел 5 честности) |

## 8. Уточнения при реализации (основной агент, 2026-10-22)

- Тексты ошибок — те, что отдаёт сервер (0254), вместо общего «Этому
  аккаунту нельзя оставить отзыв.» из §7.3: «Нельзя оставить отзыв самому
  себе.», «Отзыв можно оставить только специалисту.», «Этому специалисту
  сейчас нельзя оставить отзыв.» — точнее и понятны без пояснений.
- Отзыв без задания — только специалисту с опубликованным профилем
  (`master_profiles.status = 'active'`, как в каталоге): иначе можно было бы
  писать публичные отзывы о людях, которые услуг не предлагают (security F3).
- «Подозрительные» — только администратору, как «Отзывы»; доступ управляющему —
  решение владельца. Период на вкладке «Специалисты» — 30 дней без переключателя.
- Экран отзыва спрашивает «Закрыть без отправки?», если введены оценка или
  текст (`useUnsavedChangesGuard`).
