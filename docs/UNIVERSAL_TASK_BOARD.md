# Универсальная доска заданий xtrud

## TL;DR

**Имя для запроса:** «универсальные задания», «универсальная доска заданий»,
«заказ на любую услугу».

xtrud расширяет существующую classifieds-модель: клиент публикует разовую
законную задачу, исполнитель откликается сообщением и ценой, клиент сам
инициирует звонок или WhatsApp. Новую сущность задания создавать нельзя:
источниками остаются `orders` и `order_responses`.

На 2026-08-24 это **целевой контракт, а не включённая функция**. Текущий клиент
показывает только `construction` и `home-services` через
[`src/lib/product-scope.ts`](../src/lib/product-scope.ts). Цель — 10
пользовательских L1 и отдельный скрытый fallback для запроса «не знаю
категорию». Ни восстановление категорий в БД, ни наличие данных сами по себе не
включают новый scope: создание заданий, каталог и matching управляются
раздельными feature-флагами.

Локальная feature-off foundation подготовлена в
`supabase/migration-drafts/0120`–`0122`, но намеренно изолирована от runnable
migrations. Клиентские draft/auth-return и чистые universal contract helpers
также не включают новый scope и не подключены к production queries. Это
проверяемая заготовка для promotion после live inventory/backup, а не
доказательство готовой функции.

## 1. Статус и источники фактов

### CURRENT — что работает до rollout

- Клиентский scope: `construction`, `home-services`.
- Заказ: L2, заголовок, необязательное описание, до 5 фото, способ цены и сумма,
  срок или точная дата, город/район, отображаемое имя.
- Отклик: одно сообщение, цена, срок исполнения.
- Контакт: только клиент открывает телефон мастера и звонит или пишет в
  WhatsApp; номер клиента мастеру не раскрывается.
- Нет in-app чата, выбора исполнителя внутри продукта, статуса «в работе», спора
  и платформенных платежей.

**Способ проверки, 2026-08-23:** исполняемый код
[`src/lib/product-scope.ts`](../src/lib/product-scope.ts),
[`src/features/orders/order-schema.ts`](../src/features/orders/order-schema.ts),
[`src/types/database.ts`](../src/types/database.ts), миграции `0009`, `0069`,
`0106`, `0109`, `0110`, `0115`, `0116` и текущие экраны `app/(tabs)/orders/**`.
Это проверка репозитория, не live production schema.

Последняя опубликованная iOS-версия в release ledger — `1.0.1` build `11`.
**Способ проверки, 2026-08-23:** [`release/production.json`](../release/production.json),
а не App Store Connect вживую.

### TARGET — что должно появиться после rollout

- Публикация разовой задачи в любой разрешённой сфере из 10 L1.
- Путь «Не знаю категорию» без принудительной ложной классификации.
- `onsite` и `remote`; локация обязательна только для `onsite`.
- Релевантная лента исполнителя «Для меня» и полная лента «Все».
- Жалоба, взаимная блокировка и модерация пользовательского контента.
- Сохранение черновика при переходе гостя в обычный login/register и возврат в
  форму без автоматической публикации.
- Обратная совместимость с уже установленной iOS 1.0.1 на всём периоде
  поэтапной раскатки.

TARGET нельзя описывать в интерфейсе или store metadata как уже работающий,
пока соответствующий feature-флаг выключен либо production gate не пройден.

## 2. Продуктовый контракт

### 2.1. Для кого и какую проблему решаем

Клиенту не нужно заранее знать профессию исполнителя или искать профиль в
каталоге. Он описывает результат: например, «вспахать участок трактором»,
«проверить договор у юриста» или «починить розетку». Люди, которые умеют это
сделать и имеют доступ к соответствующей категории, сами находят задачу и
откликаются.

Исполнитель получает две ленты:

- **Для меня** — классифицированные открытые задачи, совпавшие с его активными
  услугами, географией, режимом работы и требованиями верификации.
- **Все** — остальные разрешённые открытые задачи, доступные по явному поиску и
  фильтрам. Неклассифицированные задания живут здесь и не вызывают массовую
  рассылку.

### 2.2. Что входит

- Только разовая законная услуга с понятным результатом.
- Физические, выездные и дистанционные услуги.
- Регулируемая услуга допускается только через категорию с требуемой
  верификацией; наличие категории не заменяет проверку документов.
- Один клиент может быть исполнителем в другой ситуации через существующую
  dual-role модель.

### 2.3. Что не входит

- Товары, доставка товаров как отдельный маркетплейс, аренда без услуги.
- Вакансии, постоянная занятость, тендеры и долгосрочные B2B-проекты.
- Незаконные, опасные или запрещённые правилами площадки задания.
- In-app чат, lifecycle сделки, выбор победителя, escrow, спор и приём платежа.
- Автоматическая публикация или автоматический выбор исполнителя.
- Генеративный AI, который меняет пользовательский текст или принимает решение
  о допуске; возможная классификация всегда остаётся служебной подсказкой.

## 3. Таксономия и управление scope

### 3.1. Пользовательские L1

Целевая таксономия восстанавливает 10 пользовательских L1 из canonical seed:

| ID | Название |
|---|---|
| `construction` | Строительство и ремонт |
| `home-services` | Дом и быт |
| `auto` | Авто и техника |
| `transport` | Перевозки и спецтехника |
| `beauty-health` | Бьюти и здоровье |
| `education` | Образование |
| `events` | События и торжества |
| `business` | Бизнес и финансы |
| `it-digital` | IT и цифровое |
| `personal-services` | Личный сервис |

Отдельно существует **внутренний скрытый fallback L1/L2/L3**. Draft backend
contract закрепляет стабильные ID `xtrud-internal / other-services /
other-service`. Они не являются пользовательской таксономией: fallback никогда
не показывается как профессия или публичная категория каталога и не должен
утекать в UI-copy или продуктовую аналитику как обычная услуга.

### 3.2. Раздельные флаги категории

Для каждой пользовательской категории backend должен независимо отвечать на
четыре вопроса:

| Логический флаг | Значение |
|---|---|
| `task_creation_enabled` | Можно ли выбрать категорию при создании задания |
| `catalog_enabled` | Можно ли показывать каталог профилей этой категории |
| `matching_enabled` | Можно ли автоматически включать задания в «Для меня»/уведомления |
| `requires_verification` | Нужна ли подтверждённая квалификация для отклика |

Эти additive-колонки становятся частью сгенерированных типов. Клиент не
хардкодит четыре разных списка.

Правила включения:

1. В taxonomy/schema migration все восстановленные и новые пользовательские
   ветки создаются fail-closed: `task_creation_enabled`, `catalog_enabled` и
   `matching_enabled` выключены.
   Текущие `construction`/`home-services` продолжают обслуживать CURRENT.
2. Включение новой ветки выполняется отдельной явно просмотренной forward-only
   activation migration. Taxonomy restore не содержит `UPDATE ... = true` для
   нового scope.
3. `task_creation_enabled` можно включить раньше каталога: спрос измеряется даже при
   малом количестве исполнителей.
4. `catalog_enabled` включается отдельно, когда достигнут и зафиксирован supply
   threshold для категории и географии. Точное численное значение — открытое
   бизнес-решение, не константа этого документа.
5. `matching_enabled` включается только после проверки качества category mapping и
   eligibility исполнителей.
6. `requires_verification` проверяется сервером при отклике; скрытая кнопка в UI
   не является защитой.
7. `is_active`/`is_visible` legacy-поля не заменяют эти четыре смысла.

### 3.3. Выбор известной и неизвестной категории

**Известная категория:** пользователь выбирает L1 → L2, при необходимости L3.
Поиск учитывает названия L1/L2/L3 и `category_terms`. В `orders.l2_id` пишется
реальная L2, а пользовательский текст услуги сохраняется без потери.

**Не знаю категорию:** пользователь вводит `requested_service_text`, заказ
получает внутренний fallback `l2_id` и явное состояние классификации. Нельзя
подменять этот путь первой похожей категорией без подтверждения клиента.

Минимальные состояния классификации на уровне контракта:

- категория подтверждена пользователем;
- fallback/ожидает классификации;
- классифицировано модератором или доверенной автоматикой с audit trail;
- отклонено модерацией.

Точные SQL enum/значения определяются backend contract. Любая смена L2 после
публикации сохраняет первоначальный `requested_service_text`, автора решения,
время и предыдущую категорию.

### 3.4. Покрытие YouDo и Яндекс Исполнителей

Доказательная матрица приоритета, границы терминов «популярное»/`UNKNOWN` и
полное сопоставление внешних групп зафиксированы в
[`SERVICE_PRIORITY.md`](SERVICE_PRIORITY.md). Этот раздел хранит только краткий
rollout-контракт.

Проверка публичных каталогов 2026-08-26 подтвердила, что 10 L1 xtrud дают
целевое место всем группам, которые соответствуют модели короткой услуги, без
буквального копирования чужой таксономии. Аренда без услуги остаётся OUT, а
точный mapping охраны требует отдельного legal/product решения. Категории
YouDo раскладываются так:

| Группа рынка | Ветка xtrud |
|---|---|
| Курьеры, грузоперевозки | `transport` |
| Ремонт, строительство | `construction` |
| Уборка, бытовая техника | `home-services` |
| Компьютерная помощь, разработка, ремонт цифровой техники | `it-digital` |
| Фото, видео, аудио, мероприятия, промо | `events` |
| Дизайн | `it-digital / design` |
| Виртуальный помощник | `business / virtual-assistant` |
| Красота и здоровье | `beauty-health` |
| Юристы и бухгалтеры | `business` |
| Ремонт транспорта | `auto` |
| Репетиторы и обучение | `education` |

В feature-off draft `0120` дополнительно закреплены недостающие L2/L3:
виртуальный помощник, ремонт цифровой техники, персонал и промоакции,
аудиомонтаж и звукозапись, срочная доставка и «купить и доставить». Search
aliases для них намеренно не вставляются: текущий synonym RPC не фильтрует
feature-off targets. Они появятся только после отдельного search hardening,
live snapshot/backup, security gate, проверки предложения исполнителей и
activation migration.

Порядок первого rollout определяется не размером чужого каталога, а сочетанием
внешних market signals и локальной проверки xtrud: ремонт и
строительство → дом и уборка → перевозки и доставка → ремонт техники → авто →
образование. Реальный спрос Магаса и Назрани пока `UNKNOWN`; после запуска его
измеряют по запросам, нулевым результатам, созданным заданиям и откликам.

## 4. Модель данных и обратная совместимость

### 4.1. Единственные сущности

- `orders` — задание и его публичное состояние.
- `order_responses` — отклик исполнителя.

Запрещено создавать параллельные `tasks`, `requests`, `job_posts` или отдельный
response flow: это породит два набора RLS, лент, аналитики и экранов.

### 4.2. Поля задания

Целевой API сохраняет действующие поля и additive добавляет недостающие:

| Группа | Контракт |
|---|---|
| Категория | `l2_id` остаётся NOT NULL для старого iOS; для unknown используется внутренний fallback; `l3_ids` опциональны |
| Суть | `title` 5–120 символов; `description` до 2000; `requested_service_text` обязателен для unknown |
| Фото | `photo_urls`, не больше 5; те же upload/storage policy, что у текущего заказа |
| Формат | `work_mode = onsite | remote` |
| Место | город/район обязателен для `onsite`; для `remote` не требуется и не участвует в matching |
| Срок | `urgent`, `this_week`, `this_month`, `flexible` или `by_date` + `preferred_date` |
| Бюджет | `fixed`, `from`, `up_to`, `negotiable` + одно `budget_value` там, где требуется число |
| Автор | `client_id`; публично показывается `contact_name` либо имя профиля, но не номер клиента |
| Классификация | состояние, исходный текст и audit metadata без изменения пользовательского текста |
| Публикация | существующие `open`, `cancelled`, `expired`; черновик до публикации — клиентское persisted state, а не новый lifecycle сделки |

Ограничения и enum проверяет сервер. UI-валидация нужна для UX, но не заменяет
constraint/RLS/RPC.

### 4.3. Совместимость с iOS 1.0.1

Порядок всегда additive:

1. Снять live read-only schema/policies/grants/functions/buckets и encrypted
   backup; доказать restore на rehearsal.
2. Исправить P0 security отдельной forward-only migration.
3. Добавить категории, fallback и nullable/defaulted поля без удаления или
   переименования того, что читает старый binary.
4. Держать новую функциональность выключенной на backend.
5. Проверить старый binary: открытие существующих двух категорий, список,
   detail, создание и отклик не падают от новых строк/полей.
6. Включать новые категории только для клиентов, которые понимают fallback,
   `work_mode` и новые состояния.
7. Удалять legacy-контракт можно только после принятой политики minimum
   supported version; этот rollout удаления не включает.

Для старого клиента неизвестная новая категория не должна появляться в его
фильтрах или ответах. Backend обязан сохранять корректное поведение legacy RPC
и SELECT-проекций; полагаться на то, что старый UI «просто не нажмёт», нельзя.

## 5. UX-контракт создания задания

### 5.1. Один маршрут, адаптивное создание

Создание остаётся в одном маршруте `/orders/new`, но делится на две короткие
фазы вместо длинной формы или многоэкранного wizard:

1. «Что нужно сделать?» — свободный запрос пользователя.
2. Варианты названия из видимого каталога. Каждый вариант показывает категорию;
   только явный выбор одновременно подтверждает заголовок и L2. Если вариант не
   подходит, пользователь сохраняет свой текст и выбирает категорию вручную.
3. Компактные детали: описание, фото до 5, формат/место, срок или точная дата,
   цена и отображаемое имя.
4. Явная кнопка «Опубликовать бесплатно».

Подсказки не переписывают запрос генеративной моделью и не выбирают категорию
скрыто. Они детерминированно пересекают результаты поиска с категориями,
видимыми текущему клиенту. Для известных категорий допускаются 1–3 коротких
контекстных вопроса/подсказки; при отсутствии проверенной конфигурации всегда
остаётся универсальное ручное описание.

Поле не должно автоматически выбирать «Не срочно» или «Договорная»: срок и
вид цены пользователь подтверждает явно. Ошибка ведёт к первому неверному полю
и не стирает остальную форму.

Публикация в MVP бесплатна. Временное продуктовое решение — не более 3 открытых
заданий на аккаунт. До серверного rollout клиентская проверка является только
UX-precheck; атомарное ограничение должно быть реализовано на backend с защитой
от гонки двух устройств и идемпотентностью.

### 5.2. Масштабируемый category picker

Picker — полноэкранный, search-first и поддерживает путь L1 → L2 → L3. При
входе фокус остаётся предсказуемым: на iOS клавиатура не должна закрывать
результаты или sticky CTA, на web доступны Tab/Enter/Escape и browser Back.

Состояния:

- initial: 10 L1 и отдельное текстовое действие «Не знаю категорию»;
- search: совпадения по L2/L3/terms сгруппированы под L1;
- selected: видимый breadcrumb, возможность изменить выбор;
- no results: предложить unknown path, сохранив исходный запрос;
- loading/error/offline: повтор без потери введённого текста;
- disabled category: не выбирается, причина объясняется без обещания доступа.

### 5.3. Auth-return и черновик

Гость может заполнить форму, но публикует только после обычной регистрации или
входа. Anonymous JIT-account запрещён.

Контракт возврата:

1. До перехода в auth сохраняется версия draft schema, timestamp и все поля.
2. После успешного login/register пользователь возвращается в `/orders/new`.
3. Данные восстанавливаются и ещё раз валидируются по актуальному серверному
   scope.
4. Публикация не запускается автоматически: пользователь видит восстановленную
   форму и снова нажимает «Опубликовать».
5. После success черновик и временные фото очищаются; после logout/account
   switch PII-черновик предыдущего пользователя недоступен.

Фото должны либо пережить auth-return через управляемое временное хранилище и
TTL, либо форма до перехода явно предупреждает, какие фото нужно прикрепить
заново, и после возврата показывает соответствующее состояние. Молчаливо
потерять фото нельзя. Web `blob:` URL нельзя считать устойчивым после reload.

## 6. Лента, matching и отклики

### 6.1. «Для меня»

Задание попадает в персональную ленту, только если одновременно выполнены:

- `status = open` и срок действия не истёк;
- категория разрешает `matching`;
- L2/допустимое L3 совпадает с активной услугой исполнителя;
- для `onsite` совпадает зона работы; для `remote` география не ограничивает;
- исполнитель не является автором;
- между сторонами нет блокировки;
- обязательная верификация пройдена;
- задание и аккаунты не скрыты модерацией.

Сортировка сначала учитывает релевантность и свежесть. Рейтинг не должен
превращать ленту в вечную монополию старых исполнителей; конкретные веса
фиксируются отдельно и покрываются тестами.

### 6.2. «Все»

Показывает разрешённые открытые задания с поиском и фильтрами по категории,
формату работы, месту, сроку и бюджету. Неклассифицированные задания доступны
здесь после базовой модерации, но:

- не попадают в массовые push/email;
- не попадают в «Для меня» до надёжной классификации;
- не раскрывают контакт автора;
- могут быть переклассифицированы с audit trail.

### 6.3. Отклик и контакт

Один исполнитель отправляет не более одного активного отклика на заказ:
сообщение, способ цены/сумму и опциональный срок. Сервер проверяет `open`,
eligibility, self-response, блокировку, модерацию и verification независимо от
UI.

Клиент видит имя, мастер-профиль, рейтинг, текст, цену и срок. Только клиент
может инициировать `tel:`/WhatsApp по контакту исполнителя. Телефон и иные
прямые контакты клиента не возвращаются исполнителю ни через таблицу, RPC,
storage metadata, URL preview, analytics payload или error report.

## 7. Безопасность, жалобы, блокировки и модерация

### 7.1. Жалоба

Жалоба возможна на пользователя, заказ, отклик и отзыв. Если enum `reports`
ещё содержит legacy `message`, его нельзя трактовать как наличие чата; новый
тип отклика добавляется backward-compatible migration либо однозначным
контрактом target ID.

Модерация меняет видимость/допуск контента и аккаунтов. Она не создаёт статус
сделки и не возвращает dispute flow.

### 7.2. Блокировка

Блокировка пользователя имеет серверный двусторонний эффект независимо от
того, кто нажал кнопку:

- стороны не видят профили, заказы и отклики друг друга;
- нельзя создать новый отклик или открыть контакт;
- существующий отклик не даёт обойти блок через прямой detail URL;
- RPC/REST/Realtime дают тот же результат, что UI-фильтр;
- админ сохраняет минимально необходимую видимость для расследования жалобы;
- unblock не восстанавливает автоматически удалённые/скрытые действия.

Хранить только локальный список скрытых карточек недостаточно.

### 7.3. P0 gates до backend rollout

До применения feature migration обязательны:

1. live read-only inventory production schema, RLS, grants, functions, Auth,
   Storage buckets/policies и migration ledger;
2. encrypted backup вне репозитория и успешный rehearsal restore;
3. forward-only исправление известных P0-кандидатов: self-admin, demo-admin,
   owner-update trust/ranking, anonymous contact/login RPC, account deletion и
   secret in legacy history;
4. RLS tests минимум для anon, клиента-владельца, другого клиента,
   подходящего/неподходящего мастера, blocked pair, moderator/admin и
   service-role;
5. rate limit/anti-abuse для создания, отклика, жалобы и раскрытия контакта;
6. проверка, что storage paths и signed URL не обходят блокировку/модерацию.

## 8. Наблюдаемость и продуктовые метрики

События не содержат свободный текст, телефоны, email, точный адрес или URL
фотографий. Минимальный набор:

- начало/завершение формы, выбор known/unknown, auth-return success/failure;
- доля публикаций по L1/L2 и `work_mode`;
- search with no result и доля unknown;
- время до первого релевантного отклика;
- задания без откликов через 24/72 часа;
- просмотр контакта клиентом после отклика;
- report/block rate по категории;
- moderation queue age и доля переклассификации;
- supply threshold: активные проверенные исполнители и response coverage по
  категории/географии.

Численные цели и supply threshold утверждает бизнес-директор после появления
baseline. Пока фактические production значения не измерены, их нельзя
придумывать в документации или release gate.

## 9. Rollout и rollback

### 9.1. Rollout функции

1. Утвердить этот продуктовый/data/UX контракт.
2. Получить live inventory, encrypted backup и rehearsal restore.
3. Закрыть P0 security отдельной forward-only migration.
4. Additive восстановить таксономию, fallback, выключенные флаги, поля, индексы
   и RLS; новый scope остаётся fail-closed.
5. Обновить сгенерированные типы и контрактные тесты.
6. Проверить старую iOS 1.0.1 при feature-off backend.
7. Выпустить feature-off web canary, наблюдать ошибки и legacy flow.
8. Отдельной activation migration включать
   `task_creation_enabled`/`matching_enabled` по категории и согласованной
   когорте; `catalog_enabled` включать отдельно после supply threshold.
9. Собрать и проверить новую iOS на реальном устройстве, затем submit отдельной
   явной командой владельца.
10. Android считать активным только после preview build и полной platform QA.

Rollback функции — выключить соответствующий category/cohort flag. Данные и
forward migration не откатываются разрушительным SQL; новые заказы остаются
доступны владельцу и модерации, а старый клиент не получает неизвестный scope.

### 9.2. Перенос backend на Beget — отдельная программа

Feature rollout не зависит от одновременного cutover на Beget. Порядок
self-hosted migration, dual-run/transition и rollback определён в
[`SUPABASE_BEGET_MIGRATION.md`](SUPABASE_BEGET_MIGRATION.md). Нельзя объединять
в один production change:

- security migration;
- universal task feature;
- смену backend URL/провайдера.

Каждое изменение имеет собственный backup, canary, наблюдение и rollback
decision. Старый iOS binary не переключится на новый backend без новой сборки.

## 11. Открытые решения и production facts

- Точные SQL enum/колонки классификации — определяет backend contract и
  сгенерированные типы; этот документ фиксирует семантику.
- Supply threshold для включения каталога — решение бизнес-директора по данным.
- Перечень категорий и документов для `requires_verification` — юридическая и
  операционная проверка по региону работы; на 2026-08-23 не подтверждён.
- Оператор, сроки хранения и правила обработки пользовательского контента —
  требуют юридически подтверждённых production данных.
- Live Supabase schema/RLS/data volume и применённые migration SHA — не
  подтверждены; Git migration chain не считается production snapshot.
- Реальная работа iOS universal links, Android и Beget cutover — отдельные
  неподтверждённые platform/infra факты.

## 12. Когда применять этот документ

**Применять:** при изменении создания задания, категории/поиска, ленты,
matching, откликов, contact disclosure, report/block/moderation, RLS или rollout
universal scope.

**Не применять как доказательство:** что TARGET уже выложен, production БД
совпадает с миграциями, конкретная категория юридически разрешена или каталог
достиг supply threshold. Для этого нужны датированные live-проверки.
