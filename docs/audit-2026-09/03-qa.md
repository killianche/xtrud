## 2. Два предыдущих fatal-крэша из client_errors — статус

### 2.1. MasterCard `TypeError: undefined is not a function` (45×, 1.0.3, до 2026-09-10) — ИСПРАВЛЕНО (FACT)

`git show c2d39d0` (2026-09-10, ledger 73): причина — миграция PostgREST→
node-pg моста (2026-09-08) стала отдавать `numeric`/`bigint` строками вместо
чисел; `SpecialistsListScreen.tsx` вызывал `master.rating_avg.toFixed(1)` —
у строки нет `.toFixed`. Исправлено на сервере (парсеры типов pg) + защита на
клиенте: `src/features/master-view/SpecialistsListScreen.tsx:108-113` теперь
оборачивает в `Number(master.rating_avg).toFixed(1)` с явным комментарием
«причина исправлена на сервере, здесь — защита на будущее». Ошибок после
2026-09-10 в присланной сводке нет — согласуется с датой фикса.
**Остаточный риск (мелочь, UNKNOWN):** тот же класс бага (node-pg отдаёт
numeric строкой) мог остаться в других местах, где сервер возвращает числовые
поля и клиент делает `.toFixed()`/арифметику без `Number()`. Я НЕ прогонял
grep по всему `src/` на `\.toFixed\(` за отведённое время — это `UNKNOWN`,
способ проверки: `grep -rn "\.toFixed(" src app | grep -v "Number("`.

### 2.2. «Maximum update depth exceeded» (7×, 1.0.2, error-boundary, до 2026-09-07) — вероятно устарело, не подтверждено (UNKNOWN)

Последняя запись 2026-09-07, версия 1.0.2 (текущая — 1.0.4/build 105).
Не нашёл конкретный commit-фикс за отведённое время (не искал целенаправленно
— бюджет ушёл на два других пункта). Since версия сильно устарела и ошибок
после неё нет, вероятность регрессии в 1.0.4 невысокая, но это предположение,
не факт. **UNKNOWN**, способ проверки: найти компонент через `context`/`stack`
в самих записях `client_errors` (стек не символизирован — нужен offset-анализ
или переисполнение сценария на 1.0.4).

### 2.3. Realtime `cannot add postgres_changes callbacks…` (5×) — ИСПРАВЛЕНО (FACT)

`src/lib/realtime-topic.ts` целиком — детальный комментарий разбора от
2026-09-04 (commit `6d3a190 fix(realtime): падение приложения после
регистрации»). Причина: `supabase.channel(topic)` переиспользует существующий
канал по имени; React cleanup синхронный, `removeChannel` асинхронный —
двойной запуск эффекта (типичный путь: гость → регистрация → userId меняется)
добавлял обработчик к уже подписанному каналу → exception → white screen
«Что-то пошло не так». Решение — уникальное имя канала на каждую подписку
(`uniqueRealtimeTopic`). Realtime (`postgres_changes`) **всё ещё используется
в проде** — `app/(tabs)/_layout.tsx` (`useRealtimeNotifications`), это не
legacy, вопреки тому, что можно было предположить по «своему серверу вместо
Supabase»: подписки идут напрямую в Postgres realtime, а не через
xtrud-api. Фикс выглядит корневым (устраняет причину гонки, а не симптом).

### 2.4. Push запрещён (3×), таймаут 12 с (2×) — не разбирались отдельно (UNKNOWN)

Таймаут 12 с — это, вероятно, штатное срабатывание `REQUEST_TIMEOUT_MS`
(`src/lib/fetch-with-timeout.ts:26`) на реально плохой сети, а не баг; но это
предположение — не проверено, что клиент в этих 2 случаях получил
«Нет связи»/офлайн-каталог, а не тупик. «Push запрещён» — это, скорее всего,
не ошибка приложения, а фиксация системного отказа (`Notifications denied`),
нужно смотреть `context`, чего я не делал.

## 3. Идемпотентность и double-tap — выборочная проверка (FACT)

Проверил три самых опасных с точки зрения гонки действия (владелец явно
просил double-tap-проверку):

| Действие | Клиент — защита от повторного тапа | Сервер — защита от гонки |
|---|---|---|
| «Опубликовать» задание | `app/(details)/orders/new/review.tsx:67,68,71,207` — `publish.busy` блокирует `usePreventRemove`, `useBackGestureLock`, `useUnsavedChangesGuard` и саму кнопку. **Хорошо.** | не проверял RPC на этот заход (UNKNOWN) |
| «Откликнуться» | `src/features/orders/RespondSheet.tsx:115` — `if (!valid \|\| submit.isPending) return;`, кнопка получает `busy={submit.isPending}` (строка 267). **Хорошо.** | не проверял RPC (UNKNOWN) |
| «Выбрать исполнителем» (`pick_order_master`) | **Дефект.** `app/(details)/orders/[id].tsx:1503-1514` — кнопка `Pressable` без `disabled`/`busy`, не привязана к `pickMaster.isPending`. Единственный барьер — `confirmAsync` (диалог подтверждения, строки 247-255), это не защита от быстрого второго тапа после подтверждения. `manageBusy` (строка 410) агрегирует `isPending` для `complete/unpick/cancel/reopen/delete`, но **не для `pickMaster`** — то есть баг не «забыли добавить disabled», а конкретно пропустили один mutation в общем механизме, который для всех остальных сделан правильно. | **Сервер защищён**: `supabase/migration-drafts/0196_order_lifecycle_pick_complete.sql:57-59` — `SELECT ... FOR UPDATE` на order, и `IF v_order.status <> 'open' THEN RAISE EXCEPTION` (ERRCODE `P0001`, DETAIL `order_not_open`). Второй параллельный вызов **не сможет** выбрать второго исполнителя или испортить данные — упадёт с понятной ошибкой. |

**Итог: мелкий дефект, не блокер.** Данные в безопасности (сервер держит
инвариант через row lock), но реальный человек при двойном тапе увидит
Alert «Не удалось выбрать — Этот отклик уже неактуален» после уже
состоявшегося успешного выбора — пугающая ложная ошибка после факта успеха.
**Файл:строка:** `app/(details)/orders/[id].tsx:1503` (кнопка),
`app/(details)/orders/[id].tsx:410-419` (`manageBusy`, куда `pickMaster` не
включён). **Severity: мелочь-важно** (UX, не данные). **FACT.**

`complete_order` (`0196_order_lifecycle_pick_complete.sql:156-183`) — тот же
паттерн защиты: `FOR UPDATE`, проверка `status <> 'in_progress' OR
picked_master_id IS NULL`. На клиенте `completeOrder.isPending` **включён** в
`manageBusy` (строка 410) — эта кнопка защищена корректно, в отличие от
`pickMaster`.

## 8. Процесс качества — что `quality:check` проверяет и чего нет (FACT)

`package.json`: `quality:check` = governance-check, набор supabase
integrity/backup-safety/security-hardening/rehearsal/production-contract
**тестов-скриптов** (проверяют миграции/контракты, не runtime), catalog
test+check, security:audit:test, release:contract/legal/version
test+check, mobile:config check+test, `typecheck`, `tokens:check`,
`biome ci`, `npm test` (юнит-тесты, см. раздел 5), проверка версий и
статических ассетов. **Чего нет:** ни одного e2e/UI-теста, ни одного
screenshot-теста, ни одной проверки на реальном/симулированном устройстве,
ни одной проверки VoiceOver/Dynamic Type автоматически. `release:check`
добавляет `catalog:drift:check`, `security:audit`, `ios:bundle:check` — тоже
не runtime UI. Мониторинг после релиза — только `client_errors` без
символизации стека (сам факт подтверждён заданием владельца: «Стек не
символизирован»), то есть каждый новый crash требует ручного сопоставления
offset↔строка, как я делал вручную для MasterCard через `git log -p`.
