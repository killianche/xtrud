4. **Ценообразование:** WORKING + **КРИТИЧНО НЕПРАВИЛЬНО** — таблица `master_services` работает, CRUD реализован в `MasterServicesSection`, но есть **два параллельных подхода к ценообразованию**: (а) `master_categories.pricing_mode` (per_hour/per_unit/negotiable/on_quote) + пустой JSONB-поле `pricing`; (б) плоский `master_services` список. 6. **Аналитика:** STUB — рейтинг из отзывов работает (trigger `recalc_master_rating`), но дашборда нет. Счётчик просмотров профиля отсутствует.

7. **Безопасность / Trust:** PARTIAL — `verification_level` (0-5) есть в БД, но нет UI для загрузки паспорта/ИНН. Бейджи показываются в коде, но не тестированы.

8. **Ролевая модель:** WORKING — dual-role (client + master), переключение через свитчер на главной, `active_role` в users. Может ли быть несколько мастер-профилей? Нет, 1-к-1 связь `users.id ↔ master_profiles.user_id`.

9. **Поиск мастеров** (клиент): WORKING — фильтры по категории, городу, рейтингу в каталоге. Карточка мастера показывает: имя, рейтинг, опыт, услуги + цены, портфолио.

10. **Push-уведомления:** STUB — таблица `notification_tokens` есть, но фронтенд не отправляет FCM токены. Expo Notifications не подключены.

11. **Stub'ы и TODO:** (а) Верификация паспортом; (б) Шаблоны ответов; (c) Скрытие телефона; (d) Push-уведомления; (e) Маскированные звонки; (f) CRM-лайт.

## 3. Категории и таксономия

### Структура в БД

- **Таблицы:**
  - `categories_l1` — корневые категории (8 штук, например «Жилищно-коммунальные услуги»)
  - `categories_l2` — подкатегории (32 штуки, например «Сантехника», «Электромонтаж», «Плиточные работы»)
  - `categories_l3` — услуги (множество, например для «Сантехника»: «Замена смесителя», «Установка унитаза»)

- **Связь с мастером:**
  - `master_categories(master_id, l2_id, l3_ids, pricing_mode, pricing, category_bio, category_radius_km)`
  - Мастер выбирает: до 5 L2 (max), для каждой L2 — какие L3 делает (опц., пустой массив = все)
  - `pricing_mode` enum: `per_hour`, `per_unit`, `negotiable`, `on_quote`
  - `pricing` JSONB: (пусто в текущей версии) должно хранить `{l3_id: {min, max, unit}}`

### UX выбора категорий

#### В онбординге мастера
- **Экран:** `app/(onboarding)/master-categories.tsx` (200 строк)
- **Паттерн:** вертикальный список чипсов (toggles) с иконками L2
- **Логика:**
  - Загружаются видимые L2 через `useVisibleCategories()`
  - Мастер тапает на L2 → toggle (выбирает/отменяет)
  - Лимит 5 L2 — 6-я и дальше становятся disabled
  - Нет видимого выбора L3 (то есть мастер **выбирает только L2, не L3**)
  - Кнопка «Продолжить» (onboarding mode) или «Сохранить» (edit mode)
  - Progress-bar сверху (только в onboarding режиме)

- **Проблемы:**
  1. **L3 не выбираются при онбординге** — мастер не видит какие именно услуги (L3) он будет делать в каждой L2. Это предполагает, что он делает ВСЕ L3 в выбранной L2, либо L3 выбираются потом через настройки. В коде: `l3_ids` пусто после онбординга.
  2. **Нет preview-листа** — клиент не видит ещё на этапе wizard'а, как будет выглядеть список категорий (какие иконки, порядок).
  3. **Нет search/typeahead** — при 32 L2 при полном раскрытии это может быть долгий scroll. Лучше бы как в `/orders/category-select` (typeahead bottom-sheet).

#### В поиске заказов клиентом
- **Компонент:** `src/components/CategoryPicker.tsx` (113 строк)
- **Паттерн:** inline-button → открывает полный экран `/orders/category-select`
- **Логика:**
  - Кнопка показывает выбранную категорию либо placeholder «Выберите категорию»
  - При тапе → `router.push('/orders/category-select')`
  - На `category-select`: typeahead bottom-sheet (TODO задача в TASKS.md, пока заглушка)
  - Результат пишется в Zustand store `useOrderDraftStore().selectedL2`
  - При mount CategoryPicker слушает store и пропагирует в react-hook-form через onChange

- **Что здесь хорошо:** draft persistence в Zustand, разделение concerns (выбор на отдельном экране)

### Источник категорий

- **Хардкод:** `src/lib/category-config.ts` (не прочитан в аудите, но упоминается в TASKS.md как `DISTRICTS` const)
- **Или БД:** таблицы `categories_l1/l2/l3` с заполненными семенами (миграции `0035_focus_repair_categories.sql` и `0037_new_taxonomy_32_l2.sql`)
- **Для UI:** хук `useVisibleCategories()` загружает всё из БД

### Проблемы / КРИТИЧНО НЕПРАВИЛЬНО

1. **L3 категории не выбираются при онбординге** — wizard'е мастера нет шага «какие услуги (L3) вы выполняете в каждой L2». Это либо:
   - Упущение (нужно добавить шаг)
   - Либо допущение: мастер автоматически видит все L3 в L2, клиент может отфильтровать при создании заказа
   
2. **UX выбора категорий на вебе** — вертикальный список из 32 чипсов, если раскрыть все L2, может быть слишком многословным. Яндекс.Услуги / Avito Услуги используют typeahead + иерархию (L1 → L2 → L3). Здесь это только для клиента (`CategoryPicker`), для мастера нет typeahead.

3. **Путаница L2 vs L3** — код использует L2 как идентификатор мастера («мой L2»), но L3 внутри L2 — реальные услуги. Когда клиент ищет по L3, как система поймёт, какого мастера показать? Логика в `useMasterFeed`: фильтр по `l2_ids` (мои категории) + `city_id`. То есть поиск идёт по L2, L3 — только для отображения.

## 4. Ценообразование

### Структура в БД

**Вариант А: `master_categories.pricing_mode` + `pricing` JSONB**
- Таблица: `public.master_categories`
- Поле: `pricing_mode` enum (per_hour / per_unit / negotiable / on_quote)
- Поле: `pricing` JSONB (пусто, не используется)
- Назначение: **нет UI для заполнения**, поле зарезервировано для будущего

**Вариант Б: `master_services` (плоский прайс-лист)**
- Таблица: `public.master_services`
- Поля: `title` (text), `price_min` (int), `price_max` (int nullable), `unit` (enum per_hour/per_task/per_m2/per_day)
- Лимит: до 20 услуг на мастера (trigger)
- Назначение: **основной источник цены в текущей версии**

### UI для добавления/редактирования цены

**В профиле мастера:** `app/(tabs)/profile/edit-master.tsx`
- Компонент: `<MasterServicesSection masterId={userId} />`
- CRUD реализован: хук `useUpsertMasterService()` + `useDeleteMasterService()`
- Форма в Modal:
  - `title` (text input, 2-100 символов)
  - `price_min` (number input, обязательный)
  - `price_max` (number input, опц., может быть NULL)
  - `unit` (chips: per_hour / per_task / per_m2 / per_day)
  - Валидация: min >= 0, max >= min
- Список услуг: карточки с inline edit/delete кнопками
- Empty state: «Прайс ещё пустой»
- Счётчик: «3 из 20 услуг»

### Отображение цены (публичное)

**На карточке мастера (`master/[id].tsx`):**
- Компонент: `<MasterServicesList masterId={userId} hideTitle={false} />`
- Показывает: title + formatPriceRange(price_min, price_max) + SERVICE_UNIT_LABELS[unit]
- Карточки с bg-canvas-soft, padding 16, radius xl
- Skeleton при загрузке

**На карточке в каталоге (при поиске):**
- Неясно, показывается ли цена (нужно проверить `/search` экран)

### Проблемы / КРИТИЧНО НЕПРАВИЛЬНО

1. **Два параллельных подхода к ценообразованию:**
   - `master_categories.pricing_mode` — ставится при онбординге, но **нет UI для редактирования**
   - `master_services` — полностью рабочий, но **отдельный от категорий**
   - Вопрос: какой использовать? Система выбирает `master_services` (видно в `master/[id].tsx`)

2. **`pricing_mode` выбирается в wizard'е, но не отображается и не редактируется**
   - В `app/(onboarding)/master-categories.tsx`: нет UI для выбора `pricing_mode`
   - Поле пусто в БД после онбординга
   - Надо либо добавить UI в wizard, либо перенести в `edit-master`

3. **Нет линка между категорией и услугой**
   - `master_services` не содержит `l2_id` (какой категории принадлежит услуга)
   - Это значит: либо услуги общие для всех категорий мастера, либо система не различает
   - Возможное решение: добавить `l2_id` в `master_services` (одна услуга может быть под несколькими L2)

4. **`price_max` == NULL интерпретируется как «от X»**
   - Это работает, но formatPriceRange логику надо проверить: `{min} ₽` если max null, или `{min}-{max} ₽`?

5. **Нет «договорная цена» / «запрос цены» UX**
   - Когда мастер выбирает `pricing_mode='on_quote'`, клиент должен видеть что-то вроде «цена по договорённости»
   - Но это не реализовано нигде (очередной unused параметр)

## 5. Заказы (вид мастера)

### Экран входящих заказов

- **Главная роутная страница:** `app/(tabs)/orders/index.tsx`
  - Проверяет `active_role` юзера:
    - `client` → `<ClientOrdersView />` (список моих заказов)
    - `master` → `<MasterOrdersView />` (3 таба)

- **Master view — 3 таба:**
  1. **Новые** (`tab='new'`)
     - Источник: `useMasterFeed({ userId, l2Ids })` (infinite query, fetchNextPage)
     - Фильтры: `status='open'`, `l2_id IN (мои)`, `city_id = мой` (или null = всех городов)
     - Показывает только заказы, на которые мастер ещё не откликнулся
     - CTA: тап на карточку → `/orders/[id].tsx`

  2. **Я откликнулся** (`tab='responded'`)
     - Источник: `useMyResponses(userId)`
     - Показывает: статус отклика (sent / viewed / rejected / withdrawn)
     - Видны: краткие данные заказа + статус отклика

  3. **Меня выбрали** (`tab='assigned'`)
     - Источник: `useOrdersAssignedToMe(userId)`
     - Фильтр: `status IN ('in_progress', 'completed')`
     - Видны: текущая работа + завершённые

### Как заказ попадает к мастеру

- **Broadcast модель:** клиент создаёт заказ → система **публикует событие** через Supabase Realtime
- **или:** заказ просто видим в `master_feed` для всех подходящих мастеров (по L2 и городу)
- **Push-уведомления:** trigger'ы в БД готовы (`notify_on_new_order_for_master`), но фронтенд не получает FCM токены (отсутствует `expo-notifications`)

### Принять/отклонить/предложить цену

- **Отклик:** клиент создаёт запись в `order_responses(order_id, master_id, status='sent', proposed_price?)`
- **UI для создания отклика:** экран `/orders/[id].tsx` (большой файл, 65 КБ)
  - Форма `OrderFormBody` (401 строка)
  - Поля: `proposedPrice` (опц.), `comment`, `estimatedDays`
  - Кнопка: «Отправить отклик» (либо ошибка валидации)
  - После submit: `order_responses` инсертится, мастер видит в табе «Я откликнулся»

- **Отклонение отклика клиентом:** нет явного UI (но есть RPC `reject_response`)

- **Завершение заказа:** мастер нажимает «Я выполнил работу» → RPC `confirm_work_done` (миграция 0041)

### Чат с клиентом

- **Таблица:** `chats(id, order_id, client_id, master_id, last_message_at, last_message_text)`
- **Сообщения:** `chat_messages(id, chat_id, user_id, body, created_at)`
- **Где находится:** `app/(tabs)/chats/` (несколько файлов)
- **Что есть:**
  - Список чатов (с последним сообщением, time, unread badge)
  - Тредед чат (bubbles с аватарами, дата-сепараторы)
  - Поле ввода + кнопка отправки
  - Кнопка «Я выполнил работу» в чате (для выбранного мастера)

- **Что отсутствует:**
  - Шаблоны ответов (quick replies)
  - Скрытие номера телефона при неподтверждённом заказе
  - Маскированные звонки (рано, опционально)

### Проблемы / стабы

- **Push-уведомления:** таблица `notification_tokens` есть, trigger'ы готовы, но фронтенд не отправляет токены
- **Статус заказа** — нет явного UI для мастера «когда я откликнулся и какого я жду ответа»
- **Withdraw отклика** — нет UI для мастера (только клиент может отклонить)

## 6. Аналитика и инструменты для мастера

### Рейтинг и отзывы

## Главные проблемы (упорядочены по серьёзности)

### 🔴 КРИТИЧНЫЕ (блокируют launch или наносят UX ущерб)

1. **Ценообразование: путаница `pricing_mode` vs `master_services`**
   - Файл: `supabase/migrations/0007_master_categories.sql` (строки 35-38 — поле `pricing_mode`)
   - Файл: `supabase/migrations/0024_master_services.sql` — плоский прайс
   - Проблема: одновременно два подхода. `pricing_mode` устанавливается при онбординге, но нет UI для редактирования. `master_services` полностью рабочий, но отдельный от категорий.
   - Что показать клиенту: только `master_services` (из `MasterServicesList.tsx`)
   - Что с `pricing_mode`? Неясно.
   - **Решение:** либо убрать `pricing_mode` и полностью перейти на `master_services`, либо добавить UI для редактирования `pricing_mode` per-категории.

2. **Категории: L3 не выбираются при онбординге**
   - Файл: `app/(onboarding)/master-categories.tsx` (нет шага для выбора L3)
   - Проблема: мастер выбирает 5 L2 категорий, но какие L3 (услуги) внутри каждой L2 он выполняет — неизвестно. После онбординга `l3_ids` остаётся пустым массивом.
   - Вопрос: это допущение (мастер делает ВСЕ L3 в L2)? Или упущение?
   - **Решение:** либо добавить шаг «выберите услуги (L3) для каждой L2» в wizard, либо документировать что пустой `l3_ids` означает «все L3».

3. **UX выбора категорий для мастера**
   - Файл: `app/(onboarding)/master-categories.tsx` (200 строк)
   - Проблема: вертикальный список из 32 чипсов при раскрытии слишком многословен. Конкуренты (Яндекс.Услуги, Avito Услуги) используют typeahead + иерархия.
   - Текущая реализация работает, но UX хуже чем у конкурентов.
   - **Решение:** либо добавить search-input для фильтрации L2, либо использовать паттерн из `/orders/category-select` (typeahead bottom-sheet).

4. **Скрытие номера телефона мастера**
   - Файл: `supabase/migrations/` (нужно искать RLS policy для чата)
   - Проблема: номер телефона мастера виден в чате до подтверждения заказа. Это небезопасно.
   - Текущее состояние: нет UI для маскирования (например, `+7 9** *** 45 68`)
   - **Решение:** в компоненте Chat показывать masked phone вместо полного. Только после `order.status='confirmed'` или `payment_completed` показать полный номер.

### 🟡 ВАЖНЫЕ (влияют на engagement, retention, но не блокируют)

5. **Push-уведомления не работают**
   - Файл: `src/lib/supabase.ts` (нет кода для получения FCM/APNs токена)
   - Проблема: мастер не узнаёт о новых заказах в реальном времени. Он должен сам открыть app и обновить.
   - Текущее состояние: таблица `notification_tokens` есть, trigger'ы `notify_*` готовы в БД, но фронтенд не отправляет токены.
   - **Решение:** подключить `expo-notifications`, при mount приложения получить токен и сохранить в БД.

6. **Нет дашборда аналитики**
   - Файл: нет файла (неэкономно, TODO)
   - Проблема: мастер не видит сколько просмотров его профиля, сколько потенциальных клиентов отклонил, сколько успешных сделок закрыл.
   - Это критично для удержания мастера (он видит ценность своего труда).
   - **Решение:** создать `/master/analytics` (или аналитику в `/profile/edit-master`) с: кол-во просмотров, сколько откликов получил, conversion rate, заработанные деньги (если есть платежи).

7. **Верификация мастера (паспорт, ИНН)**
   - Файл: нет файла (отсутствует UI)
   - Проблема: поле `verification_level` в БД не используется из UI. Мастер не может загрузить паспорт или подтвердить статус самозанятого.
   - **Решение:** создать экран верификации (возможно, в `/profile/edit-master` или отдельный) с: фото паспорта, селфи, ИНН, и отправкой на модерацию.

8. **Нет шаблонов ответов**
   - Файл: нет файла (отсутствует UI + БД таблица)
   - Проблема: мастер вводит полный ответ каждый раз. Для типовых заказов это медленно.
   - **Решение:** в чате добавить dropdown с 3-5 шаблонными ответами (например, «Спасибо! Смогу в чт» / «Нужно в выезде» / …).
